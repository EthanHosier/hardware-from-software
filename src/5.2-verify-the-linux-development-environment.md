# 5.2 — Verify the Linux development environment

You can already reach the Pi through SSH from [5.1](5.1-prepare-raspberry-pi-os-and-ssh.md). Now identify the machine behind that shell, install its development tools, build and select the book's common kernel, and run a C++ program on it. This kernel already enables AF_XDP, so GPIO, buses, modules and later networking all use one baseline. The result is a saved environment record, a matching kernel build tree and a native Linux executable.

Keep the Pi powered through its USB-C supply, with its network connection and microSD card in place. Its GPIO header remains unwired. Keep the Pico's existing LED/button circuit intact, separate and unplugged, as left in 5.1. There are no Pi–Pico signal or power connections in this lesson.

## One Arm processor family, different execution environments

The Mac, Pi 4, and Pico 2 all have Arm processors, but their programs are not interchangeable. The Mac compiler normally produces macOS executables. The `arm-none-eabi-g++` installed for the Pico produces embedded firmware. Here, the Pi's distribution-provided `g++` produces a Linux application for the Pi itself: a **native build**.

Linux loads that application as a process, supplies its standard output, and reclaims its resources when it exits. There is no BOOTSEL operation, UF2 copy, or replacement of the running operating system. A later kernel module is a third case: code built for the running kernel's internal interfaces, using the kernel's build system.

## Record the machine

1. In the **Pi SSH shell**, start in your home directory and create a uniquely named record. Keep this shell open so that `env_record` remains available for later commands.

```sh
cd ~
env_record=$(mktemp "$HOME/linux-environment.XXXXXX.txt")
{
    date -Is
    printf 'Board: '
    tr -d '\000' < /proc/device-tree/model
    printf '\n'
    cat /etc/os-release
    uname -m
    uname -r
    dpkg --print-architecture
    free -h
    grep '^MemTotal:' /proc/meminfo
    df -h / /boot/firmware
} | tee "$env_record"
printf 'Record saved in %s\n' "$env_record"
```

The model should identify a Raspberry Pi 4 Model B, including its revision. For this book's 64-bit route, expect `aarch64` from `uname -m` and `arm64` from `dpkg`: the kernel and Debian package tools use different names for the same architecture. Check both; a 64-bit kernel alone does not establish that the installed userspace is 64-bit.

Read the actual memory result rather than assuming a “3GB Pi”. `MemTotal` is memory available to Linux after reservations; `free` also distinguishes memory currently used, available, and used for caches. Neither is a label printed on the RAM package. Unexpectedly low capacity is a reason to check the board identification and configuration, not to infer a new Pi model.

`/etc/os-release` identifies the distribution, such as Debian 12 Bookworm underneath Raspberry Pi OS. `uname -r` identifies the **kernel currently running**. Package updates can install a newer kernel while the old one continues running until reboot. The two version numbers answer different questions.

For a fresh card, the book selects Raspberry Pi OS **Legacy Lite, 64-bit, Bookworm**. The image's packaged kernel is only the bootstrap environment for this page. Our common kernel is built from Raspberry Pi source commit `ae161617d7a4552fa91d03626b8d9f3696d17481` and named **`6.12.96-hfs1-v8`**. It retains the pinned official configuration with `CONFIG_XDP_SOCKETS=y` and a distinct local version. Enabling that feature makes AF_XDP available; it does not redirect any traffic until a later program explicitly sets that up. The earlier UART, I²C, GPIO and memory examples use their usual Linux interfaces.

An existing compatible 64-bit Raspberry Pi OS installation need not be erased. The automated installation route is deliberately limited to the standard Pi 4 microSD layout: an ext4 root filesystem directly on `/dev/mmcblk0p2`, with its FAT boot partition mounted at `/boot/firmware`. USB-root, encrypted-root and other custom boot layouts need separate validation; do not force this installer past a failed layout check. Complete the same custom-kernel setup before the hardware lessons. The original packaged boot files stay available for emergency recovery, rather than becoming a second profile to alternate between during the course.

2. Inspect the boot layout, still on the **Pi**, from `~`:

```sh
findmnt /boot/firmware
ls -l /boot/firmware/config.txt /boot/firmware/cmdline.txt
```

Bookworm and current Raspberry Pi OS mount the boot partition at `/boot/firmware`. Firmware reads `config.txt` before Linux starts; `cmdline.txt` supplies kernel command-line arguments. These files matter when we enable buses later. We will back them up and add a separate kernel selection below; leave them unchanged for now. An older guide's `/boot/config.txt` may refer to a different layout; establish the real mount and files before following such instructions. See the [official configuration-file documentation](https://www.raspberrypi.com/documentation/computers/config_txt.html).

## Install the native tools

3. On the **Pi**, working directory `~`, install the distribution packages:

```sh
sudo apt update
sudo apt install build-essential git file bc bison flex libssl-dev libelf-dev dwarves python3 kmod xz-utils device-tree-compiler ca-certificates
command -v gcc g++ make git
gcc --version
g++ --version
g++ -dumpmachine
make --version
```

Review APT's proposed changes before accepting. `apt update` refreshes the package index; it does not itself upgrade installed packages. Debian's [`build-essential`](https://packages.debian.org/bookworm/build-essential) brings in GCC, G++, Make, and C library development files. G++ supplies the C++ headers and links the C++ runtime. Git retrieves the examples and pinned kernel source; `file` identifies the result. `bc`, Bison, Flex and the SSL/ELF development libraries support the kernel build; Python runs our build and installation scripts. `kmod` supplies module utilities, and `dtc` compiles Device Tree data. There is no need to install the Pico SDK or the Mac's pinned embedded toolchain on the Pi for this program.

Expect a Linux AArch64 compiler target such as `aarch64-linux-gnu`. Record the installed versions, rather than requiring a particular GCC patch release:

```sh
{
    command -v gcc g++ make git
    gcc --version
    g++ --version
    g++ -dumpmachine
    dpkg-query -W build-essential gcc g++ make git file
} | tee -a "$env_record"
```

## Get and build the complete program

4. On the **Pi**, from `~`, clone the public examples repository if this location is unused:

```sh
cd ~
git clone https://github.com/EthanHosier/hardware-from-software.git hardware-from-software
cd ~/hardware-from-software
```

If `~/hardware-from-software` already exists, skip the clone. Inspect that directory and reuse your existing checkout if it contains `examples/linux/hello.cpp`; do not delete it or reset local changes. As an alternative, download the [example archive](downloads/hardware-examples.zip), extract it into a new directory, and use that extraction root as your working directory. The archive contains an `examples` directory directly, without an extra repository wrapper. The remaining commands assume the root is `~/hardware-from-software`.

## Build the common kernel

5. On the **Pi**, from `~/hardware-from-software`, check available storage and cooling before starting the larger build:

```sh
cd ~/hardware-from-software
df -h . /boot/firmware
free -h
vcgencmd get_throttled
python3 scripts/build_pi_kernel.py --jobs 4
```

Run the build as your ordinary user. The script fetches the pinned Raspberry Pi source, starts from the pinned official configuration, enables AF_XDP, gives the result its own release name, and builds the kernel image, in-tree modules, DTBs and overlays. It also compiles our two external modules against the completed kernel. This follows Raspberry Pi's [kernel build workflow](https://www.raspberrypi.com/documentation/computers/linux_kernel.html), with our fixed source/configuration rather than a moving branch.

The source and output remain under `.build/pi-kernel/`. Keep that directory in place: later external-module builds need its configuration, generated headers, host tools and `Module.symvers`, not just the original C headers. A full build supplies symbol-version data that `modules_prepare` alone does not produce. [Linux external-module documentation](https://docs.kernel.org/6.12/kbuild/modules.html).

This is substantially more work than compiling our small examples. No exact build duration or free-space requirement is claimed: inspect actual storage use and build diagnostics. If the Pi runs short of memory or throttles, resolve cooling/power and rerun with `--jobs 1`; do not skip failed targets or install partial output. A successful compile proves the artifacts build, not that this physical Pi has booted them.

## Install the common kernel

6. Before changing boot selection, have the Mac's microSD reader/adapter available and know how to identify the card's FAT boot volume. Save needed personal files separately. On the **Pi**, from the same checkout:

```sh
cd ~/hardware-from-software
sudo python3 scripts/install_pi_kernel.py
```

The installer keeps the original packaged kernel, DTB and overlays, and installs the book's boot artifacts under `/boot/firmware/hfs-kernel/`. It installs the matching modules under `/lib/modules/6.12.96-hfs1-v8` and links that release's `build` directory to the completed native build tree. It backs up the original configuration as `/boot/firmware/config.txt.hfs-original`. Retain that path before rebooting.

Its isolated Pi 4 configuration block explicitly selects `kernel=hfs-kernel/kernel8.img`, `device_tree=hfs-kernel/bcm2711-rpi-4-b.dtb` and `overlay_prefix=hfs-kernel/overlays/`. Thus the matching private image, DTB and overlays are selected together, while the normal `/boot/firmware/cmdline.txt` remains the command-line file used by later UART lessons. The direct microSD/ext4 baseline has its required storage/filesystem support built into the kernel; the installer disables automatic initramfs loading so that a stock initramfs cannot be mixed with it. See the [firmware configuration reference](https://www.raspberrypi.com/documentation/computers/config_txt.html). Do not copy files over the stock image or mix a new kernel with unrelated DTBs. Inspect the resulting configuration:

```sh
sudo cat /boot/firmware/config.txt
sudo reboot
```

Reboot drops SSH. Reconnect from the Mac as in 5.1. In the **new Pi shell**, working directory `~/hardware-from-software`, verify the actual boot and feature:

```sh
cd ~/hardware-from-software
uname -r
readlink -f "/lib/modules/$(uname -r)/build"
make -s -C "/lib/modules/$(uname -r)/build" LOCALVERSION= kernelrelease
test "$(uname -r)" = 6.12.96-hfs1-v8
grep '^CONFIG_XDP_SOCKETS=y$' "/lib/modules/$(uname -r)/build/.config"
test -s "/lib/modules/$(uname -r)/build/Module.symvers"
sudo python3 - <<'PYCODE'
import socket

# Linux's AF_XDP address-family number; Python may not expose its symbolic name.
AF_XDP = 44
with socket.socket(AF_XDP, socket.SOCK_RAW, 0):
    print("AF_XDP socket creation succeeded")
PYCODE
```

AF_XDP socket creation is a feature check, not an attached packet receiver, a driver zero-copy test or evidence of changed networking behaviour. It should not alter routes or interfaces. Verify ordinary SSH remains usable and inspect the actual network interfaces with `ip -brief address`; if you normally use Ethernet too, verify that connection before proceeding. Save a fresh environment record after reboot—the earlier shell's `env_record` variable no longer exists:

```sh
env_record=$(mktemp "$HOME/linux-environment-common-kernel.XXXXXX.txt")
{
    date -Is
    cat /etc/os-release
    uname -a
    cat /proc/version
    readlink -f "/lib/modules/$(uname -r)/build"
    grep '^CONFIG_XDP_SOCKETS=y$' "/lib/modules/$(uname -r)/build/.config"
    ip -brief address
    vcgencmd get_throttled
} | tee "$env_record"
```

Continue only after the release, build tree and feature checks succeed. Keep this kernel selected for the rest of the book. Normal package updates may update the retained stock recovery files; our explicitly selected custom image is separate. This pin is reproducibility, not an automatic security-update mechanism: a deliberate future kernel update needs a reviewed rebuild and recompilation of external modules.

### Recover if the new kernel does not boot

If SSH still works, inspect the kernel log and the installer's recorded configuration before changing anything. To return temporarily to the stock recovery kernel, remove only the installer's book-kernel selection block from `config.txt` and restore any stock `auto_initramfs` lines that the installer commented, preserving unrelated settings, then reboot. This is recovery, not the normal lesson route; restore and verify the common kernel before continuing hardware work.

If SSH is unavailable, shut down through a local console when possible, disconnect the Pi supply and move the microSD to the Mac. If the Pi is hung, power removal is a last resort that may lose pending writes. Identify the actual FAT boot volume in Finder/`diskutil list`; open that volume's `config.txt` in a plain-text editor. The Pi path `/boot/firmware` is not a Mac path. Remove only the block between `# BEGIN hardware-from-software kernel selection` and `# END hardware-from-software kernel selection`, restore any stock `auto_initramfs` lines marked as disabled by the installer, or restore the installer's exact pre-change backup if no intervening configuration changes must be preserved. Keep stock files, root arguments and unrelated overlay settings intact. Eject the card, return it to the unpowered Pi and boot. The retained packaged image and its matching original Device Tree files supply the recovery route. Repair the failed build/install before selecting the common kernel again.

## Build and run the native program

The complete file `examples/linux/hello.cpp` is:

```cpp
{{#include ../examples/linux/hello.cpp}}
```

7. Build and run on the **Pi**, from `~/hardware-from-software`:

```sh
cd ~/hardware-from-software
mkdir -p .build
g++ -std=c++20 -Wall -Wextra -Wpedantic -O2 examples/linux/hello.cpp -o .build/hello
./.build/hello
printf 'Exit status: %s\n' "$?"
file .build/hello
ldd .build/hello
```

Expected application output, shown for illustration rather than as a captured Pi session:

```text
Linux userspace C++ is running
Exit status: 0
```

`-std=c++20` selects the language version; the three warning options enable useful diagnostics; `-O2` enables optimisation; `-o` names the executable. Using `g++` for the link step also selects the C++ runtime libraries.

`file` should describe a 64-bit AArch64 ELF executable. It may also say PIE, meaning a position-independent executable. ELF is a container format also used by our Pico debug binaries; its presence alone does not mean two executables share a target environment. `ldd` shows the shared libraries resolved by the Pi's dynamic loader, including the C++ runtime. Run it only on this program you just built. Library paths and addresses vary.

The SSH connection carries terminal input and output. The compiler and executable both run on the Pi; the Mac merely displays their output. No GPIO changes should occur. This verifies compiler, C++ headers, linking, loader, and a userspace execution path, not access to any hardware peripheral.

## Troubleshooting and next state

| Symptom | Check and correction |
| --- | --- |
| `g++: command not found`, or missing `iostream` | Confirm you are in the Pi SSH shell, then check that `apt install build-essential` completed successfully. An embedded compiler is not a substitute. |
| Compiler target contains `none-eabi`, or `file` reports macOS/another architecture | Inspect `command -v g++` and `g++ -dumpmachine`. Use `/usr/bin/g++` on the Pi after installing its packages, then rebuild. Do not copy a Mac executable over the result. |
| `uname -m` is `armv7l`, or `dpkg` reports `armhf` | You are outside the selected 64-bit route. Preserve any work and return to 5.1 to choose an appropriate card before the later module labs. |
| Source file not found | Run `pwd` and `ls examples/linux/hello.cpp`. Build from the repository or archive root, not from `examples/linux`. |
| Permission denied while compiling or running | Keep the checkout and `.build` under your own home directory and inspect `ls -ld . .build`. Build without `sudo`; do not solve this with `chmod 777`. If a mount forbids execution, use a user-owned directory on the normal root filesystem. |
| Wrong running release, missing `build` link or symbol-version file | Do not install unrelated distribution headers. Check the selected boot block and retain or restore the original source/output paths. The installer refuses conflicting or partial installations; repeating it is not an automatic repair. Inspect its exact error and recover the original installation before changing any boot files. Repeat all release and feature checks before Chapter 8. |
| Build is killed, storage fills or the Pi throttles | Inspect the failure, `df -h`, `free -h` and `vcgencmd get_throttled`; fix power/cooling/storage and retry fewer jobs. Never install a partially failed build. |
| AF_XDP socket creation fails | Read the actual error. Confirm the booted release and matching `.config`; a config file alone does not prove the running image uses it. Stop and resolve this before calling the common environment complete. |
| APT fails to download packages | Restore networking and check free space before retrying. Keep the existing repositories for your OS release; do not add a different Debian release to obtain one missing package. |

Keep the environment record and source checkout for later lessons. The executable exits on its own; there is no process or module to stop. To remove just this generated executable, run `rm .build/hello` on the **Pi** from `~/hardware-from-software`; rebuilding recreates it. Leave development packages installed and the Pi header unwired. Continue to [5.3 — Establish GPIO identity and ownership](5.3-establish-gpio-identity-and-ownership.md), where we inspect the GPIO controller without assuming its device number.
