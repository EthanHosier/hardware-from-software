# 8.2 — Build and load the smallest external module

You will build a C kernel module, insert it into the Pi's running kernel, observe its load message, and remove it to observe its exit message. This isolates the module lifecycle before [8.3](8.3-describe-the-device-and-bind-the-driver.md) adds Device Tree binding and GPIO ownership.

Start with the native tools and checkout from [5.2](5.2-verify-the-linux-development-environment.md), after completing [8.1](8.1-establish-a-userspace-gpio-baseline.md). All commands below run in a **Pi SSH shell**, never a Mac terminal running local commands. The Mac only carries the SSH connection.

The common kernel baseline is **`6.12.96-hfs1-v8`**, installed in 5.2 with AF_XDP enabled. Both modules must be rebuilt for that exact kernel, using its own configuration and symbol-version data. The [verification record](verification.md) distinguishes the current build evidence from earlier builds against distribution headers; compilation does not demonstrate loading into a Pi kernel. Physical Pi module loading and unloading have **not been exercised during authoring**; the observations below are expected results for your machine.

## Keep the hardware baseline idle

Leave the Pi-only circuit from [8.1's schematic](8.1-establish-a-userspace-gpio-baseline.md#1-separate-the-boards-and-build-the-pi-circuit) attached: BCM17, physical 11 → 1 kΩ → LED anode, with cathode → ground physical 9; BCM27, physical 13 → button → ground physical 14, with a 4.7 kΩ pull-up to 3V3 physical 17. Do not change wiring. The Pico remains separate and unplugged, with its local circuit retained. All Pi–Pico UART/I²C wires and debug connections remain absent.

Let `gpio_events` finish or stop your own running instance. On the **Pi, from `~/hardware-from-software`**, inspect:

```sh
cd ~/hardware-from-software
pgrep -af '[g]pio_events'
```

No result is expected. Repeat 8.1's version-appropriate `gpioinfo` inspection; confirm the `hfs-led` and `hfs-button` requests have gone. Verify that no custom button overlay or driver is bound, as left at the end of 8.1. Resolve a remaining owner through its normal cleanup. This lesson's `hello` module requests **no GPIO**, so pressing the button produces no module event and loading it should not change the LED. A released GPIO's electrical state is not guaranteed by the old program's exit.

## Kernel code has a different execution boundary

A Linux C++ application has its own virtual address space and asks the kernel for services through system calls. This module executes as part of the kernel, with kernel privilege and access to kernel memory. A bad pointer here can damage the system rather than just terminate one process. `sudo insmod` authorises insertion; it does not wrap module execution in a protected userspace sandbox.

Use the distribution's native **C compiler and kernel build system**, rather than the C++ runtime used by our Linux applications or the Pico's embedded C++ toolchain. The kernel supplies its own interfaces and build flags. Its internal interfaces have no general stable source or binary ABI promise across kernel releases: rebuild and review an external module when the kernel changes. This differs from the kernel's userspace interface. See [Linux's driver-interface explanation](https://www.kernel.org/doc/html/latest/process/stable-api-nonsense.html).

## 1. Establish the exact kernel/header match

On the **Pi, working directory `~/hardware-from-software`**, save a fresh record:

```sh
cd ~/hardware-from-software
module_record=$(mktemp "$HOME/module-environment.XXXXXX.txt")
{
    date -Is
    cat /etc/os-release
    uname -m
    uname -r
    dpkg --print-architecture
    cat /proc/version
    command -v gcc make
    gcc --version
    gcc -dumpmachine
    make --version
} | tee "$module_record"
```

Expect `aarch64` and Debian architecture `arm64` for this book's 64-bit Pi 4 route. The OS image supplies userspace; the kernel selected in 5.2 is **`6.12.96-hfs1-v8`** for all Linux exercises, including later networking. Neither the OS name nor the kernel's first two version components proves a match. Use the full release string.

On the **Pi, same directory**, install the native module utilities:

```sh
sudo apt update
sudo apt install build-essential file kmod libelf-dev
uname -r
ls -ld "/lib/modules/$(uname -r)/build"
readlink -f "/lib/modules/$(uname -r)/build"
make -s -C "/lib/modules/$(uname -r)/build" LOCALVERSION= kernelrelease
```

`kmod` provides `insmod`, `rmmod`, `lsmod` and `modinfo`. The `build` link must resolve to the matching build tree installed and prepared in 5.2, under the checkout's `.build/pi-kernel/`. That tree contains the exact configuration, generated headers and `Module.symvers` for our custom kernel. A distribution `linux-headers-rpi-v8` package targets its packaged kernel, **not this custom release**. Do not substitute it or redirect a broken link to an unrelated tree.

Compare releases and check the build inputs explicitly, still on the **Pi, same directory**:

```sh
running_release=$(uname -r)
header_release=$(make -s -C "/lib/modules/$running_release/build" LOCALVERSION= kernelrelease)
printf 'Running: %s\nBuild tree: %s\n' "$running_release" "$header_release" | tee -a "$module_record"
test "$running_release" = 6.12.96-hfs1-v8
test "$running_release" = "$header_release"
test -s "/lib/modules/$running_release/build/Module.symvers"
grep '^CONFIG_XDP_SOCKETS=y$' "/lib/modules/$running_release/build/.config"
```

Continue only if every check succeeds. If the build tree was moved, restore it and its matching source to their original paths, then repeat these checks. If it was deleted, stop and inspect [5.2's installation and recovery record](5.2-verify-the-linux-development-environment.md#install-the-common-kernel): the installer refuses conflicting or partial installations and does not automatically repair them. Preserve the original artifacts rather than pointing the link at another tree. If the stock recovery kernel is running, restore the book kernel selection and reboot before continuing. Do not install a distribution kernel/header pair as a repair for the custom baseline. Installing files does not change the kernel already running in memory.

The full kernel build supplies symbol versions; `modules_prepare` alone does not generate `Module.symvers`. The native full build supplies both that symbol data and host build helpers for the Pi. See [Linux kbuild's external-module prerequisites](https://docs.kernel.org/6.12/kbuild/modules.html).

`/proc/version` records the compiler used for the running kernel; compare it with `gcc --version` and the build's compiler diagnostics. A target such as `aarch64-linux-gnu` is appropriate. A compiler-name difference can be cosmetic, but a real version or target mismatch needs investigation using the distribution's matching compiler packages. Never substitute `arm-none-eabi-gcc`, a Mac compiler, or guessed flags to suppress the warning.

## 2. Read the complete module and kbuild file

The complete `examples/kernel/hello.c` is:

```c
{{#include ../examples/kernel/hello.c}}
```

There is no `main`. `module_init` registers `hfs_hello_init` as the insertion entry point. Its zero return means initialisation succeeded; a negative error return would reject insertion. `module_exit` registers the removal cleanup. `__init` marks initialisation-only code that can be discarded after successful initialisation; `__exit` marks exit-only code. These annotations are defined in the [baseline kernel's `init.h`](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/include/linux/init.h), and the callbacks are documented under [driver entry and exit points](https://www.kernel.org/doc/html/latest/driver-api/basics.html#driver-entry-and-exit-points).

`pr_info` writes an informational message to the kernel log through the [`printk` logging infrastructure](https://www.kernel.org/doc/html/latest/core-api/printk-basics.html). It does not write to your SSH terminal's stdout. The prefix `hfs_hello:` identifies our messages, while the module's actual name is **`hello`**, derived from the build target.

`MODULE_DESCRIPTION` adds inspectable metadata. `MODULE_LICENSE("GPL")` declares a GPL-compatible module license to the kernel, including eligibility to use GPL-only exported symbols; it is not a memory-safety certificate or a replacement for the source's licensing terms. See the [kernel licensing rules](https://www.kernel.org/doc/html/latest/process/license-rules.html#module-license).

The complete `examples/kernel/Makefile` is:

```makefile
{{#include ../examples/kernel/Makefile}}
```

Both entries use `obj-m`: build these objects as loadable modules. The shared file therefore builds **both `hello.ko` and `mybutton.ko`**. Only `hello.ko` will be loaded here. Compiling `mybutton.c` does not bind a device, claim a line, or install an overlay.

## 3. Build and inspect the artifact

On the **Pi, working directory `~/hardware-from-software`**:

```sh
cd ~/hardware-from-software
make -C "/lib/modules/$(uname -r)/build" LOCALVERSION= M="$PWD/examples/kernel" W=1 modules
file examples/kernel/hello.ko
modinfo ./examples/kernel/hello.ko
modinfo -F vermagic ./examples/kernel/hello.ko
uname -r
```

Build as your ordinary user. `-C` selects the matching kernel build tree; the absolute `M` path selects our external-module directory. `W=1` requests additional warnings, as in the recorded CI build. This is the [documented kbuild external-module route](https://www.kernel.org/doc/html/latest/kbuild/modules.html).

Keep `LOCALVERSION=` in these commands. The pinned source is a shallow Git checkout; leaving that make variable unset can add a `+` suffix when the kernel regenerates its release string. An explicitly empty value keeps the module release identical to the course image. The build and installer scripts already use the same setting.

A fresh build compiles the C source into an object, runs **MODPOST** to check exported-symbol references and generate module metadata, then links a `.ko`. Incremental builds may omit unchanged stages. Symbol-version information comes from the matching kernel build; an arbitrary unpacked source tree or a different configuration is not equivalent to this completed kernel build.

`file` should identify an AArch64 ELF relocatable object. Our native userspace program was an ELF executable; Pico debug firmware was a different-target ELF, with UF2 used for BOOTSEL copying. This `.ko` is input to the **Linux module loader**, not an executable to run with `./hello.ko` and not firmware to flash.

The first field of `vermagic` must match the complete running release. Its remaining fields describe relevant build properties. This check helps detect stale artifacts; it does not prove the code is safe or replace the loader's architecture, symbol and configuration checks. If any build stage failed, stop rather than inserting a leftover `.ko` from a previous build.

## 4. Load only your newly built module

First check for a name collision on the **Pi, same directory**:

```sh
lsmod | awk '$1 == "hello" { print }'
ls -ld /sys/module/hello
modinfo hello
```

The missing `/sys/module/hello` directory is expected before loading. `modinfo hello` searches installed modules by name and may report that none exists; it does **not** prove whether a module is loaded. Inspect any result. If `hello` is already loaded or present in `/sys/module`, stop and establish what owns it. Do not remove someone else's module to make room for this example. Our insertion below uses an explicit file path so that an installed file of the same name is not selected accidentally.

In a **second Pi SSH shell, working directory `~`**, watch only new kernel messages:

```sh
cd ~
sudo dmesg --follow-new
```

Leave it running. In the **first Pi SSH shell, `~/hardware-from-software`**, insert:

```sh
hello_loaded_by_us=no
if sudo insmod ./examples/kernel/hello.ko; then
    hello_loaded_by_us=yes
fi
lsmod | awk '$1 == "hello" { print }'
```

Continue to removal only after insertion succeeds. Expected new log content, **illustrative rather than a captured Pi transcript**, is:

```text
hfs_hello: loaded
```

Timestamps and other kernel messages vary. `lsmod` should contain a `hello` row; size values vary by build. `modinfo ./examples/kernel/hello.ko` describes the file, whereas `lsmod` describes loaded modules.

The loader resolves kernel-symbol dependencies and calls the init function. `insmod` inserts the specified file; it does not automatically load dependency modules as `modprobe` can. This minimal example needs no separate helper module. It creates no `/dev` node and has no Device Tree match table or GPIO binding.

An external module normally records the **`O` out-of-tree taint**, even with `MODULE_LICENSE("GPL")`. That differs from the proprietary-license `P` taint. An unsigned-module taint may also occur under the running kernel's policy. Taint records diagnostic history and persists after unloading; see [Linux's taint documentation](https://www.kernel.org/doc/html/latest/admin-guide/tainted-kernels.html). An enforced signature policy can reject insertion instead; do not bypass that policy to continue.

## 5. Remove it and leave a clean next state

On the **Pi, in the same first shell and directory**, remove only the module successfully inserted above:

```sh
if [ "$hello_loaded_by_us" = yes ]; then
    sudo rmmod hello && hello_loaded_by_us=no
fi
lsmod | awk '$1 == "hello" { print }'
```

The `hello` row should disappear. The log watcher should show this expected new message:

```text
hfs_hello: unloaded
```

The loader calls the exit function before removing the module's code. Stop the second shell's log watcher with Ctrl-C; that stops `dmesg`, not a module. Keep your environment record. There is no boot installation or autoload configuration to undo: this lesson used neither `modules_install` nor a persistent load setting.

Optional generated-file cleanup, **Pi, `~/hardware-from-software`**, after successful removal:

```sh
make -C "/lib/modules/$(uname -r)/build" LOCALVERSION= M="$PWD/examples/kernel" clean
```

This removes generated kernel-build artifacts for **both modules** in that directory, including `.ko` and intermediate files; source files remain. Run it only when those are your disposable build outputs. Leave the Pi circuit attached, its userspace GPIO requests closed, the Pico unplugged, and no custom button overlay or driver bound. The next lesson gives a module an actual device to manage.

## Troubleshooting

| Symptom | Interpretation and correction |
| --- | --- |
| Missing `build` directory, configuration, or symbol-version data | Repeat 5.2's complete native build and installation and verify its `Module.symvers`. Do not build against an unrelated kernel checkout. |
| Missing compiler, Make or module utilities | Complete the package installation above. If a build helper specifically reports missing ELF development headers, install the official `libelf-dev` package on the Pi and retry. The CI environment installed it explicitly; do not install a whole kernel-source toolchain by guesswork. |
| Compiler mismatch warning or wrong architecture | Compare `/proc/version`, `gcc --version`, compiler path and `gcc -dumpmachine`. Resolve the actual discrepancy and rebuild against the matching build tree. A 32-bit OS/kernel is outside this page's route. |
| `Invalid module format` | Read the new kernel log for the precise mismatch. Compare full `uname -r`, header `kernelrelease`, `file` and `vermagic`; remove stale generated artifacts and rebuild after correcting the environment. Never force-load. |
| Unknown symbol or symbol-version disagreement | Confirm the matching prepared build tree and successful MODPOST stage. A `.ko` copied from another kernel is not interchangeable. Check named dependencies before considering any load. |
| `File exists` or `hello` already present | Stop; inspect `lsmod` and `/sys/module/hello`. Do not assume an earlier module belongs to this run and do not unload an unknown module. |
| `dmesg: read kernel buffer failed` | Use the Pi's authorised `sudo dmesg` command. Do not weaken the system-wide log-access setting. |
| Insertion refused for signatures or permissions | Read the kernel log and use the distribution's supported module policy. Do not disable checks or force insertion. |
| `rmmod: Module hello is in use` | Inspect its `lsmod` use count and dependent-module names. This example acquires no persistent device users; an unexpected reference needs explanation. Do not force removal or unload unrelated modules. |
