# 9.2 — Observe demand paging and protection faults

A page fault can be part of a successful memory access. In this lesson, you will compare minor-fault counts while writing to newly mapped memory, then observe a deliberately forbidden write terminate a child process. The parent checks that termination and exits successfully. Neither experiment requires kernel code or GPIO access.

## A mapping and its backing memory

`mmap` establishes a virtual address range with permissions. Our `MAP_PRIVATE | MAP_ANONYMOUS` mapping supplies initially zeroed memory without a backing file. Successful creation does not promise that a separate physical page has already been allocated for every page of the range. See the [mmap manual](https://man7.org/linux/man-pages/man2/mmap.2.html).

With **demand paging**, Linux can defer backing work until an access needs it. A processor translation fault transfers control to the kernel. If the access is permitted, Linux can supply the backing and translation, then resume the instruction. Anonymous reads may use a shared zero-filled page; a write needs backing that can hold this process's data. That is why this experiment writes, rather than merely reads, one byte per page. The kernel's [memory-management concepts](https://docs.kernel.org/admin-guide/mm/concepts.html#anonymous-memory) explain this distinction.

A **minor fault** is serviced without I/O. A **major fault** requires I/O to service it. `ru_minflt` counts minor faults; it is not a count of physical pages owned by the process. The program queries it with `getrusage(RUSAGE_SELF, ...)`, which reports the calling process, including its threads. See [getrusage](https://man7.org/linux/man-pages/man2/getrusage.2.html).

The initial `/proc/self/maps` listing is printed **before** `mmap`; it cannot contain the new mapping. The subsequent address line identifies that allocation. `sysconf(_SC_PAGESIZE)` supplies the runtime page size, and `bytes` is 128 times that value. The loop visits offsets zero, one page, two pages, and so on, writing exactly one byte in each of 128 runtime-sized pages. It does not assume 4096-byte pages. See the runtime page-size query in [sysconf](https://man7.org/linux/man-pages/man3/sysconf.3.html).

The pointer's `volatile unsigned char` type keeps those accesses observable to the compiler. It provides neither thread synchronization nor access permission; GCC documents why volatile is [not a memory barrier](https://gcc.gnu.org/onlinedocs/gcc/Volatiles.html). A C++ volatile access still goes through the processor's memory translation and permission checks.

The two `getrusage` calls bracket the touch loop. Earlier work, including printing maps and making the mapping, precedes the baseline. Work after the second sample is excluded. Any other minor faults occurring within that interval also count: subtraction narrows the observation but does not isolate an individual allocation. Both samples precede `fork`, so the later child experiment cannot contribute to the reported delta.

## 2. Save three bounded runs

Read the two files saved in 9.1 first. Then make three additional runs on the **Pi**, in the same directory. Each process maps only 128 runtime-sized pages, creates one child, and finishes; keep that bound rather than increasing allocation until memory runs out.

```sh
for run in 1 2 3; do
    (ulimit -c 0; ./.build/memory_lab) \
      > ".build/paging-run-$run.txt" 2> ".build/paging-run-$run.err"
    result=$?
    printf '%s\n' "$result" > ".build/paging-run-$run.status"
    printf 'Run %s: parent status %s\n' "$run" "$result"
    tail -n 2 ".build/paging-run-$run.txt"
    cat ".build/paging-run-$run.err"
    if [ "$result" -ne 0 ]; then break; fi
done
```

Expected: parent status `0`, an address/page-size/minor-fault line, and `child protection fault: expected SIGSEGV`. These are expected observations, not a recorded Pi transcript. Keep each actual delta beside its page size and status. Do not require a delta of exactly 128.

The subshell limits ordinary core files without changing your interactive shell's limit. The child also attempts `setrlimit(RLIMIT_CORE, {0, 0})`; the source does not check that call's return. Neither step guarantees that no crash data is collected: Linux can ignore `RLIMIT_CORE` when `core_pattern` pipes dumps to a collector. Leave system-wide crash policy unchanged. See [core dumps](https://man7.org/linux/man-pages/man5/core.5.html).

## 3. Interpret both kinds of fault

A positive delta is consistent with Linux doing demand-paging work as the loop writes. It does not prove one newly allocated physical page per counted event. Page size, huge-page policy, kernel accounting and incidental faults can change the relationship. Earlier faults are subtracted by the baseline; backing established before that baseline would not be counted again merely because the loop visits it. Three runs show repeatability or variation, not a physical-page inventory. Linux documents [huge-page mappings](https://docs.kernel.org/admin-guide/mm/concepts.html#huge-pages), which can cover more memory per translation.

Next, `fork` creates a separate child address space. Linux uses copy-on-write rather than immediately copying all private data. The parent has already touched the region before this happens. The child's permission change affects its own mapping, leaving the parent's permissions intact. See [fork](https://man7.org/linux/man-pages/man2/fork.2.html).

In the child, `mprotect(region, bytes, PROT_NONE)` denies access to the mapped range. The `mmap` result is page-aligned and the length is a whole number of pages, satisfying the alignment requirements. The following `data[0] = 2` violates that permission. Linux delivers `SIGSEGV`; the default action terminates the child. This is an invalid access even though the address was previously writable and already had backing. The [mprotect manual](https://man7.org/linux/man-pages/man2/mprotect.2.html) defines this behaviour.

The parent waits for that specific child, retrying `waitpid` after `EINTR`. It checks `WIFSIGNALED(status)` before using `WTERMSIG(status)`, and accepts only `SIGSEGV`. A failed `mprotect` makes the child call `_exit(2)`; reaching past an unexpectedly successful write calls `_exit(3)`. Both yield `unexpected result`, not success. The program prints only that summary, not the child's detailed status. These status macros and child reaping are defined by [waitpid](https://man7.org/linux/man-pages/man2/waitpid.2.html).

The successful touch fault is serviced so the instruction can continue. The forbidden write cannot be made valid under the child's permissions, so its process terminates. This does not crash the Pi kernel. Keep intentional invalid accesses in this child userspace experiment; there is no equivalent fault exercise to perform inside the GPIO module.

## Troubleshooting and next state

| Symptom | Interpretation and action |
| --- | --- |
| Missing `/proc`, Linux headers, source or executable | Verify the Pi SSH shell, checkout directory and 5.2 development environment; rebuild the complete source. |
| Delta differs between runs or from 128 | Keep the measurements and runtime page size. Recheck the sampling interval and accounting limits above; do not change system memory policy to force a number. |
| Status is nonzero or output stops early | Inspect the saved standard error and user memory/process limits. Some failure branches return without a diagnostic; absence of an error message does not establish success. Do not rerun with `sudo`. |
| `unexpected result` | Confirm the canonical source and rebuild. Child exit 2 or 3, or a different terminating signal, fails the expected-signal check. |
| The parent itself reports a segmentation fault or hangs | Stop repeating, save output and status, and verify source/binary identity. An expected child termination must leave the parent able to print its summary and return 0. |
| A crash collector records the child | Core-limit behaviour depends on system policy; this does not by itself mean the parent or kernel crashed. |

On its expected path the parent reaps the child, calls `munmap`, and exits. Process exit also releases its remaining mappings; there is no persistent allocation to clean up manually. Keep the executable and your saved results. Driver binding, circuit and unplugged Pico state remain unchanged.
