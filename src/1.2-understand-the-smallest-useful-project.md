# 1.2 — Understand the smallest useful project

A useful first firmware image identifies itself repeatedly. Repetition matters: the Pico can start before you open its USB serial connection, so a message printed only once is easily missed. This lesson builds that image on the Mac. [The next lesson](1.3-flash-with-bootsel-and-read-output.md) transfers it to the Pico and reads its output.

Finish [the toolchain setup](1.1-install-a-reproducible-macos-toolchain.md) first. Keep the non-wireless Pico 2 unpowered in the state established in [0.6](0.6-assemble-the-bench-and-understand-the-electrical-rules.md): GP16 (physical pin 21) → 1 kΩ resistor → LED anode, with the cathode connected to GND (physical pin 23). Leave the Pi and Debug Probe disconnected. No wiring changes or connected board are needed for compilation. This program does not configure the external LED.

## The application

1. Open `examples/pico/heartbeat.cpp` in your checkout. This is the complete file:

```cpp
{{#include ../examples/pico/heartbeat.cpp}}
```

`stdio_init_all()` initialises the standard input/output backends enabled by the build. Here that means USB serial. `std::printf` therefore sends text through the Pico's USB device controller and USB cable; it does not write to the Mac Terminal that invoked the compiler. The SDK's USB stdio backend implements CDC, a standard USB serial-device interface. It uses TinyUSB and background interrupt work, so the application is small partly because it delegates substantial work to a library. [SDK USB stdio documentation](https://www.raspberrypi.com/documentation/pico-sdk/runtime.html#pico_stdio_usb).

`heartbeat_count++` prints the previous count and increments it. `sleep_ms(1000)` requests a one-second delay between iterations; printing and USB handling also take time. This is an identity and liveness check, not a precise timing instrument. The counter is working state, lost when the firmware restarts.

Initialisation does not mean a terminal has connected. With this SDK's default USB connection-wait setting, initialisation does not wait for a reader, and early text may be discarded. Repeated messages let a later reader see the identity and a later count. [SDK 2.3.1 USB configuration](https://github.com/raspberrypi/pico-sdk/blob/2.3.1/src/rp2_common/pico_stdio_usb/include/pico/stdio_usb.h).

## The project description

2. Read `examples/pico/CMakeLists.txt` alongside the source:

```cmake
{{#include ../examples/pico/CMakeLists.txt}}
```

This is the book's complete shared project, containing the heartbeat and later examples. Its `foreach` creates a separate executable for each name; the files do not become one combined program. For this lesson, follow the iteration where `name` is `heartbeat`.

The SDK import occurs **before** `project(...)`, because the SDK must select the embedded toolchain before CMake enables C, C++, and assembly. `PICO_SDK_PATH` identifies the installed SDK; the explicit existence check catches a missing path early. `pico_sdk_init()` makes SDK libraries and build helpers available. This is build-time configuration, distinct from runtime initialisation on the Pico. [SDK project setup](https://github.com/raspberrypi/pico-sdk/blob/2.3.1/README.md#quick-start-your-own-project).

`add_executable` associates a target with its source. `target_link_libraries` supplies SDK code and its build requirements. The common list includes peripheral libraries needed by later lessons; heartbeat mainly needs `pico_stdlib` and USB stdio. Unused library code can be discarded during linking. `-Wall -Wextra -Werror` makes selected compiler warnings fail the build.

`pico_enable_stdio_usb(... 1)` enables USB output, while `pico_enable_stdio_uart(... 0)` disables the SDK's default UART stdio backend. USB diagnostics therefore do not occupy GP0/GP1. `pico_add_extra_outputs` requests additional image formats, including UF2, alongside the ELF. These are SDK CMake helpers, not C++ statements executed on the board.

## Build on the Mac

3. In **Mac Terminal**, start in the project root, `~/hardware-from-software`, established in 1.1. If you placed the example tree or an authorised checkout elsewhere, substitute its location for the first command:

```sh
cd ~/hardware-from-software
python3 scripts/setup_deps.py
python3 scripts/build_examples.py --pico
```

The setup step reuses installed dependencies and checks the pinned SDK commit. The build script selects checkout-local CMake, Ninja and Arm GNU tools, sets `PICO_SDK_PATH`, and configures these choices:

| Setting | Meaning |
| --- | --- |
| `PICO_BOARD=pico2` | Non-wireless Pico 2 board configuration |
| `PICO_PLATFORM=rp2350-arm-s` | RP2350 Arm secure platform, using Cortex-M33 rather than Hazard3 RISC-V |
| `CMAKE_BUILD_TYPE=Debug` | Debug build with information for source-level debugging |
| Source `examples/pico`, build `.build/pico` | Keep generated files out of the source directory |

The project does not launch the second application core. It runs the application on the initial Arm core, with no RTOS. Board selection and processor-platform selection are separate SDK configuration choices; the SDK supplies a [Pico 2 board definition](https://github.com/raspberrypi/pico-sdk/blob/2.3.1/src/boards/include/boards/pico2.h) and an [Arm platform definition](https://github.com/raspberrypi/pico-sdk/blob/2.3.1/cmake/preload/platforms/rp2350-arm-s.cmake).

CMake configures a build graph; Ninja executes it. The compiler runs as a macOS program but emits Arm object files. The linker combines those objects with selected SDK and runtime code, resolves symbol references, and assigns addresses using the SDK linker script. No Linux process loader is involved on the Pico.

4. Check the two files in **Mac Terminal**, still in the checkout root:

```sh
ls -l .build/pico/heartbeat.elf .build/pico/heartbeat.uf2
.deps/arm-gnu-toolchain-14.2.rel1-darwin-arm64-arm-none-eabi/bin/arm-none-eabi-readelf -h .build/pico/heartbeat.elf
```

Both files should exist and be nonempty. The ELF header should identify `ELF32` and machine `ARM`. File sizes, timestamps and addresses may change; do not compare them with a fixed transcript. The book's recorded build compiled all twelve Pico targets and produced these files. Physical execution has not been exercised.

## What the files contain

The **ELF** contains executable code, data, addresses, symbols, and debug information. Keep it for GDB: source lines and variable names come from this information. It is not a Mac executable, even though the tools that created it run on the Mac.

The **UF2** packages the firmware into address-labelled blocks accepted by the Pico's BOOTSEL USB loader. It is the file we will copy to the mounted boot volume. It does not replace the ELF's source-level debugging information. Both files describe the same build in forms suited to different tools. [Official first-binary instructions](https://www.raspberrypi.com/documentation/microcontrollers/c_sdk.html#your-first-binaries).

For this default flash-linked project, code and read-only data normally reside in external flash and are accessed through the RP2350's execute-in-place mapping. Mutable data, stack and heap use SRAM. Flash retains the installed image without power; SRAM supplies working storage while powered. Some SDK routines are placed in SRAM, so “firmware in flash” does not mean every instruction executes there. The [RP2350 linker script and its section definitions](https://github.com/raspberrypi/pico-sdk/blob/2.3.1/src/rp2350/pico_platform/memmap_default.ld) define these placements.

`main()` is not the first instruction after reset. The chip's boot machinery reaches the image's startup code. SDK startup establishes the C/C++ environment, including copying initial data into SRAM and clearing zero-initialised storage, then runs runtime initialisation before calling `main()`. The SDK also supplies stack/vector support and the linker layout. [SDK 2.3.1 startup source](https://github.com/raspberrypi/pico-sdk/blob/2.3.1/src/rp2_common/pico_crt0/crt0.S). Its default runtime configures clocks and timer ticks, including the USB clock needed by this application. [Clock initialisation source](https://github.com/raspberrypi/pico-sdk/blob/2.3.1/src/rp2_common/pico_runtime_init/runtime_init_clocks.c). Later register-level GPIO work keeps this startup support.

## If the build fails

- **`Set PICO_SDK_PATH` or missing SDK headers:** run the setup script from the checkout, then use the build script. Do not mix this build with an editor extension's managed SDK path.
- **Missing TinyUSB or USB stdio support:** rerun setup; it initialises the pinned SDK's TinyUSB submodule. A successful build without the intended USB backend would not establish the required serial behaviour.
- **CMake reports an incompatible generator, compiler, board or platform:** an old cache may describe another configuration. From the **Mac checkout root**, rename the generated directory with `mv .build/pico .build/pico-before-reset` (choose another unused backup name if necessary), then rerun `python3 scripts/build_examples.py --pico`. This performs a fresh configure and build while retaining the old output.
- **No message appears in this Terminal:** building never starts the firmware. USB connection and observation follow in the next lesson.

Keep the source and generated files. Leave the Pico unpowered and the LED circuit assembled. Next, use `heartbeat.uf2` in [1.3 — Flash with BOOTSEL and read output](1.3-flash-with-bootsel-and-read-output.md).
