# 5.3 — Establish GPIO identity and ownership

You will identify the Pi's header GPIO controller and save the names, offsets, ownership and permissions needed for later labs. Start with the working Pi SSH shell and native environment from [5.2](5.2-verify-the-linux-development-environment.md). This lesson inspects metadata; it does not request lines, read electrical levels or toggle outputs. There is no program to compile or run.

Leave the Pi powered by its USB-C supply and networked. Its **40-pin header stays completely unwired**: no HAT, LED, button, Pico or jumper wires. Keep the Pico's earlier circuit separate and unplugged. The selected fresh-image baseline remains Raspberry Pi OS **Legacy Lite, 64-bit, Debian 12 Bookworm**. Record your actual OS and running kernel, including after updates; neither the image label nor this book establishes what is running on your Pi. Physical Pi inspection has not been exercised during authoring.

## Four numbers that mean different things

A physical pin number identifies a metal contact on the board. A **BCM GPIO number** identifies a signal of the BCM2711 SoC. The character-device interface identifies a line using a **chip device and a local offset**. Finally, older Linux examples use a **global GPIO number**, historically formed from a controller's assigned base plus its offset. Do not substitute any of these numbers for another.

For example, the later Pi LED uses **BCM17 at physical pin 11**. On the expected Pi 4 header controller, its line offset is 17, but you will verify that mapping. The device's suffix in `/dev/gpiochipX` is a controller identifier, not a GPIO number or physical pin. Other controllers can also have a line at offset 17. Linux documents the [chip/offset interface](https://www.kernel.org/doc/html/latest/userspace-api/gpio/chardev.html); the [obsolete sysfs interface](https://www.kernel.org/doc/html/latest/userspace-api/gpio/sysfs.html) explains the older global numbering. We do not export sysfs GPIOs.

The diagram’s `SDA1` and `SCL1` labels name the familiar I²C1 alternate functions of BCM2/3, not the controller selected for our later experiment. [6.1](6.1-i-c-on-the-wires.md) selects the active I²C controller and pin function on these same physical contacts and handles conflicting routing. Do not enable I²C1 simply from these labels.

Power and ground contacts are not requestable GPIO lines. Pi GPIO signalling uses 3.3 V and is not 5 V tolerant. BCM2 and BCM3 have fixed board pull-ups to 3.3 V; we reserve these lines for I²C rather than choosing them as arbitrary test outputs. The [official header documentation](https://www.raspberrypi.com/documentation/computers/raspberry-pi.html#40-pin-gpio-header) describes these distinctions.

## Inspect the actual devices

1. **Pi SSH shell — working directory `~`:** create a fresh record independent of the shell variable from 5.2. Keep this shell open for the remaining steps.

```sh
cd ~
gpio_record=$(mktemp "$HOME/gpio-identity.XXXXXX.txt")
{
    date -Is
    tr -d '\000' < /proc/device-tree/model
    printf '\n'
    cat /etc/os-release
    uname -r
    uname -m
} | tee "$gpio_record"
printf 'GPIO record: %s\n' "$gpio_record"
```

2. **Pi — still `~`:** install the inspection tools. The `acl` package supplies `getfacl`, which shows access control lists in addition to ordinary mode bits.

```sh
sudo apt update
sudo apt install gpiod acl
{
    command -v gpiodetect gpioinfo
    gpiodetect --version
    gpioinfo --version
    dpkg-query -W gpiod acl
    ls -l /dev/gpiochip*
    id
} | tee -a "$gpio_record"
```

Review APT's changes. Bookworm's [Debian gpiod package](https://packages.debian.org/bookworm/gpiod) is in the 1.6 series; Pi repositories or a different release can supply another version. **Check the tool's reported version before copying CLI syntax.** A library package named `libgpiod2` is not proof that these are version-2 commands.

3. **Pi — `~`:** enumerate chips, then inspect all their lines. These commands work with both CLI majors:

```sh
gpiodetect | tee -a "$gpio_record"
gpioinfo | tee -a "$gpio_record"
```

If opening the devices is denied, repeat these two metadata commands with `sudo` before the tool name. Do not treat permission failure as missing hardware. `gpiodetect` reports each chip's kernel name, label and line count. An expected Pi 4 header-controller label is `pinctrl-bcm2711`; an expander such as `raspberrypi-exp-gpio` serves different board signals. Identify the header controller from its label **and** its line-name pattern. Do not assume it is the first entry or `/dev/gpiochip0`. The [libgpiod tool overview](https://libgpiod.readthedocs.io/en/v2.3.1/gpio_tools.html) includes an illustrative Pi 4 inventory, not a measurement of your machine.

Look for lines named `GPIO17` and `GPIO27` on that controller, with offsets 17 and 27, and the neighbouring header GPIO names. Labels and names come from the kernel/board description; they are not discovered by probing physical contacts. If they are absent or contradictory, resolve the identity before proceeding.

4. **Pi — `~`:** enter the full device path you actually identified at the prompt, then check it exists:

```sh
printf 'Verified header chip path: '
read -r gpio_chip
test -c "$gpio_chip" && printf 'Character device exists: %s\n' "$gpio_chip"
printf 'Header chip path: %s\n' "$gpio_chip" | tee -a "$gpio_record"
```

If the existence check prints nothing, correct the path before continuing. Existence alone does not establish that it is the right controller. Inspect this chip again using **one** branch, according to `gpioinfo --version`.

**Pi — `~`, libgpiod CLI 1.x:** the chip is a positional argument; the command prints all its lines.

```sh
gpioinfo "$gpio_chip" | tee -a "$gpio_record"
```

**Pi — `~`, libgpiod CLI 2.x:** select the chip with `--chip`; offsets may then select individual lines. Start with the complete inventory:

```sh
gpioinfo --chip "$gpio_chip" | tee -a "$gpio_record"
```

Again, use `sudo` before `gpioinfo` if required. The [upstream 1.x implementation's help](https://kernel.googlesource.com/pub/scm/libs/libgpiod/libgpiod/+/d0a9ddcb9cfe199cffcb6946dcc8b6e358b128ff/tools/gpioinfo.c) and [2.x manual](https://libgpiod.readthedocs.io/en/v2.3.1/gpioinfo.html) specify these different forms. Passing the chip positionally to 2.x can instead be interpreted as a line name. This CLI distinction is independent of the later C++ program's GPIO v2 ioctls; upgrading libgpiod is not a prerequisite for that program.

## Interpret availability and ownership

A line has a name and, when claimed, may have a **consumer label** describing its user. In 1.x, a typical unused line is printed with `unused`; a requested line has `[used]` and often a consumer string. Version 2 formats these fields differently, often using `consumer="..."`. The important evidence is the used state, offset and identity, not whitespace or quote style. An empty consumer string alone does not prove availability: consumers need not supply a label.

A GPIO request gives a process or kernel driver ownership of the selected line. The later `examples/linux/gpio_events.cpp` requests an output and an edge-event input, labelled `hfs-led` and `hfs-button`, and checks each request for failure. Do **not** run it against the unwired header now. [8.1](8.1-establish-a-userspace-gpio-baseline.md) supplies that circuit and execution procedure. `gpioinfo` asks for line information without requesting the line for input/output; even `gpioget`, despite its name, requests lines and is outside this inspection.

There is another layer: **pin multiplexing** connects a physical pad to GPIO or an alternate peripheral such as I²C or UART. Linux's [pin-control subsystem](https://www.kernel.org/doc/html/latest/driver-api/pin-control.html) manages that routing. Peripheral ownership is not always represented as a GPIO consumer, so `unused` in `gpioinfo` is not permission to overwrite an I²C or UART pin.

5. **Pi — `~`:** inspect configuration and services without changing them:

```sh
cat /boot/firmware/config.txt
cat /proc/cmdline
ls -l /dev/serial0
systemctl --no-pager --all list-units 'serial-getty@*' 'hciuart.service'
```

A missing `/dev/serial0` can simply mean no primary serial alias is currently provided. Look for I²C/UART settings and overlays, and `console=serial0,...`, `console=ttyAMA...` or `console=ttyS...` kernel arguments. Included configuration files and conditional sections also matter; this is evidence to retain, not a complete live mux report.

If kernel pinctrl debug information is already exposed, this read-only command shows per-pin mux ownership:

```sh
sudo sh -c 'for f in /sys/kernel/debug/pinctrl/*/pinmux-pins; do
    [ -f "$f" ] || continue
    printf "\n%s\n" "$f"
    cat "$f"
done'
```

Match the controller and its pin names; pinctrl's numbering is its own namespace. No output means this diagnostic is unavailable, not that every pin is free. Do not mount or reconfigure anything to force it here. An unexplained owner on BCM17 or BCM27 remains unresolved until you identify the relevant driver/overlay.

Reserve BCM14/15 for the later UART route. Pi 4's default UART assignment also involves Bluetooth, and a serial login service can use the port. [Raspberry Pi's UART documentation](https://www.raspberrypi.com/documentation/computers/configuration.html#configuring-uarts) explains these relationships. Chapter 7 performs deliberate routing and console changes; leave Bluetooth, `hciuart`, boot configuration and services unchanged now.

## Check access and save the mapping

6. **Pi — `~`:** inspect the selected node's permissions and your effective groups:

```sh
ls -l "$gpio_chip"
getfacl "$gpio_chip"
id
getent group gpio
```

`getfacl` shows any ACL entries and effective restrictions. A common policy gives the `gpio` group access, but inspect your node rather than assuming that policy. Membership must appear in the current shell's `id` output to apply there. A group change would require a new login; this lesson does not need one because privileged metadata inspection is sufficient. Do not use `chmod 666`, direct `/dev/mem` access or sysfs exports to bypass policy or ownership. Device permissions govern opening the interface; they do not override another user's line request or a peripheral driver's claim.

Append your verified header-controller label, device path, line names, offsets and ownership results to the record using your preferred editor. Record BCM17/physical11 and BCM27/physical13 separately. The expected offsets are 17 and 27 **only after the inventory confirms that mapping**. Also note BCM2/3 reserved for I²C and BCM14/15 reserved for UART. Keep unknown identity, mux or ownership marked unresolved rather than filling it with expected values.

Your result is a dated inventory showing whether the intended later GPIO lines appear unclaimed and have no identified conflicting mux owner. It does not reserve them or prove an electrical circuit works. Repeat discovery and ownership checks immediately before Chapter 8's requests, particularly after kernel, overlay or service changes.

## Troubleshooting and next state

| Symptom | Check and correction |
| --- | --- |
| No `/dev/gpiochip*` nodes | Confirm the Pi model and actual kernel, and that you are in its SSH shell rather than a Mac terminal or container. Check `sudo journalctl -k -b` for GPIO/pinctrl driver failures. Installing CLI tools does not create a missing kernel controller. Do not manufacture nodes with `mknod`. |
| Tool reports permission denied | Compare `ls -l`, ACLs and `id`; retry only the metadata command with `sudo`. Keep permission policy separate from line ownership. |
| `--chip` rejected, or chip name treated as a missing line | Recheck `gpioinfo --version` and `gpioinfo --help`; use the matching 1.x/2.x branch. |
| Names are empty, label missing, or expected lines absent | Do not choose by chip index or numerical coincidence. Confirm Pi 4, the installed board description and controller driver; compare with the official header map and matching kernel/Device Tree sources. Defer requests until the mapping is established. |
| Intended GPIO is used or a later request says `Device or resource busy` | Read the consumer and mux evidence. Identify the owning process, service or overlay before planning a reversible change. `sudo` does not make a busy line available; do not stop arbitrary services. |
| Line says unused but boot configuration assigns a bus | Treat the bus routing as a conflict until resolved. A GPIO consumer list is not a complete peripheral-ownership list. |

There is no GPIO process or line request to release. Keep the packages and private inventory; public reports should omit local account and host details. Leave the Pi header unwired and the Pico unplugged. Continue to [6.1 — I²C on the wires](6.1-i-c-on-the-wires.md), which introduces the electrical bus before making the first Pi–Pico connections. Power down both boards and remove their supplies before that wiring change; do not join their separately supplied power rails.
