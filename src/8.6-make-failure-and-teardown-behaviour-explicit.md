# 8.6 — Make failure and teardown behaviour explicit

A driver is unfinished if its successful path works but removing the device leaves a process asleep or using freed memory. You will test independent readers, interruption and device detach, then repeat module removal and insertion. The result is a defined end to each device lifetime, including for applications that still hold a descriptor.

Start after [8.5](8.5-expose-dev-mybutton-to-a-c-client.md), with its permissions rule installed, clients stopped, and the lesson driver bound as verified in [8.3](8.3-describe-the-device-and-bind-the-driver.md#5-verify-the-device-then-load-and-verify-binding). Keep the Pi-only circuit: BCM17, physical 11 → 1 kΩ → LED anode; cathode → ground physical 9. BCM27, physical 13 → button → ground physical 14, with a 4.7 kΩ pull-up to Pi 3V3 physical 17. Use the switch contact groups in [8.1's schematic](8.1-establish-a-userspace-gpio-baseline.md#1-separate-the-boards-and-build-the-pi-circuit). The Pico stays unplugged with its local circuit retained; all inter-board bus and debug wires remain absent. Power down before changing wiring.

Hosted Arm64 CI compiled the C++ client as a native Linux application and compiled the kernel module against official **6.12.96+rpt-rpi-v8** kernel headers. The module was not loaded, and neither artifact was exercised on a Pi during authoring. Every observation below is an expected bench result, not a measured result or proof of race freedom. All commands run on the **Pi through SSH**, in **`~/hardware-from-software`**, unless a second shell is explicitly named.

## 1. Establish exactly which device will be detached

The module name is `mybutton`, the platform driver name is `hfs-mybutton`, and the Device Tree compatible is `hfs,mybutton`. Rediscover the platform device from its `of_node` identity rather than guessing its generated name:

```sh
cd ~/hardware-from-software
button_device=
button_matches=0
for candidate in /sys/bus/platform/devices/*; do
    if [ "$(readlink -f "$candidate/of_node")" = \
         /sys/firmware/devicetree/base/hfs_button ]; then
        button_device=$candidate
        button_matches=$((button_matches + 1))
    fi
done
printf 'Matches: %s; device: %s\n' "$button_matches" "$button_device"
```

Continue only with exactly one match. Check the live compatible and the built module's release. If the module is absent after a reboot, this guarded block loads only the explicitly built artifact; an existing module is retained:

```sh
(
    set -eu
    test "$button_matches" -eq 1
    test "$(tr '\0' '\n' < "$button_device/of_node/compatible")" = hfs,mybutton
    test "$(make -s -C "/lib/modules/$(uname -r)/build" kernelrelease)" = "$(uname -r)"
    test "$(modinfo -F vermagic ./examples/kernel/mybutton.ko | cut -d ' ' -f 1)" = "$(uname -r)"
    if [ ! -d /sys/module/mybutton ]; then
        test ! -e "$button_device/driver"
        sudo insmod ./examples/kernel/mybutton.ko
    fi
    test "$(readlink -f "$button_device/driver")" = /sys/bus/platform/drivers/hfs-mybutton
    test "$(readlink -f "$button_device/driver/module")" = /sys/module/mybutton
    ls -l /dev/mybutton
)
```

Stop on any failure. A missing or stale `.ko` needs 8.3's matching-header build, not force-loading. An unexplained existing module or different binding needs investigation. Retaining the known module from 8.5 is the intended initial state. Do not run the userspace GPIO requester against its owned lines.

## 2. Give independent readers the same press

Every separate `open` has its own `seen` counter. Reading one does not consume another's notification. Descriptors made with `dup`, or inherited from a shared open, instead share `seen` and the reader mutex. Use one caller per open throughout these tests. `O_NONBLOCK` avoids the event wait; it does not bypass `mutex_lock_interruptible`, which can still wait behind another read sharing that open.

Release the button and wait half a second. Run this complete helper. It opens the device twice, waits at most 30 seconds for each reader, then checks the held state for three seconds:

```sh
python3 - <<'PY'
import os
import re
import select
import time

fds = []
def ready(fd, timeout_ms):
    p = select.poll()
    p.register(fd, select.POLLIN)
    events = p.poll(timeout_ms)
    if not events:
        raise TimeoutError("no accepted press")
    mask = events[0][1]
    if mask & (select.POLLERR | select.POLLHUP | select.POLLNVAL):
        raise RuntimeError("device offline or poll error")
    assert mask & select.POLLIN

def record(fd):
    data = os.read(fd, 64)
    assert re.fullmatch(rb"[0-9]+ [01]\n", data), data
    return data

try:
    for _ in range(2):
        fds.append(os.open("/dev/mybutton", os.O_RDONLY | os.O_NONBLOCK | os.O_CLOEXEC))
    print("Both opens ready: press once and HOLD until the helper ends", flush=True)
    ready(fds[0], 30000)
    first = record(fds[0])
    ready(fds[1], 30000)
    second = record(fds[1])
    print("Independent records:", repr(first), repr(second), flush=True)
    assert first == second, "extra accepted press between snapshots; release and rerun slowly"
    p = select.poll()
    for fd in fds:
        p.register(fd, select.POLLIN)
    deadline = time.monotonic() + 3
    while time.monotonic() < deadline:
        remaining = max(1, int((deadline - time.monotonic()) * 1000))
        assert not p.poll(remaining), "another notification while held: investigate bounce or wiring"
    print("No further notification during the held interval; release now")
finally:
    for fd in fds:
        os.close(fd)
PY
```

Expected: both records contain the same sequence and light value, and holding produces no further accepted press. A stable held level is not a stream of new edges. Release and allow half a second before repeating.

For a bounce experiment, rerun while making one ordinary press, then compare slow press/release cycles with quick taps using 8.5's C++ client under an overall limit:

```sh
timeout --signal=TERM --kill-after=2s 20s ./.build/button_client /dev/mybutton 10
```

The client was built in 8.5; rebuild there if missing. Stop after a few taps and let the deadline close it. Status 124 indicates the outer timeout expired. Quick taps may be missed, and bounce may add accepted transitions. `mod_delayed_work` arranges a single later sample, nominally after 20 ms of scheduled delay; it does not establish continuous physical stability. Do not manufacture bounce by shorting unrelated contacts or changing live wiring. Neither matching records nor a quiet held interval validates every possible bounce waveform.

A slow reader may jump from sequence 4 to 7: three presses were accepted since its last record. Intermediate states are not queued. Reader scheduling can also make two readers capture different latest snapshots if more presses arrive between their reads. Counter equality is expected in this controlled single-press test, not a general concurrency guarantee.

## 3. Interrupt a blocking read

Make no presses during this test. Release and wait half a second, then run:

```sh
python3 - <<'PY'
import errno
import os
import signal

class Interrupted(Exception):
    pass

def interrupt(signum, frame):
    raise Interrupted("SIGALRM interrupted the idle read")

signal.signal(signal.SIGALRM, interrupt)
fd = os.open("/dev/mybutton", os.O_RDONLY | os.O_CLOEXEC)
try:
    signal.alarm(3)
    print("Blocking read armed; leave the button released", flush=True)
    try:
        os.read(fd, 64)
        raise AssertionError("unexpected press; rerun without pressing")
    except Interrupted as error:
        print(error)
    finally:
        signal.alarm(0)
    os.set_blocking(fd, False)
    try:
        os.read(fd, 64)
        raise AssertionError("unexpected new sequence")
    except BlockingIOError as error:
        assert error.errno == errno.EAGAIN
        print("Same open remains usable: EAGAIN")
finally:
    signal.alarm(0)
    os.close(fd)
PY
```

The driver uses interruptible waits and mutex acquisition. At the system-call boundary a signal may cause `EINTR` or a restart, depending on signal handling. Python normally retries some interrupted calls; this handler deliberately raises an exception so its read does not restart. The test checks escape from the idle read and reuse of that open, rather than claiming that Python prints a raw `EINTR`. An interruption that exits the wait before copying a record does not advance `seen`. Here, with no presses, the next nonblocking read should report `EAGAIN`.

## 4. Detach with a descriptor still open

An open device file pins this module's code through `.owner = THIS_MODULE`. Ordinary `rmmod mybutton` will normally refuse while it is open. That is a useful module-lifetime rule; it does not exercise a bound device disappearing while the module stays loaded. Use the driver core's **unbind** operation for that test. Never use forced module removal.

First read the implementation already built in 8.3. This is the complete file, including its failure unwinding and removal path:

```c
{{#include ../examples/kernel/mybutton.c}}
```

There are two lifetimes. `kref_init` gives the device object its base reference; each successful open takes another. Closing the open drops its reference, and the final `kref_put` calls `hfs_free`. A reference keeps the allocation alive; it does not keep detached hardware resources usable. These are the [kernel's kref rules](https://www.kernel.org/doc/html/v6.12/core-api/kref.html).

`hfs_remove` performs the following ordered work:

1. Mark `online=false` under the same spinlock used for state snapshots, then wake the wait queue. Offline itself satisfies `hfs_ready`, so a waiter need not receive another press.
2. Deregister the misc device to stop new opens. The [misc core](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/drivers/char/misc.c) serialises its open path against deregistration; an overlapping open either obtains a valid reference while online or fails.
3. Free the IRQ, waiting for its handlers to finish, so they cannot queue more debounce work. Then synchronously cancel delayed work, including a running callback.
4. Request LED-low while the descriptor is still valid, then drop the base reference. The driver core releases the managed GPIO resources after remove returns.

The IRQ/work synchronization matters even with `online`: a worker may already have sampled a GPIO or passed its state check when removal starts. Cancellation completes before GPIO release or final freeing. The [IRQ](https://www.kernel.org/doc/html/v6.12/core-api/genericirq.html) and [workqueue](https://www.kernel.org/doc/html/v6.12/core-api/workqueue.html) contracts supply those synchronization operations. The managed-resource boundary is documented in [devres](https://www.kernel.org/doc/html/v6.12/driver-api/driver-model/devres.html).

An old open retains only offline memory: its nonzero reads return `ENODEV` at the online check, and poll reports `POLLERR | POLLHUP`. These file operations must not access the released GPIOs. A zero-length read still returns 0, because that branch precedes the online check. An unread event can be discarded when offline wins the check; a read that captured an online snapshot before detach can still finish successfully. There is no promise to drain pending events at removal.

In **Pi shell A**, release the button, wait half a second, and run this bounded helper. Make no presses. It prints readiness before entering a blocking read:

```sh
python3 - <<'PY'
import errno
import os
import select
import signal

def expired(signum, frame):
    raise TimeoutError("unbind did not interrupt the read within 30 seconds")

signal.signal(signal.SIGALRM, expired)
fd = os.open("/dev/mybutton", os.O_RDONLY | os.O_CLOEXEC)
try:
    signal.alarm(30)
    print("READY: shell B must unbind the verified lesson device now", flush=True)
    try:
        os.read(fd, 64)
        raise AssertionError("unexpected event; rerun without pressing")
    except OSError as error:
        assert error.errno == errno.ENODEV, error
        print("Existing open: ENODEV")
    finally:
        signal.alarm(0)
    assert os.read(fd, 0) == b""
    p = select.poll()
    p.register(fd, select.POLLIN)
    events = p.poll(1000)
    assert events, "offline descriptor was not ready"
    mask = events[0][1]
    assert mask & select.POLLERR and mask & select.POLLHUP, mask
    print("Existing open: POLLERR | POLLHUP; zero-length read: 0")
finally:
    signal.alarm(0)
    os.close(fd)
PY
```

In **Pi shell B**, while shell A says `READY`, repeat step 1's device discovery block in this shell so `button_device` and `button_matches` are local and verified. Then run, from **`~/hardware-from-software`**:

```sh
(
    set -eu
    test "$button_matches" -eq 1
    test "$(readlink -f "$button_device/of_node")" = /sys/firmware/devicetree/base/hfs_button
    test "$(readlink -f "$button_device/driver")" = /sys/bus/platform/drivers/hfs-mybutton
    test "$(readlink -f "$button_device/driver/module")" = /sys/module/mybutton
    printf '%s\n' "${button_device##*/}" | sudo tee /sys/bus/platform/drivers/hfs-mybutton/unbind
    test ! -e "$button_device/driver"
    test ! -e /sys/class/misc/mybutton
)
```

The generated device name printed by `tee` is not a driver log. Shell A should finish with `ENODEV` and error/hangup readiness; it must not remain asleep until its alarm. `READY` establishes that the descriptor is open; scheduling can still let unbind win before the read actually sleeps. Repeat the test to exercise different schedules, and retain the source-level lifetime reasoning. The LED should be driven low during removal, but no permanent voltage is guaranteed after releasing its GPIO. The DT device remains, and `/sys/module/mybutton` remains: unbind detached the device, not the module.

After shell A exits and closes its descriptor, **shell B, same directory**, rebind only that same discovered device:

```sh
(
    set -eu
    test "$button_matches" -eq 1
    test "$(readlink -f "$button_device/of_node")" = /sys/firmware/devicetree/base/hfs_button
    test ! -e "$button_device/driver"
    printf '%s\n' "${button_device##*/}" | sudo tee /sys/bus/platform/drivers/hfs-mybutton/bind
    test "$(readlink -f "$button_device/driver")" = /sys/bus/platform/drivers/hfs-mybutton
    sudo udevadm settle
    ls -l /dev/mybutton
)
```

Rebinding probes a **new object**, with sequence zero and LED off. If the button is held at probe, that initial level is remembered without incrementing the counter: release, wait half a second, then press. An old descriptor, if retained across rebind, would still refer to its old offline object; reopening is required to join the new lifetime.

## 5. Repeat clean module lifetimes

Close all your clients first; finish both helpers and stop any foreground watcher. Keep the button released. In **shell B**, which still has its verified device variables, run three bounded cycles. This intentionally removes the known lesson module left by the preceding steps, then reloads the explicit artifact:

```sh
(
    set -eu
    test "$button_matches" -eq 1
    for cycle in 1 2 3; do
        test "$(readlink -f "$button_device/of_node")" = /sys/firmware/devicetree/base/hfs_button
        test "$(readlink -f "$button_device/driver")" = /sys/bus/platform/drivers/hfs-mybutton
        test "$(readlink -f "$button_device/driver/module")" = /sys/module/mybutton
        sudo rmmod mybutton
        test ! -d /sys/module/mybutton
        test ! -e "$button_device/driver"
        test ! -e /sys/class/misc/mybutton
        sudo insmod ./examples/kernel/mybutton.ko
        test "$(readlink -f "$button_device/driver")" = /sys/bus/platform/drivers/hfs-mybutton
        test "$(readlink -f "$button_device/driver/module")" = /sys/module/mybutton
        sudo udevadm settle
        test -c /dev/mybutton
        printf 'Completed cycle %s\n' "$cycle"
    done
)
sudo dmesg --since '5 minutes ago'
```

Stop if a cycle fails. Expected: no stale node or driver link after removal, successful binding after each insertion, and no new use-after-free, locking or workqueue diagnostics. The module has no success banner. Review the actual messages rather than assuming silent commands prove correctness. Three cycles exercise a few schedules; they cannot establish absence of all races.

| Symptom | Action |
| --- | --- |
| `rmmod` says module in use | Close your identified device clients; inspect `sudo fuser -v /dev/mybutton` while the node exists and `lsmod`. Do not kill unrelated processes or force removal. |
| Unbind read reaches its alarm | Confirm shell B actually detached the verified device and inspect kernel messages. A timeout is a failed teardown test, not a successful wake. |
| Helper receives an event before unbind | A press raced the experiment. Release, rebind if needed, and rerun without pressing. |
| Rebind fails or node stays absent | Inspect binding and new errors; check exclusive GPIO owners and module identity using 8.3. Do not write another device name into `bind`. |
| Permission denied after rebind | Inspect the recreated node and 8.5's udev rule/group membership. |
| Extra counts, missed taps or held notifications | Return to slow transitions; check pull-up and switch pairs with power removed. The delayed sample is not a complete bounce recorder. |

The final successful cycle leaves the driver bound, rule installed, Pi circuit unchanged and no clients open. Retain that state for later integration. To stop instead, close clients and use [8.3's module and boot-overlay cleanup](8.3-describe-the-device-and-bind-the-driver.md#troubleshooting-and-next-state), then verify GPIO ownership. Removing this firmware-applied overlay requires editing its specific boot directive and rebooting; runtime unbind alone does not remove the DT node. Remove only the lesson udev rule if you no longer need it, following 8.5.

## Prefer an existing subsystem when it fits

For a real GPIO key, Linux's standard `gpio-keys` driver and input subsystem are usually the better fit. Its [frozen binding](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/Documentation/devicetree/bindings/input/gpio-keys.yaml) describes child keys, GPIO polarity, `linux,code`, debounce interval and wakeup properties. Its [matching implementation](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/drivers/input/keyboard/gpio_keys.c) reports input events and handles established input-device lifecycle requirements. That lets ordinary input clients consume key events through the existing subsystem. It does not implement our custom accepted-press counter and LED-toggle ABI.

This custom driver made the obligations visible: resource ownership, filtering, per-open state, interruption and offline lifetime. Production code should take on those obligations only when existing interfaces do not supply the required behaviour. Do not bind `gpio-keys` to BCM27 alongside this driver; comparing their designs needs no additional GPIO owner.
