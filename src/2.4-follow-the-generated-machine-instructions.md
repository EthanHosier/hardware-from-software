# 2.4 — Follow the generated machine instructions

A C++ register assignment becomes a processor store. We will find that store in the actual `blink_registers.elf`, calculate its destination, and connect it to the LED output latch. Complete [2.3](2.3-replace-gpio-calls-with-register-accesses.md) first; use its unchanged source and pinned Chapter 1 tools.

This is a **Mac file-inspection exercise**. Keep the Pico unpowered, with USB unplugged. Retain only the existing external LED circuit: **Pico 2 GP16, physical 21 → 1 kΩ resistor → LED anode; cathode → GND, physical 23**. Leave Pi, button and Debug Probe detached. There is no flashing or live stepping here. Chapter 3 adds SWD and checks the running target.

## Start with the source and its types

The complete file remains `examples/pico/blink_registers.cpp`:

```cpp
{{#include ../examples/pico/blink_registers.cpp}}
```

Focus on `sio_hw->gpio_set = mask`. `sio_hw` is a typed pointer to the fixed SIO base, `0xd0000000`, in our Secure Arm configuration. The SDK struct places `gpio_set` at byte offset `0x18`. The member has type `io_wo_32`, a typedef of `volatile uint32_t`. Consequently this expression names a 32-bit peripheral register, rather than a variable allocated in SRAM. See the pinned [SIO layout](https://github.com/raspberrypi/pico-sdk/blob/2.3.1/src/rp2350/hardware_structs/include/hardware/structs/sio.h) and [access-type definitions](https://github.com/raspberrypi/pico-sdk/blob/2.3.1/src/rp2_common/hardware_base/include/hardware/address_mapped.h).

The compiler knows both the address and `mask = 1u << 16` at compile time. It need not perform that shift at runtime. It must still implement the volatile register access under this compiler's rules. `volatile` does not supply a CPU memory barrier or C++ thread synchronisation; those limits remain as discussed in 2.3. [GCC documents its volatile-access rules](https://gcc.gnu.org/onlinedocs/gcc-14.2.0/gcc/Volatiles.html).

GNU's [`objdump` manual](https://sourceware.org/binutils/docs/binutils/objdump.html) describes symbol-selected disassembly and the optional `-S` source interleaving.

100001ec: f04f 4350  mov.w r3, #3489660928  @ 0xd0000000

Whitespace is compacted here. Your linked code addresses can change with source, SDK, compiler or build-option changes. Identify the symbol and operations rather than searching for a permanently fixed `0x100001e8`.

## Read the store's operands

`r2` and `r3` are CPU registers, temporary values inside the processor. They are distinct from peripheral registers selected by memory addresses.

| Instruction in `led_on` | Meaning in this build |
| --- | --- |
| `mov.w r3, #3489660928` | Put SIO base `0xd0000000` in CPU register `r3`. `#` denotes an immediate constant. |
| `mov.w r2, #65536` | Put mask `0x00010000` in `r2`. No runtime shift is needed. |
| `str r2, [r3, #24]` | Store the 32-bit value in `r2` at address `r3 + 24` bytes. |
| `bx lr` | Branch through the link register, returning to the caller in this ordinary function. |

The two `mov.w` instructions materialise constants encoded in the instructions; they do not load these values from peripheral registers. Arm documents MOV, STR and BX in the [Cortex-M33 instruction guide, §§3.4.7, 3.14.3 and 3.11.2](https://documentation-service.arm.com/static/66be2153882fec713ef49e49).

For the store, calculate:

```text
destination = 0xd0000000 + 24 = 0xd0000018  (GPIO_OUT_SET)
value       = 0x00010000                   (bit 16)
```

The address selects the **operation**; the value selects the **GPIO bits**. The value is not a pointer to `0x00010000`, and `24` is not a GPIO number. The SIO hardware interprets each written 1 as a request to set the corresponding output-latch bit. Other bits remain unchanged. There is no preceding read of `GPIO_OUT` and no software read-modify-write in this function. The [RP2350 SIO register tables](https://datasheets.raspberrypi.com/rp2350/rp2350-datasheet.pdf#page=58) and pinned SIO layout establish that meaning.

`led_off` uses the same value but offset `32` decimal (`0x20` hexadecimal). Its destination is `0xd0000020`, `GPIO_OUT_CLR`; writing bit 16 clears GP16's latch. Turning an output off here means writing a nonzero mask to a different register, rather than writing zero to SET.

### Code addresses are not store destinations

The left column locates instructions in this linked firmware. `led_on` starts at `0x100001e0`, in the flash execute-in-place (XIP) address region. The `str` instruction resides at `0x100001e8` in this build. When executed, it requests a write to **`0xd0000018`**, calculated from its operands. Instruction location and data-access destination serve separate purposes. The [RP2350 address map](https://datasheets.raspberrypi.com/rp2350/rp2350-datasheet.pdf#page=28) identifies the XIP and SIO regions.

The middle hexadecimal groups are instruction encodings. Cortex-M33 uses Thumb instructions with 16-bit or 32-bit encodings. Here `mov.w` occupies four bytes, while `str` and `bx` each occupy two. `.w` describes encoding width; the two-byte `str` still stores a **32-bit word**. Arm's [instruction-width rules, §3.3.8](https://documentation-service.arm.com/static/66be2153882fec713ef49e49#page=95), distinguish these widths.

## Compilation and electrical timing are separate

The supplied Debug build uses `-Og -g`, as recorded in `.build/pico/CMakeCache.txt` and `build.ninja`. Debug does not mean “no optimisation”. `-Og` permits optimisations while supporting debugging; `-g` supplies debug information. `noinline` prevents these functions from being inlined, but does not freeze their instruction sequence. Different options can change register allocation, constant construction and source-line correspondence. Keep the baseline unchanged for Chapter 3. See GCC 14.2's [optimisation options](https://gcc.gnu.org/onlinedocs/gcc-14.2.0/gcc/Optimize-Options.html) and [`noinline` attribute](https://gcc.gnu.org/onlinedocs/gcc-14.2.0/gcc/Common-Function-Attributes.html#Common-Function-Attributes).

Disassembly establishes what instructions the binary contains. The architectural store requests an MMIO write; the RP2350's address decoding and SIO register semantics give it a hardware effect. Whether that effect reaches the external pin also depends on the output enable, SIO function selection and pad configuration established before the loop in 2.3. A correct store with pad isolation still enabled cannot establish the intended LED output.

Instruction count is not a measurement of bus completion, pad transition time or LED timing. Code fetching, processor execution, hardware access and the electrical load are different parts of the path. The `sleep_ms(500)` calls express the program's intended delay between output operations; these four instructions cannot prove an exact pulse width. No physical execution or timing has been measured in this exercise.

## Troubleshoot and keep the matching files

| Symptom | Check |
| --- | --- |
| Tool file not found | Run the pinned setup from the checkout root; set `arm_tools` again in the current shell. |
| ELF missing | Build the Pico examples, then inspect `.build/pico/blink_registers.elf`. |
| No `led_on` output | Use this target's ELF and unchanged source; retain `extern "C"` and `noinline`. Run the two disassembly commands separately. |
| Source interleaving absent with `-S` | Check that the source remains available at its build location. Plain `-d` still decodes instructions. |
| Addresses or instructions differ | Check SDK/toolchain and Debug configuration; rebuild matching source. Recalculate the store destination from your output. |

Leave USB unplugged and the LED wiring intact. Keep this ELF and its matching source: the next chapter attaches the [Debug Probe over SWD](3.1-attach-the-debug-probe-over-swd.md), then observes the running program. The result here is identifying and explaining the store, supported by target-compiled file evidence.
