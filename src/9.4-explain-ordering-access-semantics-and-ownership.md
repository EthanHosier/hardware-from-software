# 9.4 — Explain ordering, access semantics, and ownership

A register access has three separate requirements: the program must own the device, use the correct kind of access, and obey the device's ordering protocol. A valid pointer alone satisfies none of these. You will compare the Pico register code with Linux's MMIO interface, then read a small mapping fragment without executing it.

## RAM stores and device commands

In [9.2](9.2-observe-demand-paging-and-protection-faults.md), writing a byte changed ordinary anonymous memory. A device register can instead interpret a write as a command or acknowledge an event. Its datasheet defines the transaction's width, byte order and side effects.

| Operation | Meaning |
| --- | --- |
| Store to ordinary RAM | Replace stored data, subject to the program's synchronization rules. |
| Write a SET/CLR command | Change the selected bits of another hardware register. |
| Write one to a W1C field | Acknowledge/clear the selected latched condition. Writing zero leaves it alone. |
| Read a device register | Obtain device-defined data; some reads also consume data or clear status. |

The Pico's `blink_registers.cpp` writes `mask` to `sio_hw->gpio_set` or `gpio_clr`. These are dedicated SIO command registers; the state register is `gpio_out`. Do not read SET as though it held the output state. The RP2350 also provides address aliases for atomic SET/CLR/XOR operations on supported register blocks. The SDK's `hw_set_bits` uses a SET alias, as the interrupt example does for `proc0_irq_ctrl.inte[word]`. A mask write avoids a software read-modify-write that could overwrite another writer's changes to other bits. It does not arbitrate competing intentions for the same bit or protect a multi-register configuration sequence. See the [RP2350 datasheet, Atomic Register Access and SIO register descriptions](https://datasheets.raspberrypi.com/rp2350/rp2350-datasheet.pdf), and the pinned [SDK alias helpers](https://github.com/raspberrypi/pico-sdk/blob/079c6f39023649b154152db30f1d781e884879bc/src/rp2_common/hardware_base/include/hardware/address_mapped.h).

The interrupt example supplies a different contract. GP17 belongs to `intr[2]`; its falling-edge latch is bit 6 (`0x40`) and rising-edge latch bit 7 (`0x80`). These fields are W1C; neighbouring level fields are read-only. The ISR reads masked pending edges and assigns that mask directly to `intr[word]`. With `intr[word] |= mask`, the read could collect other pending edges and write their ones back too, acknowledging events the handler did not intend to clear. With `&= ~mask`, it could write zero to the very latch it meant to clear. Use the documented W1C write rather than either RAM idiom or a guessed alias operation. These field definitions are in the pinned [RP2350 IO_BANK0 header](https://github.com/raspberrypi/pico-sdk/blob/079c6f39023649b154152db30f1d781e884879bc/src/rp2350/hardware_regs/include/hardware/regs/io_bank0.h).

## What volatile contributes

The SDK describes register members using types such as `io_rw_32`, a `volatile uint32_t`. In these examples, volatile keeps the compiler from eliminating the intended register access as an unused ordinary-memory operation. It does not provide inter-thread synchronization, exclude another CPU, establish ownership, or create an MMU mapping. Nor does it order arbitrary ordinary-memory accesses around the device access. GCC explains this last limitation in its [volatile documentation](https://gcc.gnu.org/onlinedocs/gcc/Volatiles.html).

That is why `button_irq.cpp` uses an interrupt-masked handoff around its volatile `changed` flag. Linux's `mybutton.c` instead protects shared RAM state using locks. Those mechanisms coordinate software participants; they cannot change a register's W1C behaviour. Do not apply a C++ atomic operation to an MMIO pointer in place of a device command. Linux explicitly excludes MMIO from its [CPU atomic-operation interface](https://www.kernel.org/doc/html/v6.12/core-api/wrappers/atomic_t.html).

On the Pico, this book still relies on SDK startup, clocks and linker support. Direct peripheral programming begins inside that established firmware environment. On Linux, the existing controller driver has the corresponding responsibility for resource acquisition and register access; a consumer such as `mybutton` requests GPIO descriptors from it.

## 2. Follow acquisition, access and release

`devm_platform_ioremap_resource(pdev, 0)` looks up the platform device's first memory resource and delegates to `devm_ioremap_resource`. This convenience path is separate from 9.3's real controller, which explicitly calls `of_address_to_resource` before `devm_ioremap_resource`. See the frozen [platform helper implementation](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/drivers/base/platform.c).

The mapping helper checks the resource type, requests its memory region, and maps it. In the frozen implementation, an absent/invalid memory resource yields `-EINVAL`, a failed region claim `-EBUSY`, and allocation/mapping failure `-ENOMEM`. The result encodes failure in a pointer: `IS_ERR` tests it and `PTR_ERR` returns the error to the caller before any access. On success the fragment continues. [Frozen managed mapping code](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/lib/devres.c).

On Arm64, the successful mapping supplies a kernel virtual address with device access attributes. It is different from 9.1's userspace anonymous RAM mapping. `__iomem` marks an I/O address for tools such as [Sparse](https://www.kernel.org/doc/html/v6.12/dev-tools/sparse.html); the annotation itself creates neither mapping nor permission. Portable kernel code passes it to MMIO accessors rather than dereferencing it as a normal pointer. `readl` and `writel` provide 32-bit little-endian device accesses. [Linux 6.12 device I/O](https://www.kernel.org/doc/html/v6.12/driver-api/device-io.html#iomem-pointer-tokens).

`readl(registers + 0)` is one illustrative read at byte offset zero. Nothing here establishes that a real device has a side-effect-free, aligned, 32-bit readable register there, or checks that its defined register window covers this access. A real driver needs that hardware contract and appropriate bounds validation first. This fragment contains no initial write, status polling or write readback. `dev_dbg` may be disabled; silence would not mean a failed read. Returning `0` reports successful probe completion, not a hardware self-test.

The `devm_` records release the mapping and claim on failed probe or detach. They do not stop interrupts, work or users before releasing resources. Chapter 8's explicit offline transition and work cancellation remain necessary; devres does not reference-count resources for open files. See [Linux managed resource lifetime](https://www.kernel.org/doc/html/v6.12/driver-api/driver-model/devres.html). A successful claim is cooperative resource bookkeeping, not permission to bypass an existing owner with another mapping.

## 3. Separate ordering from completion

For default I/O mappings, Linux 6.12 guarantees that `readl`/`writel` operations from the same CPU thread to the same peripheral arrive in program order. They also provide documented relationships with normal-memory accesses: for example, an ordinary-memory write issued by that thread is ordered before its subsequent `writel`. The `_relaxed` variants retain same-thread, same-peripheral ordering but omit guarantees involving normal memory, locks and delay loops. Choose them only with a specific ordering argument. A memory barrier constrains access ordering; it is neither a universal cache flush nor evidence that a peripheral finished its operation. These guarantees depend on mapping attributes and accessor choice, as detailed in the [kernel I/O barrier rules](https://www.kernel.org/doc/html/v6.12/core-api/wrappers/memory-barriers.html#kernel-i-o-barrier-effects).

A bus can **post a write**: accept it into a buffer while delivery continues. Where the bus/device protocol requires flushing such writes, a read of an appropriate safe device or bridge register can establish delivery before proceeding. Choose a documented side-effect-free register and follow that bus's rules; a FIFO read or read-to-clear status register can change the device. This is not an instruction to read offset zero in our fragment. A readback that establishes delivery still does not prove that a conversion, transfer or other commanded operation has finished. Completion needs the device's specified status/interrupt protocol. A lock alone is not a general posted-write flush. See [Linux's I/O ordering discussion](https://www.kernel.org/doc/html/v6.12/driver-api/io_ordering.html).

For our GPIO consumer, the actionable rule is to keep calling the descriptor API. The owner traced in 9.3 implements the controller's access rules. Adding volatile casts, barriers or locks in a second driver cannot give that driver ownership of the same controller.

## Diagnose and leave the state unchanged

These are source-review symptoms, not failure experiments to provoke on the Pi:

| Symptom | Likely missing distinction |
| --- | --- |
| Other interrupt events disappear after an acknowledgement | A read-modify-write may have acknowledged additional W1C bits. Check the exact access type and mask. |
| A cast compiles but access faults | A numeric address and volatile qualifier create no Linux process mapping or permission. |
| Claim fails with `-EBUSY` | Another owner may already hold the resource. Identify that owner; do not bypass the claim. |
| A command is issued but the device is still busy | Access ordering/delivery and device completion are separate. Check the documented completion protocol. |
| Detach races with a callback | Managed release does not quiesce asynchronous users. Revisit 8.6's teardown order. |
