# 9.3 — Trace a real kernel MMIO mapping

The GPIO descriptor in `mybutton.c` eventually reaches a register. You will follow that path through Linux's existing Pi GPIO controller driver, connecting a live Device Tree address to a kernel mapping and then to the LED's SET/CLR register. This is a **read-only inspection and source walkthrough**. It creates no second hardware mapping and runs no new module.

Keep [8.6's final state](8.6-make-failure-and-teardown-behaviour-explicit.md): `mybutton` bound, permissions rule installed, clients stopped. Retain the Pi-only circuit: BCM17 physical 11 → 1 kΩ → LED anode; cathode → GND physical 9. BCM27 physical 13 → button → GND physical 14, with a 4.7 kΩ pull-up to Pi 3V3 physical 17. The Pico stays unplugged and all inter-board and debug wires stay absent. No wiring change is needed. Leave the owning GPIO/pinctrl driver bound throughout; its resources serve more than our two lines.

The distinction from [9.1](9.1-observe-your-linux-process-s-mappings.md) is which address space a number belongs to:

| Address | Who interprets it? |
| --- | --- |
| Device Tree `reg` address | The device's parent bus; `ranges` connects that bus to its parent. |
| Translated CPU physical address | The CPU-side hardware address map; this range selects peripheral registers rather than RAM. |
| Controller's mapped kernel address | Kernel page tables and MMIO accessors; it is not a userspace pointer. |
| Your process's pointer | That process's virtual mappings, as inspected in 9.1. |

## 1. Establish the source version before reading it

All commands below run in a **Pi SSH shell**, working directory **`~/hardware-from-software`**. Python 3, `curl`, and the matching headers are prerequisites from the earlier development lessons. First record the running kernel and installed package provenance:

```sh
cd ~/hardware-from-software
uname -r
uname -v
tr '\0' '\n' < /sys/firmware/devicetree/base/model
readlink -f "/lib/modules/$(uname -r)/build"
dpkg-query -W -f='${binary:Package} ${Version} source=${source:Package} ${source:Version}\n' \
  "linux-image-$(uname -r)" "linux-headers-$(uname -r)"
dpkg-query -S "$(readlink -f "/lib/modules/$(uname -r)/build")/Makefile"
dpkg-query -L "linux-headers-$(uname -r)" | sed -n '/changelog/p'
gzip -cd "/usr/share/doc/linux-headers-$(uname -r)/changelog.Debian.gz" | head -n 12
```

Check the package owner of the header Makefile, not just a similar release name. On the book's **compiled-header baseline**, the header package is `linux-headers-6.12.96+rpt-rpi-v8`, Debian version `1:6.12.96-1+rpt1`. Its first changelog entry records `Linux commit: ae161617d7a4552fa91d03626b8d9f3696d17481`. That package record is why this lesson uses that frozen official source. The epoch `1:` is part of Debian's version notation.

If a package or changelog is missing, use the package listing and ownership result to find the actual installed package's documentation; do not substitute a conveniently named header package. A custom kernel needs its builder's source commit and patch/configuration record. If your release, package version or source commit differs, the following is a **comparison with the frozen baseline**, not proof of your running driver's implementation. Obtain the official source revision identified by your own kernel package and repeat the function checks before calling it a live source match. Do not downgrade or replace the running kernel for this reading exercise. Matching headers permit a module build; they alone do not prove which image booted.

Read `bcm2835_pinctrl_match`, `bcm2711_gpio_chip`, `bcm2835_pinctrl_probe`, and the get/set helpers. ## 2. Identify the live controller and translate its resource

Run `gpiodetect` first and compare it with [5.3's controller identity checks](5.3-establish-gpio-identity-and-ownership.md). We expect the Pi 4 header controller's label to be `pinctrl-bcm2711`, but never assume its index is `gpiochip0`. The helper below finds that label, follows its `of_node`, then finds the corresponding platform device by the **same node**. It only reads sysfs and Device Tree properties; it does not request a GPIO or read a hardware register.

**Pi — same directory:**

```sh
gpiodetect
python3 - <<'PY'
from pathlib import Path
import re
import subprocess

root = Path('/sys/firmware/devicetree/base').resolve()
inventory = subprocess.check_output(['gpiodetect'], text=True)
print(inventory, end='')
names = re.findall(r'^(gpiochip[0-9]+)\s+\[pinctrl-bcm2711\]', inventory, re.M)
if len(names) != 1:
    raise SystemExit('Need exactly one verified BCM2711 controller; stop here')
chip = Path('/sys/bus/gpio/devices') / names[0]
nodes = {p.resolve() for p in (chip / 'of_node', chip / 'device/of_node')
         if p.exists()}
if len(nodes) != 1:
    raise SystemExit('Cannot identify one controller DT node; stop here')
node = nodes.pop()
devices = [p for p in Path('/sys/bus/platform/devices').iterdir()
           if (p / 'of_node').exists() and (p / 'of_node').resolve() == node]
if len(devices) != 1:
    raise SystemExit('Cannot identify one matching platform device; stop here')
device = devices[0]
print('DT node:', node)
print('compatible:', (node / 'compatible').read_bytes().replace(b'\0', b' '))
print('platform:', device)
print('bound driver:', (device / 'driver').resolve(strict=True))
print('resource file:', device / 'resource')
print((device / 'resource').read_text())

def cells(path):
    data = path.read_bytes()
    if len(data) % 4:
        raise SystemExit(f'Invalid cell length: {path}')
    return [int.from_bytes(data[i:i+4], 'big') for i in range(0, len(data), 4)]

def count(path):
    values = cells(path)
    if len(values) != 1 or not 1 <= values[0] <= 4:
        raise SystemExit(f'Unsupported cell count: {path}')
    return values[0]

def number(values):
    result = 0
    for value in values:
        result = (result << 32) | value
    return result

bus = node.parent
if bus.parent != root or b'simple-bus' not in (bus / 'compatible').read_bytes().split(b'\0'):
    raise SystemExit('This helper covers the Pi 4 simple bus directly below root only')
na = count(bus / '#address-cells')
ns = count(bus / '#size-cells')
pna = count(root / '#address-cells')
reg = cells(node / 'reg')
if len(reg) < na + ns or len(reg) % (na + ns):
    raise SystemExit('Invalid reg tuples')
address, size = number(reg[:na]), number(reg[na:na+ns])
print('cell counts: child-address=', na, 'parent-address=', pna, 'size=', ns)
print('reg cells:', [hex(v) for v in reg])
ranges = cells(bus / 'ranges')
width = na + pna + ns
if not ranges or len(ranges) % width:
    raise SystemExit('Expected nonempty complete ranges tuples; stop here')
matches = []
for i in range(0, len(ranges), width):
    row = ranges[i:i+width]
    child = number(row[:na])
    parent = number(row[na:na+pna])
    span = number(row[na+pna:])
    print('range: child=', hex(child), 'parent=', hex(parent), 'size=', hex(span))
    if size > 0 and child <= address and address + size <= child + span:
        matches.append(parent + address - child)
if len(matches) != 1:
    raise SystemExit('Need exactly one range containing the first reg resource')
physical = matches[0]
print('first resource: start=', hex(physical), 'size=', hex(size),
      'inclusive end=', hex(physical + size - 1))
PY
```

Stop if identity or translation fails. This deliberately bounded decoder covers the Pi 4's simple bus immediately below the root, not arbitrary PCI or nested bus translations. It reads cell counts from the relevant parents and combines **big-endian 32-bit cells**. Native-endian `od` output would need byte swapping on this Pi; interpreting it blindly can invent an address.

`reg` pairs an address with a length in the parent bus's format. A `ranges` tuple contains a child-bus address, parent-bus address and length; the address widths can differ. On the frozen Pi 4 tree, the GPIO address is `0x7e200000`. The matching range begins at child `0x7e000000`, parent `0x00000000fe000000`, with length `0x01800000`. Thus:

```text
CPU physical = parent base + (reg bus address - child base)
             = 0xfe000000 + (0x7e200000 - 0x7e000000)
             = 0xfe200000
```

These are source-derived baseline values, not an observed register dump. Derive the length and end from **your live `reg`**, and compare the helper's result with the identified sysfs `resource` row: its columns are hexadecimal start, **inclusive** end, and resource flags. Length is `end - start + 1`; unlike a maps row, the end is included. A platform resource can exist even when no driver has claimed it, so also check the bound-driver link. The frozen [common tree](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/arch/arm/boot/dts/broadcom/bcm283x.dtsi) supplies the GPIO `reg` and bus cell widths; [BCM2711's tree](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/arch/arm/boot/dts/broadcom/bcm2711.dtsi) overrides the root address width and ranges.

You may also inspect `cat /proc/iomem` on the **Pi, same directory**. It is a system resource inventory, not process mappings. Policy may redact its addresses as zero or restrict reads. Use the already identified sysfs resource description when permitted; if that is restricted too, record the limitation and compare source only. Do not change kernel security policy, use `/dev/mem`, or infer that redacted zeroes are the controller's address.

## 3. Follow resource lookup into the kernel mapping

This **fragment**, copied from the frozen `bcm2835_pinctrl_probe`, is existing controller code to read, not a new probe to build:

```c
err = of_address_to_resource(np, 0, &iomem);
if (err) {
	dev_err(dev, "could not get IO memory\n");
	return err;
}

pc->base = devm_ioremap_resource(dev, &iomem);
if (IS_ERR(pc->base))
	return PTR_ERR(pc->base);
```

`np` is the controller's DT node. `of_address_to_resource` translates its first `reg` entry through the ancestor bus ranges into `struct resource`. This is a description; it does not return a pointer for accessing registers. Its implementation calls `of_translate_address` for a memory resource. [Frozen OF address implementation](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/drivers/of/address.c).

`devm_ioremap_resource` validates the memory resource, claims its region and creates the mapping. It returns an error pointer on failure, including a resource conflict. Its managed records arrange unmapping and release on detach or failed probe. The helper delegates to the appropriate `ioremap` variant, including resource flags where applicable. [Frozen managed mapping implementation](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/lib/devres.c).

On this Arm64 system, `pc->base` is a **kernel virtual address** mapped to the physical peripheral region. It is neither `0xfe200000` cast to a pointer nor an address your C++ process may dereference. The mapping uses device access attributes rather than ordinary cacheable RAM behaviour: register reads must reach the device instead of being satisfied as ordinary cached data. `void __iomem *base` marks an I/O address for accessor and static-checking rules; the annotation itself neither creates a mapping nor grants ownership. `readl` and `writel` perform 32-bit MMIO accesses through that mapping. Their ordering and portability contract is more than a C `volatile` dereference. [Linux 6.12 device I/O](https://www.kernel.org/doc/html/v6.12/driver-api/device-io.html#iomem-pointer-tokens).

## 4. Follow our LED and button operations to registers

In our already-built `examples/kernel/mybutton.c`, `hfs_debounce` calls `gpiod_set_value_cansleep(button_device->led, light)` after an accepted press toggles `light`. The LED descriptor is active-high and push-pull, so the GPIO core's `gpiod_set_value_nocheck` reaches `gpiod_set_raw_value_commit`, which invokes the chip's `.set` callback with hardware offset **17**. BCM2711's table assigns `.set = bcm2835_gpio_set`. This is descriptor dispatch, not a physical mapping owned by `mybutton`. [Frozen GPIO core](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/drivers/gpio/gpiolib.c).

The callback chooses `GPSET0` for high or `GPCLR0` for low. The controller's following **fragments** show the final address and mask calculation:

```c
/* Fragment: bcm2835_gpio_set_bit */
reg += GPIO_REG_OFFSET(bit) * 4;
bcm2835_gpio_wr(pc, reg, BIT(GPIO_REG_SHIFT(bit)));

/* Fragment: bcm2835_gpio_wr */
writel(val, pc->base + reg);
```

Here `GPIO_REG_OFFSET(p)` is `p / 32`, and `GPIO_REG_SHIFT(p)` is `p % 32`. GPIO17 uses bank 0 and bit 17: mask `0x00020000`. High writes that mask at mapped base + `0x1c`; low writes it at base + `0x28`. These SET/CLR commands change the selected output without reading and rewriting the other outputs. They are not ordinary RAM assignments. The output direction and pin function were configured earlier; one store alone does not establish the whole electrical setup.

The button's later sample follows `gpiod_get_value_cansleep(button_device->button)` → GPIO core raw read → chip `.get` → `bcm2835_gpio_get` → `bcm2835_gpio_get_bit(pc, GPLEV0, 27)` → `bcm2835_gpio_rd` → `readl(pc->base + 0x34)`. The helper extracts bank 0, bit 27. The core then applies the descriptor's active-low flag: wire low becomes logical **pressed = 1**. IRQ delivery and debounce scheduling remain the separate mechanisms explained in 8.4. These paths and offsets come from the [frozen controller implementation](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/drivers/pinctrl/bcm/pinctrl-bcm2835.c), not from register values measured here.

## Diagnose and retain the state

| Symptom | Interpretation and action |
| --- | --- |
| Different kernel/source record | Read that exact official revision before claiming the callbacks match your running kernel; retain this walkthrough as a baseline comparison. |
| No matching chip, node or driver link | Recheck actual model, 5.3's identity discovery and sysfs layout. Do not replace a failed identity check with a guessed index or address. |
| Translation differs from sysfs resource | Check the selected node, first `reg` tuple, parent cell counts and ancestor ranges. Stop before drawing a mapping conclusion. |
| Permission denied or redacted addresses | Record what policy allows; source inspection remains useful without bypassing restrictions. |
| No controller `bind`/`unbind` files | Expected in this baseline: its driver sets `.suppress_bind_attrs = true`. Never try to detach or remap this system controller. |

The result is a trace, not a measured MMIO transaction: live identity and resource descriptions, version-qualified source, and a concrete descriptor → callback → accessor → register calculation. Existing CI compiled `mybutton` against the recorded Pi headers; that does not validate this whole controller path at runtime. Physical Pi execution and register values were not measured during authoring.

There is nothing to unload or unmap: the existing controller and `mybutton` retain ownership, clients remain stopped, and the circuit/Pico state is unchanged. Keep the downloaded source for [9.4 — Explain ordering, access semantics, and ownership](9.4-explain-ordering-access-semantics-and-ownership.md), which examines accessor semantics and the separate annotated mapping fragment.
