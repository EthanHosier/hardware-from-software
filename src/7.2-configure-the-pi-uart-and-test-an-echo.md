# 7.2 — Configure the Pi UART and test an echo

This lesson sends a known byte sequence from a Linux process on the Pi, through the GPIO UART to the Pico, and back. Success means the received bytes equal the transmitted bytes, including carriage return and binary values. It establishes the transport before [7.3](7.3-build-a-robust-c-serial-client.md) adds a command protocol.

Use the Pi 4 and non-wireless Pico 2 from [7.1](7.1-make-a-uart-link-electrically-and-logically-correct.md), the Mac build checkout, and SSH from Chapter 5. Keep your actual OS/kernel record from [5.2](5.2-verify-the-linux-development-environment.md). The primary route is Raspberry Pi OS Bookworm, 64-bit, with boot files in `/boot/firmware`; the recorded kernel compilation baseline is `6.12.96+rpt-rpi-v8`, not a claim about your running kernel. This page's firmware has been compiled; physical UART operation has not been exercised during authoring.

## 1. Separate configuration from wiring

If 7.1 left the three UART wires installed with both boards off, detach **all three**, including ground, before powering either board alone. Keep the Pico unplugged while configuring the Pi. Remove old Pi–Pico I²C wires and the Pico GP19–GP20 SPI loopback jumper if still present. Retain the Pico GP16 LED/resistor and GP17 button/external pull-up circuit. Pi BCM17 and BCM27 remain unused. Leave the Debug Probe's **U** connector empty and the probe disconnected.

Later, with **both boards off**, restore exactly this circuit:

| Pi 4 header | Direction | Pico 2 header |
| --- | --- | --- |
| BCM14 TX, physical 8 | Pi → Pico | GP1 RX, physical 2 |
| BCM15 RX, physical 10 | Pi ← Pico | GP0 TX, physical 1 |
| GND, physical 6 | Common reference | GND, physical 8 |

Use 7.1's labelled diagram to locate the contacts. Both ends use 3.3 V logic. These are not RS-232 voltage levels, and neither UART accepts a direct 5 V signal. Power each board through its own USB connection; join no 3V3, 5V, VSYS, or other power rail.

## 2. Reserve the Pi's PL011 UART

A UART device file is not automatically a free communications channel. Kernel console output, a serial login process, or Bluetooth can own it. We choose **UART0, a PL011**, on BCM14/15. On a stock Pi 4 the PL011 serves Bluetooth and the header uses the mini-UART. The mini-UART's baud rate depends on the VPU core clock; choosing PL011 avoids that clock dependency. `/dev/serial0` is a symbolic link naming the primary UART, so inspect its destination rather than inferring hardware from the name. These mappings are Pi 4 specific. [Official UART documentation](https://www.raspberrypi.com/documentation/computers/configuration.html#configuring-uarts).

Power only the Pi and reconnect by SSH. **Pi — SSH, working directory `~`:**

```sh
cd ~
findmnt /boot/firmware
ls -l /boot/firmware/config.txt /boot/firmware/cmdline.txt
backup=$(mktemp -d "$HOME/uart7.2-before.XXXXXX")
sudo cp -a /boot/firmware/config.txt "$backup/config.txt"
sudo cp -a /boot/firmware/cmdline.txt "$backup/cmdline.txt"
for unit in hciuart.service serial-getty@serial0.service serial-getty@ttyAMA0.service serial-getty@ttyS0.service; do
    printf '\n%s\n' "$unit"
    systemctl is-enabled "$unit" || true
    systemctl is-active "$unit" || true
done | tee "$backup/services.txt"
printf 'Keep this backup directory: %s\n' "$backup"
sudo cat /boot/firmware/config.txt
cat /boot/firmware/cmdline.txt
```

Record the printed backup path; shell variables will disappear after reboot. Read any `include` files recursively and the conditional sections that apply to this Pi. Back up an included file with `sudo cp -a` before changing it, retaining its original path in your notes. Preserve unrelated overlays, comments, and section boundaries. If a `cmdline=` setting selects another command-line file, back up and edit that selected file instead of the default below. [Configuration files and includes](https://www.raspberrypi.com/documentation/computers/config_txt.html).

**Pi — SSH, working directory `~`:**

```sh
sudo nano /boot/firmware/config.txt
```

Resolve existing conflicting UART settings in the applicable sections/includes: for example, comment out an active `dtoverlay=miniuart-bt`, UART pin remapping, or `enable_uart=0`. Keep unrelated settings. At the end of the main file, use an explicit `[all]` section so these settings cannot accidentally remain under a different board's filter. Add each setting only once in the effective configuration:

```ini
# Chapter 7: Pi 4 header UART0
[all]
enable_uart=1
dtoverlay=disable-bt
```

The `disable-bt` overlay disables onboard Bluetooth and restores UART0/`ttyAMA0` to GPIO14/15 on pre-Pi-5 boards. Its [official overlay reference](https://github.com/raspberrypi/firmware/blob/master/boot/overlays/README) documents this routing. Stop the Bluetooth modem service now and disable its next-boot startup. If your earlier record says `not-found`, there is no such service to change; skip that command and record the absence.

**Pi — SSH, working directory `~`:**

```sh
sudo systemctl disable --now hciuart.service
sudo nano /boot/firmware/cmdline.txt
```

In the command-line file remove **only** serial console tokens targeting this route: commonly `console=serial0,115200`, `console=ttyAMA0,115200`, or `console=ttyS0,115200`. Keep `console=tty1`, `root=…`, `rootwait`, and every unrelated argument. Keep the file as **one line**. If present, also remove an `earlycon` or `kgdboc` setting targeting this UART: an early/debug console is another source of traffic. Do not replace the line with a tutorial's example. A standard image normally has no such debugging settings. [Official kernel command-line reference](https://www.raspberrypi.com/documentation/computers/configuration.html#cmdline).

For each of the three `serial-getty@…` units recorded above that was enabled or active, stop and disable it explicitly, using its exact name. For example, if `serial-getty@ttyAMA0.service` was enabled:

```sh
sudo systemctl disable --now serial-getty@ttyAMA0.service
```

A generated getty may have no enablement links to disable; removing its kernel console token prevents regeneration on reboot. Do not disable SSH. The equivalent official `raspi-config` serial choices are **No** to a login shell and **Yes** to serial hardware; those choices alone do not select our Bluetooth/PL011 route. This page uses the explicit file route so the changes and backups are visible.

**Pi — SSH, working directory `~`:**

```sh
sudo reboot
```

## 3. Verify the live owner and permissions

Reconnect SSH after reboot, with the Pico and inter-board wires still disconnected. **Pi — SSH, working directory `~`:**

```sh
cd ~
ls -l /dev/serial0
readlink -f /dev/serial0
cat /proc/cmdline
systemctl is-active hciuart.service
systemctl list-units --all 'serial-getty@*'
ls -l /dev/ttyAMA0
id
sudo fuser -v /dev/ttyAMA0
```

On this selected Pi 4 route, the link must resolve to **`/dev/ttyAMA0`**, not `ttyS0`. `/proc/cmdline` must contain no console/debug argument selecting this UART. There must be no active getty for `serial0` or `ttyAMA0`, and `hciuart` must be inactive or absent. `fuser` should show no process using the port; its no-owner exit status is normal. If unavailable, install `psmisc` on the Pi. Do not proceed by killing an unidentified owner: inspect and stop its application/service first. A kernel console need not appear in `fuser`, hence the separate command-line check.

The normal device permissions grant access to the `dialout` group. If the actual device is group `dialout` and `id` shows you lack membership, run **on the Pi**:

```sh
sudo usermod -aG dialout "$USER"
```

Log out of all Pi SSH sessions, reconnect, and repeat `id`. Record if you added this membership for later reversal. Do not use `chmod 666` or run the echo test as root to conceal an ownership problem. A different device group or unexpected mapping requires resolving the OS/overlay configuration first.

## 5. Compare an actual round trip

Close any serial terminal or previous test and repeat the no-owner check. Use exactly one reader: two readers divide incoming bytes between themselves. Do not use `serial_client` yet; it expects the later command protocol and cannot validate this raw echo.

The following complete diagnostic runs inline, without creating another shared application. **Pi — SSH, working directory `~/hardware-from-software`:**

```sh
cd ~/hardware-from-software
python3 - <<'PY'
import os
import select
import termios
import time
import tty

path = '/dev/serial0'
pattern = b'UART echo 0123\r\n\x00\x7f\x80\xff'
fd = os.open(path, os.O_RDWR | os.O_NOCTTY | os.O_NONBLOCK)
saved = None
try:
    saved = termios.tcgetattr(fd)
    tty.setraw(fd, when=termios.TCSANOW)
    settings = termios.tcgetattr(fd)
    settings[0] &= ~(termios.IXON | termios.IXOFF | termios.IXANY)
    settings[2] &= ~(termios.CSIZE | termios.PARENB | termios.CSTOPB | termios.CRTSCTS)
    settings[2] |= termios.CS8 | termios.CLOCAL | termios.CREAD
    settings[4] = settings[5] = termios.B115200
    settings[6][termios.VMIN] = 0
    settings[6][termios.VTIME] = 0
    termios.tcsetattr(fd, termios.TCSANOW, settings)
    termios.tcflush(fd, termios.TCIOFLUSH)
    sent = 0
    received = bytearray()
    deadline = time.monotonic() + 5.0
    quiet_until = None
    while True:
        now = time.monotonic()
        if quiet_until is not None and now >= quiet_until:
            break
        if now >= deadline:
            raise TimeoutError(f'sent {sent}, received {len(received)} bytes')
        wait_until = min(deadline, quiet_until or deadline)
        try:
            readable, writable, _ = select.select(
                [fd], [fd] if sent < len(pattern) else [], [], wait_until - now)
            if writable:
                n = os.write(fd, pattern[sent:])
                if n == 0:
                    raise RuntimeError('zero-length write')
                sent += n
            if readable:
                chunk = os.read(fd, len(pattern) + 1 - len(received))
                if not chunk:
                    raise RuntimeError('port became unreadable/disconnected')
                received.extend(chunk)
                if len(received) > len(pattern):
                    raise RuntimeError('unexpected extra UART data')
            if sent == len(pattern) and len(received) == len(pattern) and quiet_until is None:
                quiet_until = time.monotonic() + 0.2
        except (BlockingIOError, InterruptedError):
            continue
    print('TX:', pattern.hex(' '))
    print('RX:', bytes(received).hex(' '))
    if bytes(received) != pattern:
        raise RuntimeError('echo mismatch')
    print('Exact echo matched')
finally:
    try:
        if saved is not None:
            termios.tcsetattr(fd, termios.TCSANOW, saved)
    finally:
        os.close(fd)
PY
```

Expected, **not measured here**: TX and RX hexadecimal strings match, followed by `Exact echo matched`. The bytes include `0d 0a`, `00`, `7f`, `80`, and `ff`; raw mode prevents the Linux terminal layer from turning them into line editing or newline translations. `tty.setraw` disables that device's terminal echo, which could otherwise feed received bytes back onto TX. The explicit flags disable software/hardware flow control, enable the receiver with `CREAD`, ignore modem-control lines with `CLOCAL`, and set 115200/8N1 even if a previous application left different settings. The SSH shell displaying your pasted command is unrelated to a GPIO round trip.

The test uses nonblocking reads/writes, handles partial transfers, limits reception to the expected length plus one, and imposes a five-second transfer deadline. The final 0.2-second listening period catches immediate extra traffic; it does not prove the link will remain noise-free forever. The `finally` block restores the saved device settings and closes the descriptor on success, failure, or Ctrl+C. No background reader remains. The printed hex comes from bytes read from the UART, not from locally displaying typed characters.

The path is Pi `write` → PL011 TX → Pico GP1 RX → `uart_getc` → `uart_putc_raw` → Pico GP0 TX → Pi PL011 RX → `read`. Linux may return several chunks for one transmitted sequence. UART carries bytes, without a concept of a complete request; the next page supplies that missing framing.

## Diagnose and leave the next state

| Symptom | Check and correction |
| --- | --- |
| Missing `/dev/serial0`, or link targets `ttyS0` | Recheck the model, effective config/includes, `disable-bt`, and reboot. Do not substitute Pi 5 instructions or add clock settings to disguise the wrong route. |
| `Permission denied` | Check the resolved node's group and fresh SSH group membership. |
| Timeout with no received bytes | Confirm both boards are powered, `uart_echo.uf2` was flashed, and there is no competing reader. With both boards off, check Pi TX → Pico RX, Pico TX → Pi RX, and common ground. USB serial access does not test these wires. |
| Partial or garbled data | Check both ends are 115200, 8N1, no flow control; inspect loose contacts and physical versus GPIO numbering. Recheck the actual PL011 route and other owners. |
| Login text, boot messages, extra bytes, or repeating traffic | Inspect `/proc/cmdline`, active getty/Bluetooth services, and serial terminals. Ensure raw mode with terminal echo disabled; do not strip noise until a comparison passes. |

Keep UART0 reserved, Bluetooth disabled, and the serial console off for 7.3/7.4. Leave **`uart_echo`** installed until the next page explicitly replaces it with `uart_device`. To stop bench work, shut down the Pi and disconnect both supplies before touching wiring. For Pico-only programming, always detach all three inter-board wires with both boards off first.

To abandon this route, first shut down both boards and detach the inter-board wires. Boot the Pi alone. Set `backup` to the directory printed in step 2, inspect its `services.txt`, and restore the saved configuration and command-line files using `sudo cp -a "$backup/config.txt" /boot/firmware/config.txt` and `sudo cp -a "$backup/cmdline.txt" /boot/firmware/cmdline.txt`. Restore any included or alternate command-line files you edited. If unrelated boot changes were made since the backup, undo only this lesson's edits instead of overwriting those later changes. Reboot before starting Bluetooth again. Restore each changed service's **recorded** enabled/disabled state with `sudo systemctl enable UNIT` or `sudo systemctl disable UNIT`; start it only if originally active. Generated gettys return through the restored console configuration. Leave originally absent or masked services alone. If this lesson added your `dialout` membership and it is no longer needed, `sudo gpasswd -d "$USER" dialout` on the Pi reverses it after logout/login. Keep the backups until the original state works.
