# 1.1 — Install a reproducible macOS toolchain

By the end of this lesson, your Mac can run the compiler, build tools and debugger used throughout the Pico lessons. You will verify which executable each command selects and which processor the compiler targets. No board connection is needed.

Complete the [bench preparation](0.6-assemble-the-bench-and-understand-the-electrical-rules.md) first. Leave the Pico, Pi and Debug Probe disconnected from power. The external LED circuit can remain assembled and unpowered; this lesson adds no wires. You need an Apple Silicon Mac, an internet connection and the book's example files. The installer deliberately rejects Intel Macs and Linux; [Appendix B](appendix-b.md) covers recovery and other environments.

## The compiler runs here; its output runs elsewhere

The **host** is the computer running a development tool: your Mac. The **target** is the machine for which the tool produces code: the Pico 2's Arm Cortex-M33. Both processors implement Arm instruction sets, but a macOS executable and bare-metal firmware have different instruction profiles, executable formats and runtime assumptions.

`arm-none-eabi-g++` is a Mac program that produces embedded Arm code. `none` means there is no target operating system; `eabi` names the embedded application binary interface. Apple's `clang++` normally produces a Mac application instead. We will use it later for host tests, but it is not the Pico compiler selected here.

| Tool | Job on the Mac |
| --- | --- |
| Arm GCC/G++ and binutils | Compile C/C++, link firmware, inspect its machine code. |
| CMake | Configure the project and generate build instructions. |
| Ninja | Execute those instructions when sources change. |
| Pico SDK | Supply headers, libraries, startup code and board/build definitions. This is source, not a program to launch. |
| Arm GDB | Read the firmware's debug information and control a target through a debug server. |
| OpenOCD | Translate debugger requests into SWD operations through the Debug Probe. |
| picotool | Support Pico binary processing and device operations; the build uses it when generating firmware files. |

## 1. Check the Mac prerequisites

**Mac — working directory: your home directory.** Open Terminal and run:

```sh
cd ~
uname -m
xcode-select -p
git --version
python3 --version
```

`uname -m` must report `arm64`. If it reports `x86_64` on an Apple Silicon machine, reopen Terminal without Rosetta translation before continuing. The selected developer directory may be `/Library/Developer/CommandLineTools` or a directory inside an installed Xcode application.

If the developer tools are missing, run the following command and finish Apple's installation dialog. Then repeat the checks above. The full Xcode application is not required for this route. Apple documents this command in [Installing the command-line tools](https://developer.apple.com/documentation/xcode/installing-the-command-line-tools/).

**Mac — working directory: your home directory; only if the tools are missing:**

```sh
xcode-select --install
```

Use Python 3.9 or newer with the `venv` module. If `python3` is missing or too old, install a supported macOS Python from [Python.org](https://www.python.org/downloads/macos/), reopen Terminal and check again. The authoring machine used Python 3.9.6; Python itself is a prerequisite rather than a dependency pinned by the installer.

## 2. Put the example tree in a known location

All following lessons assume the project root is `~/hardware-from-software`. This means the directory containing `scripts/`, `examples/` and `EXAMPLES.md`, not an enclosing downloads directory.

Download `hardware-examples.zip` from [Download the examples](downloads.md). If Safari already expanded it, move or rename the extracted directory to `hardware-from-software` in your home directory. Otherwise, with the archive saved under its original name, use:

**Mac — working directory: your home directory; for a new example directory:**

```sh
cd ~
mkdir hardware-from-software
unzip ~/Downloads/hardware-examples.zip -d ~/hardware-from-software
cd ~/hardware-from-software
ls scripts/setup_deps.py scripts/build_examples.py examples/pico/CMakeLists.txt
```

The archive contains those paths directly. If `mkdir` reports that the directory exists, inspect your existing copy rather than extracting over modified work. If you already have an authorised clone of the source repository, use that checkout instead; no second clone is needed. Replace `cd ~/hardware-from-software` with its actual location in every command block. The repository is private, so the public example archive is the route that does not require repository access.

## 3. Install the pinned tools

**Mac — working directory: `~/hardware-from-software`:**

```sh
cd ~/hardware-from-software
python3 scripts/setup_deps.py
```

This is the book's installer, not Raspberry Pi's similarly named setup tooling. It creates `.deps/` inside this project. It creates a Python virtual environment for CMake and Ninja, clones SDK 2.3.1, checks its exact commit, initialises the TinyUSB submodule needed by our USB examples, and installs the compiler and Raspberry Pi tool bundles. Downloaded compiler and tool archives have SHA-256 checks recorded in the script. You can rerun it after an interrupted download; completed installations are reused.

The selected baseline is SDK **2.3.1**, commit `079c6f39023649b154152db30f1d781e884879bc`, and Arm GNU **14.2.Rel1** for `darwin-arm64-arm-none-eabi`. Raspberry Pi's [SDK release](https://github.com/raspberrypi/pico-sdk/releases/tag/2.3.1) and [tools release v2.3.1-0](https://github.com/raspberrypi/pico-sdk-tools/releases/tag/v2.3.1-0) identify the upstream versions. Pinning keeps later examples tied to one known SDK/header set; it does not claim this is the newest available release.

The script cannot modify the environment of your already running shell. Expose the installed tools explicitly for interactive commands:

**Mac — working directory: `~/hardware-from-software`; repeat in each new Terminal session:**

```sh
cd ~/hardware-from-software
export PICO_SDK_PATH="$PWD/.deps/pico-sdk"
export PATH="$PWD/.deps/venv/bin:$PWD/.deps/arm-gnu-toolchain-14.2.rel1-darwin-arm64-arm-none-eabi/bin:$PWD/.deps/openocd:$PWD/.deps/picotool/picotool:$PATH"
export OPENOCD_SCRIPTS="$PWD/.deps/openocd/scripts"
rehash
```

Prepending these directories makes this copy take precedence over other installations. `OPENOCD_SCRIPTS` points to the configuration scripts distributed with this OpenOCD binary. Do not copy these project-specific exports into a global shell configuration unless you intentionally want this checkout to supply tools for other projects.

## 4. Verify paths and versions

**Mac — working directory: `~/hardware-from-software`, after the exports above:**

```sh
command -v arm-none-eabi-gcc arm-none-eabi-g++ cmake ninja arm-none-eabi-gdb openocd picotool
arm-none-eabi-gcc --version
arm-none-eabi-gcc -dumpmachine
cmake --version
ninja --version
arm-none-eabi-gdb --version
openocd --version
picotool version
git -C "$PICO_SDK_PATH" rev-parse HEAD
test -f "$OPENOCD_SCRIPTS/target/rp2350.cfg" && echo 'RP2350 configuration present'
```

Every path printed by `command -v` should be beneath this project's `.deps/`. The SDK commit must match the value above. These are the executable versions recorded on the authoring Mac:

| Check | Recorded result |
| --- | --- |
| GCC | `14.2.1 20241119`, release label `Arm GNU Toolchain 14.2.Rel1` |
| Compiler target (`-dumpmachine`) | `arm-none-eabi` |
| CMake | `3.31.6` |
| Ninja | `1.11.1.git.kitware.jobserver-1` |
| GDB | `15.2.90.20241130-git` |
| OpenOCD | `0.12.0+dev-gacff23f (2026-09-05-14:14)` |
| picotool | `v2.3.1` |

The pinned Python package is `ninja==1.11.1.4`; its bundled executable prints the longer banner above. Likewise, GDB's version is independent of GCC's version even though both arrive in one Arm toolchain archive. OpenOCD's `+dev` build is the Raspberry Pi bundle, which includes the RP2350 target configuration; do not substitute an arbitrary executable merely because it says `0.12.0`.

`-dumpmachine` establishes the compiler's target family. The later CMake selection `PICO_BOARD=pico2` and `PICO_PLATFORM=rp2350-arm-s` selects this board and Arm platform; the toolchain name alone does not do that. A working version command also does not establish that a probe or board is connected.

## If a check fails

**A command is missing or points outside `.deps/`.** Return to the project root, repeat the exports and `rehash`, then repeat `command -v`. The automated build script sets its own compiler/CMake/Ninja search path, but that does not change your Terminal's path.

**The installer reports a checksum mismatch or SDK commit mismatch.** Stop at that error. Do not bypass the check or check out a newer SDK to make it disappear. Preserve your source edits and follow the dependency recovery instructions in [Appendix B](appendix-b.md). A checksum mismatch may be a damaged cached download; a commit mismatch means the SDK directory differs from the baseline.

**A download fails, or Python reports a certificate error.** Check the network and system clock. For Python.org installations, follow the installer's certificate setup instructions. Retry the setup script after fixing the cause; do not disable HTTPS verification.

**macOS refuses to launch a downloaded executable.** Read the macOS dialog and confirm you downloaded through the script's official source and passed its hash check. Follow macOS Privacy & Security's per-application review if offered. Do not disable system-wide security controls.

**GDB runs but OpenOCD has no RP2350 configuration.** Check both the executable path and `OPENOCD_SCRIPTS`. A binary from one installation and scripts from another are an inconsistent pair.

## Optional editor integration and next state

You can edit the sources in any editor. Raspberry Pi also provides an [official Pico VS Code extension](https://github.com/raspberrypi/pico-vscode) that manages SDKs and tools and creates projects. It is an alternative managed environment: its generated settings and tool paths may differ from this book's `.deps/` baseline. Keep the commands above in an ordinary Terminal when following this route, and avoid mixing extension-managed SDK paths into an existing build directory.

Keep `.deps/` and leave all boards unpowered. Closing Terminal discards these shell exports; no background debugger server was started. In [1.2 — Understand the smallest useful project](1.2-understand-the-smallest-useful-project.md), we will read the complete CMake/C++ project and run `python3 scripts/build_examples.py --pico` to produce ELF and UF2 files. The published verification record reports all 12 Pico targets compiled with this baseline; no physical flashing or runtime result is implied.
