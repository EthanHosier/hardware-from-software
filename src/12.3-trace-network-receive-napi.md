# 12.3 — Follow receive DMA, interrupts and NAPI into a socket

Incoming bytes do not arrive in the UDP application's array directly. The driver first supplies RAM to the Ethernet controller, later hands a completed packet to Linux, and supplies replacement storage for the next frame. Here we connect those ownership changes to interrupts, NAPI polling and the finite exchange from [11.2](11.2-send-numbered-udp.md).

Finish [12.2](12.2-trace-network-transmit-dma.md) first. Keep the Pi 4 on `6.12.96-hfs1-v8`, with the source/provenance record checked in [12.1](12.1-trace-network-driver-probe.md). Leave GPIO wiring unchanged and the Pico powered off with inter-board wires disconnected. The physical observation reuses the verified Ethernet/LAN path and Pi wired address from 11.1; Mac Wi-Fi can carry the requests. A private veth run remains useful when that path is unavailable, but cannot exercise GENET, its IRQs or DMA. No new driver or kernel build is needed.

## A replacement buffer before delivery

![GENET receive ownership: the driver maps replacement RAM for device writes and programs an MMIO descriptor; DMA fills packet RAM; the queue interrupt schedules NAPI; polling replaces and unmaps the old buffer before reading its receive status and passing its skb to GRO, IP, UDP and a socket.](assets/12.3-genet-rx-ownership.svg)

[Open the larger diagram](assets/12.3-genet-rx-ownership.svg). This is a conceptual data/ownership path, not a physical board drawing. An `sk_buff` (skb) is kernel packet metadata with associated storage. The driver controls the lifetime of that storage until it transfers the received skb to the stack.

1. Read the matched driver on the **Pi, repository root** (`~/hardware-from-software`):

```sh
uname -r
GENET=.build/pi-kernel/source/drivers/net/ethernet/broadcom/genet/bcmgenet.c
grep -nE 'bcmgenet_free_rx_cb|bcmgenet_rx_refill|bcmgenet_desc_rx|bcmgenet_rx_poll|bcmgenet_isr1|rx_bds =' "$GENET"
sed -n '1851,1866p' "$GENET"
sed -n '2206,2440p' "$GENET"
sed -n '3023,3042p' "$GENET"
```

Require the course release; resolve a mismatch through 5.2 before interpreting live counters. The line numbers and names here refer to the [pinned GENET implementation](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/drivers/net/ethernet/broadcom/genet/bcmgenet.c), commit `ae161617d7a4552fa91d03626b8d9f3696d17481`.

`bcmgenet_init_dma` sets `rx_bds = priv->base + rdma_offset`. Each software control block's `bd_addr` points into that mapped controller region. **GENET's descriptor addresses and ring indexes use MMIO; packet buffers and the separately allocated `rx_cbs` bookkeeping live in RAM.** A DMA address written with `dmadesc_set_addr` identifies packet RAM to the controller. It is neither a CPU pointer nor the controller's physical resource address.

`bcmgenet_alloc_rx_buffers` initially fills the ring using `bcmgenet_rx_refill`. Refill allocates an skb, then maps its data with `dma_map_single(..., DMA_FROM_DEVICE)`: the device will write those bytes. While that streaming mapping belongs to the device, the CPU must not treat the bytes as a completed packet. The [DMA ownership rules](https://docs.kernel.org/6.12/core-api/dma-api-howto.html#using-streaming-dma-mappings) explain why a pointer cast, `volatile`, or a delay cannot replace mapping/unmapping and the platform's cache work.

After reception, `bcmgenet_desc_rx` reads `RDMA_PROD_INDEX` and calculates pending completions against `ring->c_index`, with mask-based wraparound. It does not infer completion from an arbitrary buffer byte. For each completed slot, refill **allocates and successfully maps a replacement first**, calls `bcmgenet_free_rx_cb` to unmap the old buffer, then writes the replacement DMA address into the MMIO descriptor. The returned skb contains the old packet; the replacement remains on the ring. Advancing `RDMA_CONS_INDEX` later returns the serviced slot for reuse.

Allocation or mapping failure returns before removing the old skb or mapping. The RX loop counts a drop and advances the consumer anyway, reusing the existing mapped storage for future reception. A failed new mapping frees only the newly allocated skb. This keeps buffer ownership coherent while losing this packet; it does not deliver partially prepared data to Linux. These failures are exposed as `alloc_rx_buff_failed` and `rx_dma_failed` driver counters.

For a successful refill, the old streaming mapping has ended before the CPU examines its contents. In this path the receive length/status comes from a **receive status block in DMA buffer RAM**, through `status_64`, rather than a status read from the descriptor MMIO address. The driver rejects oversized lengths, missing start/end flags and reported receive errors. The flags describe DMA packet boundaries; this rejection is not IPv4 fragment reassembly. It extends the skb to the received length, removes the 64-byte status block and two alignment bytes, and trims an FCS if CRC forwarding was enabled. Checksum metadata can describe hardware checksum work. `eth_type_trans` identifies the Ethernet protocol, statistics advance, and `napi_gro_receive` transfers the skb to the network stack. Error and drop paths also consume poll work.

## Interrupts announce work; NAPI drains it

2. Continue on the **Pi, repository root**:

```sh
sed -n '2711,2755p' "$GENET"
sed -n '3107,3199p' "$GENET"
sed -n '3337,3360p' "$GENET"
```

`bcmgenet_isr1` reads unmasked queue interrupt status and acknowledges it. For an RX queue, it prepares that queue's NAPI instance, disables its RX interrupt and calls `__napi_schedule_irqoff`. This hard IRQ handler schedules processing; it does not run the UDP application. `bcmgenet_isr0` handles other events, including MDIO notification and deferred link work. Both handlers are registered using the interface name, so two identically labelled rows in `/proc/interrupts` need not mean two RX queues.

NAPI is Linux's network event-processing mechanism. Normally its poll callbacks run in softirq context; work may continue in `ksoftirqd` when deferred, and other configurations can use NAPI threads. This is kernel polling of device work. The application's `poll()` waits for socket readiness; it is not a busy loop reading hardware. No socket busy-poll option is enabled here. See the [Linux 6.12 NAPI contract](https://docs.kernel.org/6.12/networking/napi.html).

`bcmgenet_rx_poll` gives its budget to `bcmgenet_desc_rx`, which processes at most that many completed slots. With `work_done < budget`, the pinned callback calls `napi_complete_done` and re-enables the ring interrupt. Returning the full budget leaves NAPI scheduled for another poll, even if the last item happened to empty the ring. Budgeting bounds one turn of RX work so one busy device cannot simply drain an unbounded stream in that callback. A zero RX budget processes no RX slots and does not enter the completion branch.

This masks repeated RX notifications while polling makes progress. Hardware coalescing can also delay a notification until a time/packet threshold; the driver has coalescing and optional dynamic-moderation support. We leave those settings unchanged. Several packets can share an interrupt, one poll can process several packets, and a burst can need several polls. There is no one-packet/one-IRQ invariant.

GRO (generic receive offload) may combine eligible packets or batch their handoff; calling it does not promise that these small UDP messages merge. Linux then dispatches the Ethernet protocol, processes IPv4 and local delivery, checks UDP and selects a socket by its addressing/binding rules. Its socket queue and readiness notification are separate from the NIC ring. When the process is scheduled, `recvfrom()` copies the datagram payload into its userspace array; it does not lend the application a DMA buffer. See the pinned [receive core](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/net/core/dev.c) and [UDP receive/copy implementation](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/net/ipv4/udp.c). Filtering, validation or a full socket queue can still discard a packet after driver reception.

6. After the endpoint exits, on the **Pi, same shell/directory**, take the matching snapshot:

```sh
ip -s link show dev "$IFACE" > "$RX_RECORD/link-after.txt"
ethtool -S "$IFACE" > "$RX_RECORD/driver-after.txt"
cat /proc/interrupts > "$RX_RECORD/irq-after.txt"
cat /proc/softirqs > "$RX_RECORD/softirq-after.txt"
diff -u "$RX_RECORD/link-before.txt" "$RX_RECORD/link-after.txt"
diff -u "$RX_RECORD/driver-before.txt" "$RX_RECORD/driver-after.txt"
diff -u "$RX_RECORD/irq-before.txt" "$RX_RECORD/irq-after.txt"
diff -u "$RX_RECORD/softirq-before.txt" "$RX_RECORD/softirq-after.txt"
```

`diff` exits 1 when files differ; that is expected. Compute after-minus-before for the same fields and sum the same IRQ row across CPU columns. Keep the complete record rather than interpreting only the most convenient counter.

| Record | What it establishes | Limit |
| --- | --- | --- |
| Endpoint sequence records and accepted count | Valid messages reached this process and replies were submitted | A submit is not proof that the Mac received a reply; accepted counts are not unique-sequence counts |
| Sender validated sequence list | Exact request/reply exchanges completed | No DMA or one-way timestamps |
| Interface RX packets/errors/drops | Interface accounting changed during the interval | Includes ARP, broadcasts and other traffic; stages differ from application accounting |
| Driver RX/error/allocation counters | Driver/hardware-specific events were counted | Names and units must be read as reported; no message ID links a delta to one datagram |
| Identified IRQ row deltas | Those interrupts ran on the listed CPUs | Queue IRQs can include TX; coalescing/polling break packet-to-IRQ equality |
| `NET_RX` in `/proc/softirqs` | Per-CPU network receive softirq executions increased | System-wide execution counts, not packet counts; other interfaces also contribute |

Scheduling, other traffic, batching and socket drops explain why these values need not match ten. A low-rate exchange may not exhaust a budget at all. A counter comparison correlates an interval with activity; it is not a timestamp trace of one selected packet.

## Optional: observe an available NAPI tracepoint

7. On the **Pi, repository root**, discover access and format first:

```sh
command -v perf
sudo test -r /sys/kernel/tracing/events/napi/napi_poll/format
sudo cat /sys/kernel/tracing/events/napi/napi_poll/format
```

Proceed only if a compatible `perf` is already available and the event exists. Missing tracing support, an unmounted tracefs or a permission restriction means skip this optional observation; do not switch kernels or change tracing/security settings to complete it. The [pinned event definition](https://github.com/raspberrypi/linux/blob/ae161617d7a4552fa91d03626b8d9f3696d17481/include/trace/events/napi.h) records device name, work and budget, not our UDP sequence.

Repeat the finite exchange while this runs in a separate **Pi terminal, repository root**:

```sh
NAPI_RECORD=$(mktemp -d .build/network-napi-XXXXXX)
sudo perf record -a -e napi:napi_poll -o "$NAPI_RECORD/perf.data" -- sleep 10
sudo perf script -i "$NAPI_RECORD/perf.data"
```

Inspect only events naming the selected interface. Work equal to budget is consistent with another poll being needed; smaller work is consistent with draining that poll's work. Both RX and TX NAPI can name the interface. Absence during this short window does not prove absence of NAPI: confirm overlap, event availability and tool diagnostics. Trace overhead and scheduling affect observations, and these records still do not identify a particular payload or measure its hardware arrival time. This command observes events without changing network configuration or the global ftrace enable controls.

If replies time out, check readiness, bind address, route and actual ingress as in 11.2 before blaming refill. If only another interface's counts rise, the run did not demonstrate wired ingress. Rising allocation/DMA error counters warrant preserving diagnostics; increasing drops alone does not locate the loss. If IRQ rows are missing or access is restricted, record the limit and keep the source walkthrough and available counters.

Stop any still-waiting endpoint/sender with Ctrl-C. Optional recording ends after ten seconds.
