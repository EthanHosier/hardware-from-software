# 10.2 — Verify, troubleshoot, and explain the system

A useful demonstration includes a defined failure and a repeatable recovery. You will restart the application, restart the firmware, run with the data link absent, check malformed-input handling, and detach the driver while the application holds it open. Keep a short record of the scenario, actual diagnostic, exit status and observed LEDs. The expected results below are **predictions, not physical measurements recorded during authoring**.

Complete [10.1](10.1-use-a-linux-device-event-to-control-pico-hardware.md) first. Reuse its complete firmware, driver and clients; no source changes are needed. `verification.json` records Pico compilation, Linux application/module compilation and host parser/PTY tests. It does **not** record a physical capstone run, UART waveform, LED observation or live module teardown.

## Keep one explicit starting state

Keep [10.1's consolidated circuit and schematic](10.1-use-a-linux-device-event-to-control-pico-hardware.md#2-power-down-and-assemble-the-complete-circuit). Both boards use separate USB supplies; the Debug Probe is disconnected. The Pico runs `uart_device`, free of breakpoints. The Pi driver is bound, its udev rule is installed, and `/dev/serial0` resolves to the reserved PL011 `/dev/ttyAMA0`, with Bluetooth and serial consoles disabled as in [7.2](7.2-configure-the-pi-uart-and-test-an-echo.md). Do not run `gpio_events` against the driver's lines.

| Circuit retained | Exact connections |
| --- | --- |
| Pi button | BCM27 physical **13** → switch → GND physical **14**; **4.7 kΩ** pull-up to Pi 3V3 physical **17** |
| Pi LED | BCM17 physical **11** → **1 kΩ** → LED anode; cathode → GND physical **9** |
| Pico button | GP17 physical **22** → switch → GND physical **23**; **4.7 kΩ** pull-up to Pico 3V3(OUT) physical **36** |
| Pico LED | GP16 physical **21** → **1 kΩ** → LED anode; cathode → GND physical **23** |
| Request wire | Pi BCM14 TX physical **8** → Pico GP1 RX physical **2** |
| Reply wire | Pico GP0 TX physical **1** → Pi BCM15 RX physical **10** |
| Reference wire | Pi GND physical **6** ↔ Pico GND physical **8** |

No I²C wires, SPI loopback jumper or inter-board power-rail connections remain. The Pi button drives the integrated demonstration; the Pico button changes only the Pico COUNT value. Retain the switch contact-pair orientation from 10.1. Before **every** inter-board wiring change, shut down the Pi, wait for shutdown, unplug its supply and Pico USB, and confirm both boards are off. Never leave one powered board driving UART into the other unpowered board.

## 1. Demonstrate and restart the client

Release the Pi button and wait half a second. All commands below run in **Pi SSH shells**, working directory **`~/hardware-from-software`**, unless labelled otherwise. If executables are missing, use 10.1's native Pi build; the Mac dependency installer is not a Pi installer.

```sh
cd ~/hardware-from-software
readlink -f /dev/serial0
sudo fuser -v /dev/ttyAMA0
./.build/capstone /dev/mybutton /dev/serial0 2
```

Confirm the expected route and no prior UART owner before launching. Make two slow press/release cycles after launch, observing both LEDs. The process should print two acknowledged forwards and exit successfully. Immediately run `echo $?` to record its status. Illustrative output, with a kernel counter that was already at 10:

```text
button 11 -> 1 OK 1
button 12 -> 2 OK 0
```

The left number belongs to the kernel device lifetime. The right identifier belongs to this application's UART transactions. They need not match. The application checks the kernel record's separator, final LF and exactly one `0` or `1` state byte. It trusts the kernel producer for the sequence prefix; it does **not** parse that prefix as a number. It forwards the supplied LED state rather than inverting it on each read.

Run the same command again. It starts UART IDs at 1 again and waits for a **future** accepted press. Opening `/dev/mybutton` records the current sequence; it supplies no initial snapshot or replay. Presses made while the client was stopped are not replayed. Transactions are sequential, so accepted presses during a slow UART exchange can coalesce into one later latest-state record. The CLI count, **1–1000**, counts successful forwards, not physical presses or the sequence delta.

For signal cleanup, launch another instance with count 2, leave the button released, and press **Ctrl-C** in its foreground shell. It has no custom signal handler: normal SIGINT termination causes Linux to close its descriptors. This is different from the exception path, where the C++ serial owner closes during unwinding. Check `sudo fuser -v /dev/ttyAMA0` afterward. Neither closing path resets either LED or unloads the driver. Do not run `serial_client` or any diagnostic until capstone has exited: the code does not enforce exclusive UART ownership.

## 2. Restart the Pico without powering through UART

A Pico reset starts new firmware state, including `Device.light = false` and COUNT zero. It does not notify or reset the Pi driver's state. If firmware alone restarts while the Pi LED state is 1, the two can disagree until another LED request succeeds. Capstone has no initial synchronization, reconnect loop or state replay.

Use this conservative physical restart experiment rather than pulling Pico USB while UART is connected:

1. Stop capstone and every UART client. On the **Pi**, run `sudo poweroff`; wait for shutdown. Unplug Pi power and Pico USB.
2. With **both boards off**, detach all three inter-board wires. Retain both local button/LED circuits.
3. Connect **only the isolated Pico** to the Mac normally, without holding BOOTSEL. This power cycle restarts the already installed `uart_device`; the external LED should start off. The [Pico 2's BOOTSEL button](https://datasheets.raspberrypi.com/pico/pico-2-datasheet.pdf) selects the USB boot route when used during startup; it is not a firmware reset button. No added RUN switch is assumed.
4. Unplug Pico USB again. With both boards off, restore the three wires from the table, then power both boards and reconnect SSH.
5. Repeat 8.3's matching-module insertion and binding checks: this manual module is not configured to autoload. Verify the recreated node and permissions. Run capstone again and make new slow presses.

This safe procedure also reboots the Pi and creates a new driver lifetime. It checks restart/reassembly, **not** isolated-Pico-reset recovery with a persistent Pi state. A new driver also starts its counter and LED state at zero. Do not present matching initial LEDs here as evidence of automatic resynchronization. The [7.3 firmware source](7.3-build-a-robust-c-serial-client.md) defines reset state; the client cannot infer it from an open UART.

## 3. Fail with the request wire absent, then recover

Stop all clients. Shut down and unplug both boards as above. Remove **only** Pi BCM14 physical 8 → Pico GP1 physical 2, leaving the reply and reference wires. With the missing wire secured away from contacts, power both boards. Reconnect SSH and restore/verify the manually loaded driver after boot.

Run capstone with count 1 and make one new Pi press. Expected: the local Pi LED/state changes, but no valid request should arrive at the Pico and no valid acknowledgement should return. Capstone should exit with `UART deadline expired` and status 1. Its transaction uses a two-second absolute deadline, subject to scheduling; the GPIO UART node generally remains present despite the absent wire. A successful Linux write is not proof of delivery.

The local driver can still accept presses during this UART failure. The Pico LED need not follow them. Without a press, capstone instead reaches its separate 30-second `button timeout/offline` path; that would not test UART failure.

Stop the failed application, shut down and unplug **both** boards, then restore the missing request wire. Power both, verify the driver again, and repeat the count-1 run with a new press. This is manual recovery. There is no hot-wire reconnect or automatic retry. After any ambiguous timeout, a request may already have changed the LED even if its reply was lost. Reopening performs `tcflush`, which discards locally queued bytes at that instant; it cannot remove a future late reply. Because new processes reuse ID 1, establish a fresh known state with the powered-down restart above when stale traffic is possible. IDs supply correlation, not a persistent session, deduplication or a retry guarantee. See [termios queue semantics](https://man7.org/linux/man-pages/man3/termios.3.html).

## 4. Reject malformed input at the right boundary

Stop capstone first. **Pi — checkout root:**

```sh
./.build/serial_client /dev/serial0 LED 2
echo $?
python3 scripts/build_examples.py --host --linux
python3 scripts/test_serial.py
```

The first invocation should print `invalid command` and return 1. It opens/configures the port but validates before transmitting: **it sends no malformed request**. The subsequent tests use host memory and simulated pseudo-terminals, not the physical UART. They repeat [7.3's malformed grammar, forbidden-byte, overflow-recovery and malformed-reply checks](7.3-build-a-robust-c-serial-client.md#what-the-tests-establish).

The shared collector ignores CR anywhere. Other invalid bytes or excessive length discard through LF; a completed malformed firmware frame produces `0 ERR malformed\n` without applying an LED command. An incomplete frame has no response until LF.

Now exercise rejection **over the actual link**. Keep `uart_device` free-running and both boards powered with the complete circuit intact. Confirm every capstone, serial client and terminal has exited; `sudo fuser -v /dev/ttyAMA0` should show no owner. Save this complete diagnostic as **`.build/malformed_uart.py` on the Pi**, from the checkout root. It bypasses the C++ command validator deliberately, sends exactly one malformed LED request, checks the exact error line, then sends a fresh ID-2 PING to check parser recovery:

```python
import os
import select
import sys
import termios
import time
import tty

path = sys.argv[1] if len(sys.argv) == 2 else "/dev/serial0"
fd = os.open(path, os.O_RDWR | os.O_NOCTTY | os.O_NONBLOCK | os.O_CLOEXEC)
saved = None

def exchange(request, expected):
    deadline = time.monotonic() + 2.0
    sent = 0
    received = bytearray()
    while sent < len(request) or b"\n" not in received:
        remaining = deadline - time.monotonic()
        if remaining <= 0:
            raise TimeoutError("UART diagnostic deadline expired")
        try:
            readable, writable, _ = select.select(
                [fd] if sent == len(request) else [],
                [fd] if sent < len(request) else [], [], remaining)
            if writable:
                n = os.write(fd, request[sent:])
                if n <= 0:
                    raise RuntimeError("UART write made no progress")
                sent += n
            if readable:
                chunk = os.read(fd, 64 - len(received))
                if not chunk:
                    raise RuntimeError("UART read made no progress")
                received.extend(chunk)
                if len(received) >= 64:
                    raise RuntimeError("oversized diagnostic reply")
        except (BlockingIOError, InterruptedError):
            continue
    if bytes(received) != expected:
        raise RuntimeError(f"expected {expected!r}, received {bytes(received)!r}")
    print(f"TX {request!r}; RX {bytes(received)!r}", flush=True)

try:
    saved = termios.tcgetattr(fd)
    tty.setraw(fd, when=termios.TCSANOW)
    settings = termios.tcgetattr(fd)
    settings[0] &= ~(termios.IXON | termios.IXOFF | termios.IXANY)
    settings[2] &= ~(termios.CSIZE | termios.PARENB | termios.CSTOPB | termios.CRTSCTS)
    settings[2] |= termios.CS8 | termios.CLOCAL | termios.CREAD
    settings[4] = settings[5] = termios.B115200
    settings[6][termios.VMIN] = 0
    settings[6][termios.VTIME] = 0
    termios.tcsetattr(fd, termios.TCSANOW, settings)
    termios.tcflush(fd, termios.TCIOFLUSH)
    exchange(b"1 LED 2\n", b"0 ERR malformed\n")
    exchange(b"2 PING\n", b"2 OK 1\n")
finally:
    try:
        if saved is not None:
            termios.tcsetattr(fd, termios.TCSANOW, saved)
    finally:
        os.close(fd)
```

**Pi — checkout root:**

```sh
python3 .build/malformed_uart.py /dev/serial0
echo $?
```

Expected, **not physically exercised during authoring**: two TX/RX lines show the exact byte strings above, status is 0, and the invalid LED command does not change the Pico LED. The helper checks complete reply bytes, not just a substring. PING confirms a subsequent valid frame was processed; it does not measure LED current. Each exchange has an absolute two-second deadline shared across partial writes and reads, a bounded receive buffer, and no automatic retry. The finalizer restores saved terminal attributes and closes on success, exception or Ctrl-C. Wait for it to exit before using another UART tool. A timeout or unexpected bytes fails the experiment: restore the known firmware/port state from step 2 before retrying. Queue flushing alone still cannot exclude a later old reply.

## 5. Detach the driver while capstone waits

In **Pi shell B**, first repeat [8.6 step 1's device discovery and identity checks](8.6-make-failure-and-teardown-behaviour-explicit.md#1-establish-exactly-which-device-will-be-detached) to set this shell's `button_device` and `button_matches`. Continue only for the single verified `/hfs_button` node bound to this module. Prepare the following checks before launching the client: its idle poll lasts only 30 seconds.

Release the Pi button. In **Pi shell A — checkout root**, launch your client and print its PID, then wait for its status. Make no presses:

```sh
./.build/capstone /dev/mybutton /dev/serial0 1 &
capstone_pid=$!
printf 'capstone PID: %s\n' "$capstone_pid"
wait "$capstone_pid"
printf 'capstone status: %s\n' "$?"
```

In **shell B — checkout root**, enter that printed PID when prompted. Verify the executable and **both open device descriptors** before unbinding. Launching a process alone does not establish that it reached either open. The flags below describe descriptor identity, not proof of the precise instruction where the scheduler stopped it:

```sh
read -r -p 'PID printed by shell A: ' capstone_pid
(
    set -eu
    case "$capstone_pid" in ''|*[!0-9]*) exit 1 ;; esac
    kill -0 "$capstone_pid"
    test "$(readlink -f "/proc/$capstone_pid/exe")" = "$PWD/.build/capstone"
    button_open=0
    uart_open=0
    for descriptor in /proc/"$capstone_pid"/fd/*; do
        target=$(readlink -f "$descriptor")
        case "$target" in
            /dev/mybutton) button_open=1 ;;
            /dev/ttyAMA0) uart_open=1 ;;
        esac
    done
    test "$button_open" -eq 1
    test "$uart_open" -eq 1
    kill -0 "$capstone_pid"
    test "$button_matches" -eq 1
    test "$(readlink -f "$button_device/of_node")" = /sys/firmware/devicetree/base/hfs_button
    test "$(tr '\0' '\n' < "$button_device/of_node/compatible")" = hfs,mybutton
    test "$(readlink -f "$button_device/driver")" = /sys/bus/platform/drivers/hfs-mybutton
    test "$(readlink -f "$button_device/driver/module")" = /sys/module/mybutton
    printf '%s\n' "${button_device##*/}" | sudo tee /sys/bus/platform/drivers/hfs-mybutton/unbind
    test ! -e "$button_device/driver"
    test ! -e /sys/class/misc/mybutton
)
```

If a guard fails, do not unbind: inspect shell A, let that client finish, and rerun with a fresh PID. After verified opens and successful unbind, shell A should promptly report `button timeout/offline`, return 1 and close both descriptors. There remains a scheduling race between inspection and removal; the client need not already be asleep in poll. If launch/open raced removal, an open error instead does not demonstrate a waiter being woken. The identical text also describes idle timeout, so correlate it with shell B's verified detach and elapsed wait. Unbind makes poll report error/hangup; an existing descriptor stays attached to the **old offline object**, even after rebind. The retained reference protects its allocation, not released GPIO resources, following the [Linux 6.12 kref rules](https://www.kernel.org/doc/html/v6.12/core-api/kref.html). Use 8.6's bounded helper if you want to observe ENODEV and both poll flags directly. Do not force `rmmod` to simulate removal.

After shell A exits, use [8.6's guarded bind command](8.6-make-failure-and-teardown-behaviour-explicit.md#4-detach-with-a-descriptor-still-open) in shell B for that same verified device. Check `/dev/mybutton` and its permissions, release the button, wait half a second, then launch a **new** capstone and press. Rebind starts a new sequence and Pi LED state; the Pico retains its last command until a new one succeeds.

## Read a failure as a boundary

| Scenario/check | Expected result | Recovery or next check |
| --- | --- | --- |
| Restart client, no new press | Silent wait; no replay or initial LED command | Make a future slow press; idle eventually times out |
| Pi LED changes, UART deadline | Local driver worked; remote result unconfirmed | Stop client; verify firmware/owner; both off before wiring inspection |
| Reply accepted, Pico LED dark | Firmware acknowledged software state | Both off: check GP16, resistor, LED polarity and ground |
| Invalid CLI LED value / raw malformed frame | Local rejection / exact firmware error, then valid PING | Check each distinct boundary; stop owners before raw diagnostic |
| Verified unbind during wait | Error/offline exit, old open unusable | Guarded rebind; verify node; start new process |
| Unexpected ID or reply after timeout | Competing owner, wrong image or stale traffic possible | Stop all owners; establish fresh firmware/port state |

## Explain what each layer supplied

SSH brings commands and output between Mac and Pi; it is not the UART transport. A Pi button transition reaches the GPIO controller and Linux IRQ machinery. The threaded handler schedules delayed work. The worker samples the logical active-low input, increments the accepted-press counter and toggles protected LED state; it requests the Pi GPIO output and wakes readers. Poll/read supplies one latest-state record to capstone. Capstone validates the state field, sends an identified LED command through Linux's TTY/PL011 path, and checks its acknowledgement.

UART framing turns the waveform back into bytes at the Pico. Firmware polling collects an LF-terminated request, parses it and calls `Device::led`. The pinned RP2350 Arm SDK's `gpio_put` path uses the GPIO coprocessor instruction to update SIO output hardware, as [7.4's disassembly trace](7.4-trace-a-command-end-to-end.md#4-identify-the-actual-output-instruction-offline) and the [SDK implementation](https://github.com/raspberrypi/pico-sdk/blob/079c6f39023649b154152db30f1d781e884879bc/src/rp2_common/hardware_gpio/include/hardware/gpio_coproc.h) show. It is not necessarily the explicit MMIO store from Chapter 2. Mux, pad and output-driver configuration carry the latch state to GP16; the external circuit determines whether light is produced. The reply confirms applied software state, not measured voltage/current or elapsed wire time.

For the next experiment, choose the layer that interested you: [Chapter 3](3.1-attach-the-debug-probe-over-swd.md) for execution evidence, [Chapter 9](9.3-trace-a-real-kernel-mmio-mapping.md) for Linux register ownership, [Appendix D](appendix-d.md) for optional wire timing, or [Appendix F](appendix-f.md) for DMA, PIO, multicore and Rust directions.

Finish with the driver bound, both circuits intact, no clients open, and a successful fresh-press demonstration. That is a usable known state, although the last LED values remain. To pack away instead, close clients, follow [8.3's module/boot-overlay cleanup](8.3-describe-the-device-and-bind-the-driver.md#troubleshooting-and-next-state) and [8.5's lesson-rule cleanup](8.5-expose-dev-mybutton-to-a-c-client.md#diagnose-and-leave-a-known-state) if abandoning the driver. Retain unrelated configuration. Shut down the Pi, wait, unplug **both supplies**, then detach inter-board wires. With boards separated, [7.2's recorded rollback](7.2-configure-the-pi-uart-and-test-an-echo.md#diagnose-and-leave-the-next-state) restores UART/Bluetooth configuration if desired. Never reboot a lone powered Pi while it remains wired to an unpowered Pico.
