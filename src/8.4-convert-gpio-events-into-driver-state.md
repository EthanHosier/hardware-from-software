# 8.4 — Convert GPIO events into driver state

A button edge is a notification that something changed. The driver must decide whether that change represents a new press before updating its counter. You will trace that decision through the complete driver already bound in [8.3](8.3-describe-the-device-and-bind-the-driver.md), then observe its effect on the **Pi LED**. No replacement module or new wiring is needed.

Keep 8.3's successful binding and exclusive GPIO requests. The Pico stays unplugged and separate, with all inter-board UART/I²C wires and debug connections absent. Retain this Pi-only circuit; its [wiring procedure](8.1-establish-a-userspace-gpio-baseline.md#1-separate-the-boards-and-build-the-pi-circuit) identifies the switch's two contact groups. Power down before changing wires.

The driver was source-reviewed and compiled against official **6.12.96+rpt-rpi-v8** headers; the overlay was separately compiled with `dtc`. Physical Pi execution, debounce behaviour and LED operation have **not been exercised during authoring**. All bench observations below are expected results, not measured traces.

## 1. Follow the descriptor to the IRQ

The complete source remains `examples/kernel/mybutton.c`. Read `hfs_probe`, `hfs_irq` and `hfs_debounce` first; the device-file operations are explained in 8.5.

```c
{{#include ../examples/kernel/mybutton.c}}
```

`GPIOD_IN` has already made `b->button` an input. `gpiod_to_irq(b->button)` obtains its Linux IRQ number, or a negative errno on failure. The driver checks that result before requesting interrupt handling. Mapping a descriptor does not install our callback; `devm_request_threaded_irq` does that next. See the [GPIO-to-IRQ contract](https://www.kernel.org/doc/html/v6.12/driver-api/gpio/consumer.html#gpios-mapped-to-irqs).

Do not replace the returned value with **27** or **13**. Physical header contact 13 carries BCM27. An interrupt controller's **hardware IRQ number**, or `hwirq`, identifies a source within that controller's IRQ domain. The allocated **Linux IRQ number** identifies the mapping used by Linux's IRQ APIs. These number spaces have different meanings, even when two numbers happen to match. The kernel's [IRQ-domain explanation](https://www.kernel.org/doc/html/v6.12/core-api/irq/irq-domain.html) describes that translation.

The request passes `NULL` as its primary handler and `hfs_irq` as its thread function. Linux supplies a default primary handler that wakes the IRQ thread. Thus, despite its name, **our `hfs_irq` executes in a kernel thread**, not in hard interrupt context. `b` is the callback cookie supplied as `data`; `"hfs-mybutton"` identifies the registered action. Initialisation of the lock, work item and state precedes this request because interrupts may arrive as soon as handling is enabled.

`IRQF_TRIGGER_RISING | IRQF_TRIGGER_FALLING` requests both **physical** edges. The active-low descriptor translates a later value read: wire low becomes logical 1, meaning pressed. It does not turn these IRQ flags into the logical-edge flags of 8.1's userspace GPIO API. A press normally causes a physical falling edge; release causes rising. Release notification matters: the worker must record `pressed=false` before it can accept another transition to `true`.

`IRQF_ONESHOT` keeps this IRQ masked while the thread callback runs. It does **not** keep it masked throughout the later 20 ms delay or the work callback. See [threaded IRQ requests and flags](https://www.kernel.org/doc/html/v6.12/core-api/genericirq.html#c.request_threaded_irq).

## 2. Separate notification, sampling and publication

`hfs_irq` only calls `mod_delayed_work(system_wq, ..., msecs_to_jiffies(20))`, then returns `IRQ_HANDLED`. When idle, that queues delayed work; for pending delayed work, it moves the timer expiry. Repeated callbacks normally push sampling later. `msecs_to_jiffies` expresses the delay in kernel timer ticks. Expiry makes work eligible to run; it does not promise execution at an exact wall-clock instant. This is the [workqueue API's delay model](https://www.kernel.org/doc/html/v6.12/core-api/workqueue.html#c.mod_delayed_work).

This design filters activity by taking **one later logical-level sample**. It does not prove the contact was continuously stable for 20 ms. IRQ-thread scheduling can lag the physical edge, and worker scheduling adds delay. A press and release between samples can disappear entirely. Bounce lasting beyond the window can still cause extra accepted changes. If work is already running when a new IRQ thread reschedules it, that call does not rewind the running callback or invalidate the sample it has taken; another execution can follow. Treat the counter as accepted sampled presses, not a lossless physical-event instrument.

The contexts determine which operations belong where:

| Execution context | Role here | Sleeping rule |
| --- | --- | --- |
| Hard IRQ | Controller/IRQ core handles the interrupt and wakes the thread | Cannot sleep |
| IRQ thread, `hfs_irq` | Reschedules debounce work | Can generally sleep, but this callback only reschedules |
| Threaded `system_wq` worker, `hfs_debounce` | Reads GPIO, updates state, writes LED and wakes readers | May sleep outside atomic critical sections |
| Calling process in `hfs_read` | Obtains published state for userspace | May sleep where the API permits |

The `*_cansleep` GPIO accessors support controllers whose access might need a sleeping transaction. They do not necessarily sleep on every controller. Our worker reads with `gpiod_get_value_cansleep` **before** taking the spinlock and writes with `gpiod_set_value_cansleep` **after** releasing it. The [descriptor documentation](https://www.kernel.org/doc/html/v6.12/driver-api/gpio/consumer.html#gpio-access-that-may-sleep) requires a sleepable context for these accesses. Moving either inside the spinlocked section would violate that rule.

Under `b->lock`, the worker compares the sample with `b->pressed`. A negative GPIO-read result returns before changing state. For a successful sample, the transitions are:

| Stored state → sample | State update |
| --- | --- |
| Released → pressed | Store pressed; increment `sequence`; invert `light`; arrange notification |
| Pressed → released | Store released; leave counter and light unchanged |
| Unchanged | Leave counter and light unchanged |

`kzalloc` initially supplies zero counter and light values. Probe samples the initial input into `b->pressed`; loading while held therefore produces **no initial press event**. Release and allow that release to be sampled before pressing again.

The spinlock makes the compound state update indivisible with respect to other code taking the same lock, including reader snapshots and removal's `online` change. On the ordinary non-RT kernel route, `spin_lock_irqsave` also saves and disables local interrupts until restore; the lock supplies exclusion across CPUs. Keep this region brief and non-sleeping. `volatile` would supply neither that exclusion nor a consistent counter/light snapshot. See [Linux's locking lesson](https://www.kernel.org/doc/html/v6.12/locking/spinlocks.html).

The worker copies `light` locally, unlocks, then applies the LED value and wakes waiters only for an accepted press. The locked state publication and physical LED write are separate operations: a reader can observe the new state before the output write completes. There is no per-edge `printk` flood. `sequence` records accepted presses; the later interface exposes the latest counter/state, rather than queuing every transition.

`online` prevents the worker from accepting a new change after removal marks the device offline. It does not by itself keep memory or descriptors alive. Removal also stops the IRQ, synchronously cancels work, and only then requests LED-low and drops its reference. The post-IRQ probe-error path likewise stops IRQ/work before LED-low and freeing state. [8.6](8.6-make-failure-and-teardown-behaviour-explicit.md) examines these lifetime boundaries.

## 3. Observe the bound driver

**Pi — SSH shell, working directory `~/hardware-from-software`:**

```sh
cd ~/hardware-from-software
lsmod | awk '$1 == "mybutton" { print }'
ls -l /sys/class/misc/mybutton /dev/mybutton
```

Repeat [8.3's platform-device discovery and binding checks](8.3-describe-the-device-and-bind-the-driver.md#5-verify-the-device-then-load-and-verify-binding). Confirm the discovered device's driver resolves to `hfs-mybutton` and its module to `mybutton`. If binding was lost through reboot or removal, repeat 8.3's matching-header build, explicit load and verification procedure. Do not insert a second copy or reload merely to follow this page. Do not run `gpio_events` against the driver's owned lines.

Release the button and wait about half a second. Note the current LED state; it need not be off if you already pressed it in 8.3. Press, hold for roughly a second, release, and wait another half second. Repeat slowly. Expected behaviour is one toggle on each accepted press, no repeated toggles while held, and no toggle on release. The generous intervals let release sampling occur; they are not a latency measurement. For example, starting off, successive accepted presses should yield on, off, on. The counter should advance once for each of those accepted transitions; 8.5 introduces the client that reads it.

You can inspect interrupt delivery separately, on the **Pi in the same directory**:

```sh
awk 'NR == 1 || /hfs-mybutton/' /proc/interrupts
```

Locate exactly one registered action named `hfs-mybutton`; do not guess a row from a GPIO number. Its leftmost IRQ number is the Linux IRQ allocated for this boot/binding, and the CPU columns count interrupt handling. Read the row before and after a slow press/release. Counts should increase, but need not increase by exactly two: bounce, masking and controller behaviour affect delivery. An absent or ambiguous row needs investigation before drawing conclusions. These are IRQ statistics, **not `b->sequence`**; this module adds no proc or sysfs counter file.

## Diagnose and leave the next state

| Symptom | Check |
| --- | --- |
| No action row or device node | Recheck actual binding and new kernel errors using 8.3; module presence alone is insufficient. |
| IRQ counts change but LED does not | Release long enough for a sample, then press slowly. Check Pi LED polarity, series resistor and ground with power removed before touching wires. IRQ delivery does not prove a valid GPIO sample or working output circuit. |
| One toggle, then later presses do nothing | The worker may never have sampled release. Check switch contact groups, external pull-up and adequate release interval. |
| Extra toggles or missed quick presses | The sampling filter's limits apply. Return to slow actions; no exact debounce guarantee follows from the 20 ms constant. |
| Kernel reports sleeping in atomic context | Compare the complete source and build artifact; GPIO accesses must remain outside the spinlock. Stop the experiment and investigate before continuing. |

Leave the module bound, overlay enabled, circuit unchanged and Pico unplugged for [8.5](8.5-expose-dev-mybutton-to-a-c-client.md). No log watcher or userspace GPIO requester is needed. To stop instead, use [8.3's module-removal and overlay-disable procedure](8.3-describe-the-device-and-bind-the-driver.md#troubleshooting-and-next-state): close clients, remove only your module, edit only the lesson's overlay directive, reboot, and verify ownership. Do not use runtime overlay removal for this firmware-applied tree. Module removal requests LED-low before releasing GPIOs; released lines have no permanent electrical-level guarantee.
