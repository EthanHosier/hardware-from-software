# 5.2 — Verify the Linux development environment

You can already reach the Pi through SSH from [5.1](5.1-prepare-raspberry-pi-os-and-ssh.md). Now identify the machine behind that shell, install its development tools, and run a C++ program on it. The result is a saved environment record and a native Linux executable.

Keep the Pi powered through its USB-C supply, with its network connection and microSD card in place. Its GPIO header remains unwired. Keep the Pico's existing LED/button circuit intact, separate and unplugged, as left in 5.1. There are no Pi–Pico signal or power connections in this lesson.

## One Arm processor family, different execution environments

The Mac, Pi 4, and Pico 2 all have Arm processors, but their programs are not interchangeable. The Mac compiler normally produces macOS executables. The `arm-none-eabi-g++` installed for the Pico produces embedded firmware. Here, the Pi's distribution-provided `g++` produces a Linux application for the Pi itself: a **native build**.

Linux loads that application as a process, supplies its standard output, and reclaims its resources when it exits. There is no BOOTSEL operation, UF2 copy, or replacement of the running operating system. A later kernel module is a third case: code built for the running kernel's internal interfaces, using the kernel's build system.

## Record the machine

1. In the **Pi SSH shell**, start in your home directory and create a uniquely named record. Keep this shell open so that `env_record` remains available for later commands.

```sh
cd ~
env_record=$(mktemp "$HOME/linux-environment.XXXXXX.txt")
{
    date -Is
    printf 'Board: '
    tr -d '\000' < /proc/device-tree/model
    printf '\n'
    cat /etc/os-release
    uname -m
    uname -r
    dpkg --print-architecture
    free -h
    grep '^MemTotal:' /proc/meminfo
    df -h / /boot/firmware
} | tee "$env_record"
printf 'Record saved in %s\n' "$env_record"
```

The model should identify a Raspberry Pi 4 Model B, including its revision. For this book's 64-bit route, expect `aarch64` from `uname -m` and `arm64` from `dpkg`: the kernel and Debian package tools use different names for the same architecture. Check both; a 64-bit kernel alone does not establish that the installed userspace is 64-bit.

Read the actual memory result rather than assuming a “3GB Pi”. `MemTotal` is memory available to Linux after reservations; `free` also distinguishes memory currently used, available, and used for caches. Neither is a label printed on the RAM package. Unexpectedly low capacity is a reason to check the board identification and configuration, not to infer a new Pi model.

`/etc/os-release` identifies the distribution, such as Debian 12 Bookworm underneath Raspberry Pi OS. `uname -r` identifies the **kernel currently running**. Package updates can install a newer kernel while the old one continues running until reboot. The two version numbers answer different questions.

For a fresh card, the book selects Raspberry Pi OS **Legacy Lite, 64-bit, Bookworm**. On 11 November 2026, the [official download listing](https://www.raspberrypi.com/software/operating-systems/) offers the 6 October 2026 image with a 6.12 kernel; current Trixie Lite has 6.18. An existing compatible 64-bit card need not be erased. Trixie is usable for this native application lesson, but its kernel modules have not been validated by this book. The recorded module compilation baseline is `6.12.96+rpt-rpi-v8`; an image or later APT update need not have that exact patch version. Keep your measured record rather than copying the baseline into it.

2. Inspect the boot layout, still on the **Pi**, from `~`:

```sh
findmnt /boot/firmware
ls -l /boot/firmware/config.txt /boot/firmware/cmdline.txt
```

Bookworm and current Raspberry Pi OS mount the boot partition at `/boot/firmware`. Firmware reads `config.txt` before Linux starts; `cmdline.txt` supplies kernel command-line arguments. These files matter when we enable buses later. Do not edit them now. An older guide's `/boot/config.txt` may refer to a different layout; establish the real mount and files before following such instructions. See the [official configuration-file documentation](https://www.raspberrypi.com/documentation/computers/config_txt.html).

## Install the native tools

3. On the **Pi**, working directory `~`, install the distribution packages:

```sh
sudo apt update
sudo apt install build-essential git file
command -v gcc g++ make git
gcc --version
g++ --version
g++ -dumpmachine
make --version
```

Review APT's proposed changes before accepting. `apt update` refreshes the package index; it does not itself upgrade installed packages. Debian's [`build-essential`](https://packages.debian.org/bookworm/build-essential) brings in GCC, G++, Make, and C library development files. G++ supplies the C++ headers and links the C++ runtime. Git retrieves the examples; `file` identifies the result. There is no need to install the Pico SDK or the Mac's pinned embedded toolchain on the Pi for this program.

Expect a Linux AArch64 compiler target such as `aarch64-linux-gnu`. Record the installed versions, rather than requiring a particular GCC patch release:

```sh
{
    command -v gcc g++ make git
    gcc --version
    g++ --version
    g++ -dumpmachine
    dpkg-query -W build-essential gcc g++ make git file
} | tee -a "$env_record"
```

## Get and build the complete program

4. On the **Pi**, from `~`, clone the public examples repository if this location is unused:

```sh
cd ~
git clone https://github.com/EthanHosier/hardware-from-software.git hardware-from-software
cd ~/hardware-from-software
```

If `~/hardware-from-software` already exists, skip the clone. Inspect that directory and reuse your existing checkout if it contains `examples/linux/hello.cpp`; do not delete it or reset local changes. As an alternative, download the [example archive](downloads/hardware-examples.zip), extract it into a new directory, and use that extraction root as your working directory. The archive contains an `examples` directory directly, without an extra repository wrapper. The remaining commands assume the root is `~/hardware-from-software`.

The complete file `examples/linux/hello.cpp` is:

```cpp
{{#include ../examples/linux/hello.cpp}}
```

5. Build and run on the **Pi**, from `~/hardware-from-software`:

```sh
cd ~/hardware-from-software
mkdir -p .build
g++ -std=c++20 -Wall -Wextra -Wpedantic -O2 examples/linux/hello.cpp -o .build/hello
./.build/hello
printf 'Exit status: %s\n' "$?"
file .build/hello
ldd .build/hello
```

Expected application output, shown for illustration rather than as a captured Pi session:

```text
Linux userspace C++ is running
Exit status: 0
```

`-std=c++20` selects the language version; the three warning options enable useful diagnostics; `-O2` enables optimisation; `-o` names the executable. Using `g++` for the link step also selects the C++ runtime libraries.

`file` should describe a 64-bit AArch64 ELF executable. It may also say PIE, meaning a position-independent executable. ELF is a container format also used by our Pico debug binaries; its presence alone does not mean two executables share a target environment. `ldd` shows the shared libraries resolved by the Pi's dynamic loader, including the C++ runtime. Run it only on this program you just built. Library paths and addresses vary.

The SSH connection carries terminal input and output. The compiler and executable both run on the Pi; the Mac merely displays their output. No GPIO changes should occur. This verifies compiler, C++ headers, linking, loader, and a userspace execution path, not access to any hardware peripheral.

## Check the future kernel-build prerequisite

The kernel development headers are separate from the C++ standard-library headers. External modules require configuration and generated build files matching their target kernel, as described by [Linux kbuild](https://www.kernel.org/doc/html/latest/kbuild/modules.html). Installing a C++ compiler does not establish this match.

6. On the **Pi**, from `~/hardware-from-software`, install the exact running-kernel headers from its configured official package repositories:

```sh
sudo apt install "linux-headers-$(uname -r)"
ls -ld "/lib/modules/$(uname -r)/build"
readlink -f "/lib/modules/$(uname -r)/build"
make -s -C "/lib/modules/$(uname -r)/build" kernelrelease
```

The `build` path normally resolves to an installed header tree under `/usr/src`. The final command should report the same complete release string as `uname -r`, including the Pi flavour suffix. Save these results by appending them to your environment record if desired. This is a readiness check; do not build or load a module in this lesson.

If the exact package is unavailable, see the recovery below. Raspberry Pi documents [`linux-headers-rpi-v8`](https://www.raspberrypi.com/documentation/computers/linux_kernel.html#kernel-headers) as the 64-bit header metapackage. A metapackage tracks repository updates; its presence does not prove the currently booted kernel has matching headers. Chapter 8 repeats this check immediately before a module build. The book has compiled its modules against the recorded 6.12.96 headers in hosted native Arm64 CI; it has not booted this Pi, tested SSH here, or loaded those modules on physical hardware.

## Troubleshooting and next state

| Symptom | Check and correction |
| --- | --- |
| `g++: command not found`, or missing `iostream` | Confirm you are in the Pi SSH shell, then check that `apt install build-essential` completed successfully. An embedded compiler is not a substitute. |
| Compiler target contains `none-eabi`, or `file` reports macOS/another architecture | Inspect `command -v g++` and `g++ -dumpmachine`. Use `/usr/bin/g++` on the Pi after installing its packages, then rebuild. Do not copy a Mac executable over the result. |
| `uname -m` is `armv7l`, or `dpkg` reports `armhf` | You are outside the selected 64-bit route. Preserve any work and return to 5.1 to choose an appropriate card before the later module labs. |
| Source file not found | Run `pwd` and `ls examples/linux/hello.cpp`. Build from the repository or archive root, not from `examples/linux`. |
| Permission denied while compiling or running | Keep the checkout and `.build` under your own home directory and inspect `ls -ld . .build`. Build without `sudo`; do not solve this with `chmod 777`. If a mount forbids execution, use a user-owned directory on the normal root filesystem. |
| Exact kernel headers unavailable, broken `build` link, or differing release strings | Check `uname -r` against the installed package versions. For the standard Pi 4 64-bit route, use `sudo apt install linux-image-rpi-v8 linux-headers-rpi-v8` on the Pi to install the [official repository's](https://archive.raspberrypi.com/debian/pool/main/l/linux/) matching pair, review APT's changes, then `sudo reboot`. SSH disconnects; reconnect as in 5.1 and repeat the machine/header checks. Never point the link at unrelated headers. If packages still do not match, defer Chapter 8 and resolve the package/kernel combination first. |
| APT fails to download packages | Restore networking and check free space before retrying. Keep the existing repositories for your OS release; do not add a different Debian release to obtain one missing package. |

Keep the environment record and source checkout for later lessons. The executable exits on its own; there is no process or module to stop. To remove just this generated executable, run `rm .build/hello` on the **Pi** from `~/hardware-from-software`; rebuilding recreates it. Leave development packages installed and the Pi header unwired. Continue to [5.3 — Establish GPIO identity and ownership](5.3-establish-gpio-identity-and-ownership.md), where we inspect the GPIO controller without assuming its device number.
