# 13.4 Redirect a lab flow into AF_XDP receive buffers

You will receive the numbered lab requests through an AF_XDP socket while an ordinary UDP endpoint waits for those same requests. The AF_XDP receiver does not reply. After it detaches, a new request reaches the waiting endpoint and gets its normal reply. This comparison distinguishes redirection from passive capture.

Complete [13.3](13.3-verify-af-xdp-memory.md) first. Keep the Pi on the same `6.12.96-hfs1-v8` kernel established in [5.2](5.2-verify-the-linux-development-environment.md), with AF_XDP enabled. Keep the Pico and inter-board wires disconnected; existing GPIO wiring needs no changes. All commands below run on the Pi over the private namespace link, never on a physical Ethernet or management interface. macOS cannot run these Linux socket/BPF operations. An explicitly selected Linux test host can exercise the software path, but does not establish Pi boot, PHY or GENET DMA behavior.

## Match the queue before publishing the socket

An AF_XDP socket binds to an interface **and RX queue**. An XSKMAP entry identifies a socket; it does not steer traffic into that socket's queue. Linux checks the device/queue match on delivery. A mismatched target can lose the packet. See the [kernel AF_XDP description](https://docs.kernel.org/6.12/networking/af_xdp.html#concepts).

This example deliberately supports one discovered queue, `rx-0`. `require_single_receive_queue` enumerates `/sys/class/net/INTERFACE/queues` and refuses anything except exactly one `rx-0`. The helper creates both veth peers with one RX queue. We therefore cover every possible ingress queue with socket queue 0 and map key 0, rather than treating an arbitrary multiqueue device as queue 0. A multiqueue application would need matching sockets/map entries and an explicit steering policy; this program stops instead.

Construction follows a useful order: allocate/register UMEM, create and bind the socket, check its actual mode, publish free chunks to FILL, load the classifier, insert the ready socket into `sockets[0]`, then attach. Libxdp's automatic program loading is inhibited so that only our checked classifier controls redirection. Generic attachment uses `XDP_FLAGS_SKB_MODE`; binding explicitly requests `XDP_COPY | XDP_USE_NEED_WAKEUP`. `getsockopt(XDP_OPTIONS)` must succeed and report no `XDP_OPTIONS_ZEROCOPY` flag before `READY` can print. The printed `copy=1` therefore follows an actual socket check. The [kernel implementation](https://github.com/torvalds/linux/blob/v6.12/net/xdp/xsk.c) supplies this option and performs the copy into UMEM.

The classifier retains [13.2's](13.2-selective-generic-xdp.md) narrow policy: untagged, unfragmented IPv4 with a 20-byte header, UDP destination 40420, exact UDP/message lengths and `HFS` version 1. ARP and unsupported or truncated layouts pass. These checks select a layout and marker; the receive-only path does not validate IP/UDP checksums. For redirect mode, a queue-0 map lookup must find a socket; otherwise the program counts PASS. `bpf_redirect_map` also specifies `XDP_PASS` as its lookup-failure fallback. This fallback does not promise recovery from a present but unusable socket or an exhausted pool.

## A chunk has one owner

UMEM is this application's registered memory pool: by default 64 chunks of 4096 bytes, or 256 KiB. Ring entries carry offsets into that pool, not application pointers or hardware DMA descriptors.

![Conceptual receive-only ownership: application submits a free chunk offset through FILL; the kernel copies selected bytes into it and publishes an RX descriptor; the application decodes it, releases the RX entry and recycles the chunk. Nonselected packets follow the ordinary stack.](assets/13.4-fill-rx-ownership.svg)

`replenish` reserves a FILL slot, writes a free chunk's offset, then submits it. The application must leave that chunk alone until an RX descriptor returns it. `packet` checks that the descriptor fits UMEM and one chunk, and that the chunk was FILL-owned, before making it application-owned. The receiver decodes and logs the sequence, marks the chunk free, releases consumed RX entries and later republishes free chunks. Releasing an RX **descriptor slot** alone does not provide a new receive buffer: the chunk must return through FILL.

The invariant is that each chunk is in exactly one ownership state. The checks reject double FILL submission, an unexpected RX chunk and recycling a TX-owned chunk. The shared implementation also contains TX/COMPLETION code for [13.5](13.5-af-xdp-transmit-completion.md); `xsk_receiver` selects `reply=false`, so it submits no TX frames.

The single application thread uses libxdp's `reserve`/`submit` and `peek`/`release` helpers. These implement acquire/release access to shared indexes; publishing an index before its entry is ready would expose incomplete work. Do not replace them with ordinary integer stores or `volatile`. See the [maintained helper implementations](https://github.com/xdp-project/xdp-tools/blob/v1.3.1/headers/xdp/xsk.h).

`XDP_USE_NEED_WAKEUP` permits the kernel to request a syscall before progress resumes. In particular, RX refill may require `poll`; it is not enough to publish FILL entries and wait forever. This receiver calls bounded `poll` whenever no RX entries are available, after attempting refill. It does not claim a syscall-free receive path. The [need-wakeup contract](https://docs.kernel.org/6.12/networking/af_xdp.html#xdp-use-need-wakeup-bind-flag) explains the FILL and TX flags.

## Compare redirect with ordinary delivery

1. **Pi terminal A — checkout root**, build and inspect the private lab:

```sh
cd ~/hardware-from-software
uname -r
python3 scripts/build_network.py
sudo python3 scripts/network_lab.py setup
sudo python3 scripts/network_lab.py show
sudo ip netns exec hfs-lab ls /sys/class/net/hfs-peer/queues
```

Require the course release on the Pi. Package prerequisites are in [13.3](13.3-verify-af-xdp-memory.md). If the lab already exists, use `show` instead of `setup`; collision refusal is intentional. Confirm the only receive queue is `rx-0` (`tx-0` is separate). The helper owns `hfs-host` at `198.18.0.1/30` and `hfs-peer` at `198.18.0.2/30` inside `hfs-lab`. It disables TX checksum offload only on these disposable peers and changes no default route. Stop any previous XDP controller before continuing.

2. **Pi terminal A — checkout root**, start the receiver and wait for its flushed `READY` line:

```sh
sudo ip netns exec hfs-lab .build/network/xsk_receiver hfs-peer 3 30
```

3. **Pi terminal B — checkout root**, start the ordinary endpoint from [11.2](11.2-send-numbered-udp.md) and wait for its `ready` record:

```sh
cd ~/hardware-from-software
sudo ip netns exec hfs-lab .build/network/udp_endpoint 198.18.0.2 40420 1 45
```

4. **Pi terminal C — checkout root**, send promptly after both are ready:

```sh
cd ~/hardware-from-software
python3 examples/network/udp_sender.py 198.18.0.2 --count 3 --timeout 0.25 --interval 0.02 --expect-timeout
```

The intended observation is receiver sequences 1, 2, 3, no ordinary endpoint reply records, and three sender timeouts. The receiver prints `READY mode=generic copy=1 queue=0 frames=64`, then its sequence and final counter records. These are expectations, not a measured Pi transcript. Compare actual sequence sets: `received` is a count, not a duplicate detector. The receiver finishes at its target count, although a batch can take the count above the target. It prints `transmitted=0 pending=0` for this receive-only path.

5. Wait for terminal A to return to its prompt. **Pi terminal C — checkout root**, inspect attachment state and send one new request while terminal B still waits:

```sh
sudo ip netns exec hfs-lab ip -details link show dev hfs-peer
python3 examples/network/udp_sender.py 198.18.0.2 --count 1 --timeout 0.25 --interval 0.02
```

There should be no XDP attachment, and the ordinary endpoint should now accept one request and exit. A fresh sender starts again at sequence 1. Its validated reply, together with the earlier AF_XDP sequences and absence of earlier endpoint replies, establishes the path change more strongly than timeouts alone. If the endpoint's 45-second lifetime elapsed while you read, restart it before this final sender.

Generic XDP still runs in Linux after an SKB exists, and copy mode still copies packet bytes. Selected redirected frames bypass ordinary IP/UDP delivery; unrelated passed traffic continues through Linux. This experiment establishes neither hardware zero-copy nor a performance improvement.

## Exhaust FILL without corrupting ownership

6. After the endpoint and first receiver have exited, **Pi terminal A — checkout root**, start a small-pool run:

```sh
sudo ip netns exec hfs-lab .build/network/xsk_receiver hfs-peer 16 8 500 8
```

The arguments are `COUNT TIMEOUT_SECONDS STARVE_MS FRAMES`. Here the pool has eight chunks and refill is withheld until 500 ms after the receiver's `READY` time. Initial FILL publication still happens during construction. Consumed chunks become free but stay off FILL during that interval. The receiver continues observing RX; it never obtains extra capacity by republishing a kernel-owned chunk.

7. **Pi terminal C — checkout root**, run this finite burst immediately when `READY` appears. It mirrors the integration test's sequence ranges, delay and recovery pacing:

```sh
python3 - <<'PY'
import socket
import struct
import time

with socket.socket(socket.AF_INET, socket.SOCK_DGRAM) as burst:
    for sequence in range(1, 65):
        burst.sendto(struct.pack('!3sBI', b'HFS', 1, sequence), ('198.18.0.2', 40420))
    time.sleep(0.8)
    for sequence in range(65, 97):
        burst.sendto(struct.pack('!3sBI', b'HFS', 1, sequence), ('198.18.0.2', 40420))
        time.sleep(0.01)
PY
```

Record the actual sequence list, `xsk rx_dropped`, `rx_invalid_descs`, `tx_invalid_descs`, selected-flow counters and final `received`. Requests beyond available chunks can be lost during starvation; later sequences show that refill restored progress. The receiver exits after reaching at least 16 or its eight-second deadline. Remaining burst packets then take the ordinary path, with no endpoint running; this unconnected burst socket neither reads replies nor claims delivery.

The 500 ms interval begins in the receiver, not in your shell. A late manual launch can miss it entirely. Scheduling, logging, packet buffering and the point of failure affect gaps and counters; do not expect a fixed missing range or exact drop total. `redirect` counts classifier attempts, not successful userspace delivery. `rx_dropped` is an AF_XDP socket counter, not a physical NIC loss count; invalid descriptor counters should remain zero and the program rejects nonzero values. The [receive implementation](https://github.com/torvalds/linux/blob/v6.12/net/xdp/xsk.c) distinguishes allocation failures from full RX-ring statistics. To reproduce the automatically coordinated experiment, first clean up the manual lab and run `sudo python3 scripts/test_network.py` from the checkout root. It owns setup, readiness waits, finite children and cleanup, and writes `.build/network/runtime-report.json` only after all cases succeed.

## Diagnose and clean up

A queue-topology error means this bounded receiver cannot cover the discovered interface; keep using the helper's single-queue link. An unknown interface usually means the command ran outside `hfs-lab`. An existing-program error is deliberate replacement refusal: stop your own controller and inspect its attachment instead of detaching an unidentified program. Permission, verifier or socket errors require the [13.3 availability checks](13.3-verify-af-xdp-memory.md), not a silent kernel or mode change.

`EBUSY` immediately after a previous socket closes can reflect deferred queue-pool release. The implementation retries only this error for at most two seconds, deleting/re-registering the failed UMEM attempt and resetting its ring pointers before retrying. Persistent failure exits with the device, queue, mode and errno; inspect remaining lab processes. A receive deadline failure exits nonzero and still follows owned detach and socket cleanup. Zero sequences with successful ordinary replies suggests absent redirection or a receiver that already finished; sender timeouts alone establish neither.

8. Let the bounded burst finish and stop remaining lab programs with Ctrl-C in their own terminals. **Pi — checkout root**:

```sh
sudo ip netns exec hfs-lab ip -details link show dev hfs-peer
sudo python3 scripts/network_lab.py cleanup
```

Normal cleanup sets mode to PASS, verifies program identity and detaches its own program before deleting the socket, unregistering UMEM and unmapping memory. Exception destruction preserves that order. SIGKILL or power loss cannot run this cleanup: inspect the actual attachment and ownership before recovery. The helper refuses deletion while namespace processes remain or recorded identities differ. Finish with no lab processes, attachment or namespace; the same course kernel and physical network configuration remain ready for [13.5](13.5-af-xdp-transmit-completion.md).
