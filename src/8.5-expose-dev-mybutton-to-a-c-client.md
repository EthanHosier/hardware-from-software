# 8.5 — Expose `/dev/mybutton` to a C++ client

You will run a C++ process that sleeps until the Pi button changes the driver's state, then prints a record from `/dev/mybutton`. The boundary is now a small **application binary interface (ABI)**: an agreement about bytes, readiness and errors that both sides must follow.

Start after [8.4](8.4-convert-gpio-events-into-driver-state.md), with the complete driver bound as verified in [8.3](8.3-describe-the-device-and-bind-the-driver.md#5-verify-the-device-then-load-and-verify-binding). Retain the Pi-only circuit: BCM17, physical 11 → 1 kΩ → LED anode; cathode → ground physical 9. BCM27, physical 13 → button → ground physical 14, with a 4.7 kΩ pull-up to Pi 3V3 physical 17. The [8.1 schematic](8.1-establish-a-userspace-gpio-baseline.md#1-separate-the-boards-and-build-the-pi-circuit) shows the switch contact pairs. Leave the Pico unplugged, its local circuit retained, and all inter-board bus and debug wires absent. Do not run `gpio_events` against the driver's owned lines.

The recorded hosted native Arm64 CI compiled the C++ client with the Linux userspace toolchain and compiled the kernel module against official **6.12.96+rpt-rpi-v8** headers; it did not load the module. **Physical runtime, including every `/dev/mybutton` experiment below, remains unexercised during authoring.** Outputs are illustrative. All commands here run in a **Pi SSH shell**, with working directory **`~/hardware-from-software`** unless stated otherwise. After a reboot, repeat 8.3's manual module insertion and binding verification first. The overlay persists in boot configuration; module autoload has not been configured.

## The record describes the latest state

A successful nonzero read returns one complete ASCII record:

```text
<sequence> <led0or1>\n
```

For example, `12 0` followed by a newline means the driver's accepted-press counter is 12 and its software LED state is off. The fields are unsigned decimal, separated by one space, with no NUL terminator. The LED value is 0 or 1. This is **software state**, not an electrical readback: the worker publishes state under its lock before setting the GPIO, so the physical LED can briefly lag the returned state.

`sequence` starts at zero for a newly probed device and increases for each accepted press, not releases. It is a 64-bit counter, practically monotonic during one device lifetime, with unsigned wrap after 2⁶⁴ increments. Rebinding creates a new lifetime and resets it. It is neither a timestamp nor a persistent count across boots.

Each separate `open` remembers its own last-seen sequence, initialised to the **current** sequence. Opening does not report old presses or an initial LED snapshot. Release an already-held button, allow the debounce worker to observe release, then make a new press. If a reader last saw 12 and three presses occur before its next read, it can receive `15 1\n` once. The difference records three accepted presses; intermediate LED states are gone. This is a latest-state/counter interface, **not an unlimited event queue**.

`misc_register` registers `mybutton` with a dynamically assigned minor number and our file operations. The misc core supplies `file->private_data` pointing to `struct miscdevice` before calling `hfs_open`. `container_of` recovers the enclosing device. Our open method allocates `hfs_reader`, retains a device reference, copies the current sequence under the device lock, and replaces `private_data` with that reader. Later callbacks therefore receive the reader, rather than the original misc pointer. This initial private-data convention is documented by [Linux 6.12's misc-device API](https://www.kernel.org/doc/html/v6.12/driver-api/misc_devices.html).

The reader mutex serialises reads sharing one open file description, including a descriptor duplicated with `dup` or inherited through `fork`. Those descriptors share one `seen` value; they do not each receive a copy of a press. Separate opens have independent reader objects and mutexes and can each observe the same latest sequence. The read method holds its reader mutex across the event wait. Use **one active read caller per open** in these experiments: even with `O_NONBLOCK`, a read sharing an open with another active reader may wait interruptibly to acquire that mutex. `O_NONBLOCK` skips the event wait only after mutex acquisition; it does not make this implementation entirely non-sleeping. The device spinlock protects a coherent sequence/LED snapshot across CPUs. `READ_ONCE`/`WRITE_ONCE` expose the reader's sequence to readiness checks; this source targets **64-bit Arm Linux**.

The following rules come from `hfs_read` and `hfs_poll`, not from regular-file conventions:

| Operation or condition | Result |
| --- | --- |
| `read` with size zero | Returns 0 immediately, even offline; consumes nothing. |
| Nonzero read, online, no new sequence, reader mutex acquired | Blocking descriptor waits interruptibly; `O_NONBLOCK` returns `EAGAIN`. |
| New sequence, buffer large enough | Copies one whole record and only then advances this reader's `seen`. A 64-byte client buffer is ample for the driver's 48-byte record buffer. |
| New sequence, buffer too short | `EINVAL`; no partial record and no advancement of `seen`. Retry with a larger buffer on the same open. |
| Failed `copy_to_user` | `EFAULT`; `seen` is unchanged. Some bytes may have reached the destination before the fault; discard them and retry safely. |
| Offline at the nonzero read's state check | `ENODEV`, even if an unread sequence remains. |
| Poll while online with a new sequence | `POLLIN` and `POLLRDNORM`. |
| Poll while offline | `POLLERR` and `POLLHUP`. |

The size check happens **after** finding a new sequence: a one-byte nonblocking read with no event gets `EAGAIN`, not `EINVAL`. The copy happens outside the spinlock, while holding the sleepable reader mutex. User memory must be accessed through `copy_to_user`, whose nonzero return counts bytes it could not copy and which may sleep. See [Linux's user-access rules](https://www.kernel.org/doc/html/v6.12/kernel-hacking/hacking.html#copy-to-user-copy-from-user-get-user-put-user).

A press arriving during copying remains pending if its sequence differs from the snapshot just delivered. After `EINVAL` or `EFAULT`, a later retry can return a newer snapshot if more presses occurred; preserving `seen` does not freeze history. Likewise, removal can race an already captured snapshot: an in-flight read can finish successfully before a subsequent read observes offline. [8.6](8.6-make-failure-and-teardown-behaviour-explicit.md) exercises that lifetime boundary.

`wait_event_interruptible` rechecks readiness when woken; waking alone is not proof of a new press. A signal can interrupt the wait or reader-mutex acquisition; at the userspace boundary the call can report `EINTR` or be restarted according to signal handling. Poll registers the same wait queue before checking state, then reports current readiness. It does not consume a record or reserve one for a particular thread. The [VFS documentation](https://www.kernel.org/doc/html/v6.12/filesystems/vfs.html#struct-file-operations) describes how these callbacks connect to system calls.

## 2. Grant access through a deliberate group policy

Keep the existing driver loaded. Inspect the node and the proposed rule destination:

```sh
cd ~/hardware-from-software
ls -l /dev/mybutton
getent group gpio
id
ls -l /etc/udev/rules.d/99-mybutton.rules
```

The final path should be absent on a first run. If it exists, inspect it before proceeding; retain an existing matching lesson rule, and resolve an unrelated rule rather than overwriting it. This lesson adopts the Pi's **existing `gpio` group** for access. Continue only if `getent` confirms that real group and that policy is appropriate on this Pi; otherwise choose the machine's administrator-approved group and adapt a local rule instead.

`SUBSYSTEM` and `KERNEL` limit the match to this misc device. `0660` grants owner/group read and write permission, with none for everyone else, following the [udev rule keys](https://github.com/systemd/systemd/blob/v252/man/udev.xml). The driver supplies no write operation, so this mode does not implement LED commands. On the Pi, install the rule only after the checks above:

```sh
sudo install -m 0644 examples/kernel/99-mybutton.rules \
  /etc/udev/rules.d/99-mybutton.rules
sudo udevadm control --reload-rules
sudo udevadm trigger --action=add /sys/class/misc/mybutton
sudo udevadm settle
ls -l /dev/mybutton
id
```

Reloading rules alone does not update an existing node; the trigger targets **only this device**. The [official udevadm manual](https://www.freedesktop.org/software/systemd/man/latest/udevadm.html) explains reload and trigger behaviour. Expect group `gpio` and mode `crw-rw----`; inspect any differing policy instead of applying `chmod 666`.

If this policy is installed and your account lacks `gpio`, run `sudo usermod -aG gpio "$USER"` **on the Pi**, then log out and reconnect. In the new Pi shell, return to `~/hardware-from-software` and verify `id` and `ls -l /dev/mybutton` again. Membership changes do not update an existing SSH process. No reboot is needed for this group change.

Build and run on the **Pi**, after releasing the button:

```sh
cd ~/hardware-from-software
mkdir -p .build
g++ -std=c++20 -Wall -Wextra -Wpedantic -O2 \
  examples/linux/button_client.cpp -o .build/button_client
./.build/button_client /dev/mybutton 3
```

It should wait silently. Press and release slowly, leaving roughly half a second between transitions. Illustrative output, with numbers depending on presses already accepted in 8.3 and 8.4:

```text
12 0
13 1
14 0
```

The client opens with `O_NONBLOCK`, then **sleeps in `poll`**, rather than blocking inside `read`. It checks error/hangup/invalid-descriptor bits before reading. A readiness race or interrupted read can produce `EAGAIN` or `EINTR`; the client retries. Other poll failures, offline indications and timeouts print `timeout, error, or device offline`, close the descriptor and return status 1. Open/read errors print their available error diagnostic. Argument errors return 2; counts must be 1–1000.

The requested count is the number of **successful reads**, not a sequence delta or proof of that many physical presses. The program prints returned bytes unchanged; it does not parse or validate the record. Each poll has a fresh 30-second timeout, including after retrying `EINTR`; there is no absolute overall deadline. For an idle-timeout experiment, rerun with count 1 and make no press after launch. Immediately after exit, `echo $?` reports the status. `poll` timeout and readiness meanings follow the [Linux poll manual](https://man7.org/linux/man-pages/man2/poll.2.html).

## 4. Exercise blocking reads and the short-buffer contract

These two complete Python 3 standard-library helpers run directly from the Pi shell; there is no extra test executable to build. Stop the C++ client first. For the blocking test, release the button and wait half a second, then run:

```sh
python3 - <<'PY'
import os
import signal

def expired(signum, frame):
    raise TimeoutError("no record within 30 seconds")

signal.signal(signal.SIGALRM, expired)
fd = os.open("/dev/mybutton", os.O_RDONLY | os.O_CLOEXEC)
try:
    signal.alarm(30)
    print("Blocking read armed: make one new press now", flush=True)
    print(repr(os.read(fd, 64)))
finally:
    signal.alarm(0)
    os.close(fd)
PY
```

Unlike the C++ client, this descriptor has no `O_NONBLOCK`. The nonzero read waits in the driver until a **future** accepted press, a signal or removal. The alarm bounds an idle experiment; on timeout Python raises `TimeoutError` and closes the descriptor.

Next release the button, wait half a second, and make **no press until the helper requests one**. Make only one press during its event phase:

```sh
python3 - <<'PY'
import errno
import os
import re
import select

fd = os.open("/dev/mybutton", os.O_RDONLY | os.O_NONBLOCK | os.O_CLOEXEC)
try:
    assert os.read(fd, 0) == b""
    try:
        os.read(fd, 64)
        raise AssertionError("unexpected press: release and rerun")
    except BlockingIOError as error:
        assert error.errno == errno.EAGAIN
        print("No new sequence: EAGAIN", flush=True)
    poller = select.poll()
    poller.register(fd, select.POLLIN)
    print("Make one new press within 30 seconds; then stop pressing", flush=True)
    events = poller.poll(30000)
    if not events:
        raise TimeoutError("no press within 30 seconds")
    mask = events[0][1]
    if mask & (select.POLLERR | select.POLLHUP | select.POLLNVAL):
        raise RuntimeError("device offline or poll error")
    assert mask & select.POLLIN
    try:
        os.read(fd, 1)
        raise AssertionError("one-byte read unexpectedly succeeded")
    except OSError as error:
        assert error.errno == errno.EINVAL
        print("Short buffer: EINVAL", flush=True)
    assert poller.poll(0), "short read consumed readiness"
    record = os.read(fd, 64)
    assert re.fullmatch(rb"[0-9]+ [01]\n", record), record
    print("Full retry:", repr(record))
finally:
    os.close(fd)
PY
```

The full retry on the **same open** demonstrates the expected short-buffer contract under the stated single-event condition. The source establishes that `seen` remains unchanged on failure; readiness alone would not establish that if another press or bounce produced a newer sequence. Closing and reopening would initialise `seen` to the current sequence and lose this demonstration. The helper checks the text shape; it does not simulate kernel behaviour or prove the electrical debounce is correct. A copy-fault test would require deliberately invalid user memory and is not part of these helpers.

## Diagnose and leave a known state

| Symptom | Check |
| --- | --- |
| No `/dev/mybutton` | Repeat 8.3's DT, module and binding checks. A loaded module alone is insufficient. |
| Permission denied | Inspect node mode/group, matching rules and current login groups. Reconnect after a membership change. |
| Silent wait then timeout | Press after opening; release an already-held button first. Recheck BCM27, physical 13, and switch contact pairs with power removed before rewiring. |
| Counter jumps | A slow reader received a coalesced latest snapshot. It has not demonstrated lost kernel increments. |
| One-byte read gets `EAGAIN` | No new sequence is available yet. Wait for readiness before testing `EINVAL`. |
| Text changes but LED does not | Check the Pi LED's polarity, resistor and physical 11/9 connections. Returned software state is not voltage evidence. |
| Offline/error output | Inspect binding and kernel messages; do not retry a stale descriptor indefinitely. |

Let each client finish or interrupt your own foreground instance with Ctrl-C; all process descriptors then close. The Python helpers close in `finally`. Closing a client does **not** unload the driver, relinquish its GPIO requests, or reset its LED. Leave the rule installed, driver bound, Pi-only wiring unchanged and no clients running for [8.6's concurrent-reader and teardown tests](8.6-make-failure-and-teardown-behaviour-explicit.md). To stop the project instead, close all clients and use 8.3's module/overlay cleanup. Remove `/etc/udev/rules.d/99-mybutton.rules` only if it is the lesson rule you installed, then reload rules; removing a rule alone does not revoke an already open descriptor.
