# 5.1 — Prepare Raspberry Pi OS and SSH

You will reach a Linux shell on the Pi 4 from your Mac, without a monitor or keyboard attached to the Pi. This is a new computer on the bench: the Pico firmware and its debugger are not involved. Finish [4.4's debugger cleanup](4.4-inspect-exception-entry-and-return.md#restore-the-free-running-program), then unplug Pico and probe. Keep their LED/button circuit intact and separate.

No physical Pi was imaged or reached over SSH during authoring. The procedure is source-reviewed; observations below are expectations for your bench, not a recorded successful installation.

## Prepare storage, power and a network

Use the Pi 4, its official USB-C supply, the 64 GB microSD card and the full-size SD adapter identified in [0.4](0.4-a-labelled-tour-of-the-debug-probe-and-cables.md). The microSD holds the data; the passive adapter merely lets it fit the Mac's SD reader. Remove the microSD from that adapter before inserting it into the Pi's underside slot. [0.3's board drawing](0.3-a-labelled-tour-of-your-raspberry-pi-4.md#orient-the-board) identifies the ports.

For this entire page, the Pi's **40-pin GPIO header is unwired**. No Pico, probe, LED, button, HAT or inter-board power connection is attached. The Pi's USB-C socket receives its own supply, not a Mac data lead. Place the board on a nonconductive surface with ventilation.

The Mac and Pi need a local network that allows devices to communicate. Normally the Mac remains on your existing Wi-Fi and the Pi joins that network. Pi 4 supports both 2.4 GHz and 5 GHz Wi-Fi ([specification](https://www.raspberrypi.com/products/raspberry-pi-4-model-b/#specifications)); it cannot join a 6 GHz-only network. A router Ethernet port and cable, if available, provide a useful alternative for the Pi. The Mac can stay on Wi-Fi if the router bridges those clients. A guest network's device isolation can prevent SSH even when both computers reach the internet. No router port forwarding is needed.

An **OS image** contains a partition layout, boot files and Linux filesystem. Imager writes these to the card; copying the downloaded image file into Finder does not install it. This differs from copying a Pico UF2 to its bootloader drive. The Pi also has bootloader firmware in on-board EEPROM: replacing the card replaces the OS and its data, not necessarily that EEPROM's contents. We do not select a bootloader recovery image here.

If your supplied card already contains a configured OS and you know its account, hostname and network settings, try the first-boot and SSH steps below before erasing anything. Then inspect its actual OS and architecture. A card labelled “Raspberry Pi OS” does not establish its release or credentials. Preserve any needed files before deciding to reimage. An unconfigured card with unknown credentials is not a reason to guess a default `pi` password.

## Choose the image and prepare an SSH key

Install the macOS version of [official Raspberry Pi Imager](https://www.raspberrypi.com/software/). Record its version from the application menu. This page follows the current tab-based workflow checked on **11 November 2026**, rather than older screenshots with an advanced-options gear.

For a fresh installation, deliberately choose **Raspberry Pi OS (Legacy) Lite (64-bit)**, based on Debian **12 (Bookworm)**. Lite omits the graphical desktop; SSH supplies the terminal we need. The [official download listing](https://www.raspberrypi.com/software/operating-systems/) checked on that date offers a **6 October 2026** Legacy Lite image with kernel series **6.12**. This course baseline aligns with the kernel family used for the book's compiled driver/header/source evidence. It does not pin your eventual kernel to that evidence's exact `6.12.96+rpt-rpi-v8` version: image revisions and APT updates can differ, so record the actual image date and running kernel.

The same listing offers current Raspberry Pi OS Lite (64-bit), Debian **13 (Trixie)** with kernel series **6.18**. An existing working 64-bit installation need not be erased simply to match this page. Record its versions and follow the later matching-header checks. The book does not claim its modules have been validated against 6.18, nor that this newer release is broken or unsupported.

Prefer a key for SSH authentication. The Pi receives a **public key**; the matching **private key stays on the Mac** and proves possession without being sent to the Pi. A passphrase protects that private-key file. It is distinct from the Pi account password, which you still set for local administration.

**Mac — Terminal, any working directory:** check whether the proposed dedicated filename exists:

```sh
ls -l ~/.ssh/hfs_pi_ed25519 ~/.ssh/hfs_pi_ed25519.pub
```

Missing files are expected for a new key. If either exists, reuse a known matching pair or choose another unused filename consistently; do not overwrite an existing key. For a new pair, first create the SSH directory if necessary and restrict access to your Mac account:

```sh
mkdir -p ~/.ssh
chmod 700 ~/.ssh
ssh-keygen -t ed25519 -f ~/.ssh/hfs_pi_ed25519 -C hardware-from-software
cat ~/.ssh/hfs_pi_ed25519.pub
```

Enter a passphrase at the prompts. Copy only the single public-key line printed by `cat`, beginning `ssh-ed25519`. Never paste the file without `.pub` into Imager. These options are documented by [OpenSSH's key utility](https://man.openbsd.org/ssh-keygen).

## Write only the intended card

1. Disconnect unrelated removable drives. Insert the microSD in its adapter and the adapter in the Mac. In Imager choose **Device → Raspberry Pi 4**, then find **Raspberry Pi OS (Legacy) Lite (64-bit)** among the Raspberry Pi OS variants. Check the description says **Bookworm**, **64-bit**, and **no desktop**; the first recommended entry may be another edition.
2. In **Storage**, keep **Exclude system drives** enabled. Identify the card by its capacity and device description; marketed 64 GB need not display as exactly 64. If uncertain, cancel, remove the adapter, and confirm which entry disappears before reinserting it. Do not select the Mac's internal storage or a backup drive.
3. Fill the customisation tabs using the table below. In **Writing**, inspect the summary again. **Writing erases all existing partitions and files on the selected storage device.** Confirm its identity before choosing **Write**, then **I understand, erase and write**. Allow verification to finish. Eject the card if Imager has not already done so.

| Customisation tab | Values for this bench |
| --- | --- |
| Hostname | A unique name such as `hfs-pi4`, without `.local` |
| Localisation | Your actual capital city/regulatory domain, time zone and keyboard layout |
| User | Your chosen lowercase Pi username and a strong account password; record them privately |
| Wi-Fi | Exact SSID and password; enable Hidden SSID only when applicable; inspect any prefilled values |
| Remote Access | Enable SSH; choose public key authentication and paste/browse the `.pub` key above |
| Raspberry Pi Connect | Leave disabled for this local SSH route |

Alternatively choose password authentication in Remote Access and use the account password when connecting. Localisation also selects the Wi-Fi regulatory domain; choose the country where the Pi operates. The UI sequence and settings are described in the [official Imager walkthrough](https://www.raspberrypi.com/documentation/computers/getting-started.html#install-using-imager). Do not skip customisation for this headless installation.

## Boot and connect from the Mac

4. With Pi power disconnected, insert the microSD into its underside slot. If using Ethernet, connect Pi Ethernet to the router now. Recheck the empty GPIO header, then connect the official USB-C supply. Allow several minutes for first-boot configuration; do not interrupt it because SSH is initially unavailable.
5. **Mac — Terminal, any directory:** replace the two example values with the username and hostname you actually configured. These shell variables contain no password:

```sh
PI_USER='your-pi-username'
PI_HOST='hfs-pi4.local'
ssh -o IdentitiesOnly=yes -i ~/.ssh/hfs_pi_ed25519 "$PI_USER@$PI_HOST"
```

For password authentication instead, use:

```sh
ssh "$PI_USER@$PI_HOST"
```

`user@host` selects an account on the remote machine; it does not use your Mac account automatically. `.local` discovery uses **mDNS**, a local-network name lookup service. It is not a public internet domain. The router typically assigns the Pi an IP address using DHCP; that address can change. If the name fails, open your router's client/DHCP list, identify the configured Pi hostname and use its current address:

```sh
PI_HOST='replace-with-pi-address-from-router'
ssh -o IdentitiesOnly=yes -i ~/.ssh/hfs_pi_ed25519 "$PI_USER@$PI_HOST"
```

Use the password-form command if that was your selected method. The [remote-access guide](https://www.raspberrypi.com/documentation/computers/remote-access.html#find-the-ip-address-of-your-raspberry-pi) explains discovery and SSH configuration. No network scan or invented example address is required.

### Recognise the server before trusting it

The first connection normally shows an authenticity prompt and a SHA256 **host-key fingerprint**. This is the Pi server's identity, separate from your user key. If you already have a trusted console or administrator-supplied fingerprint, compare it before accepting. On a trusted Pi console, this command prints the Ed25519 host fingerprint:

```sh
ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub
```

Compare the same key algorithm. Without an independent console, this setup uses **trust on first use**: confirm the new device in your own router's list on a trusted local network, understand that this does not independently authenticate its key, then type `yes` to remember it. Do not enter credentials if the destination is unexpected. `ssh-keyscan` alone would retrieve a key without proving whose key it is.

OpenSSH stores accepted identities in the Mac's `~/.ssh/known_hosts` and rejects unexpected changes ([SSH manual](https://man.openbsd.org/ssh)). A later **REMOTE HOST IDENTIFICATION HAS CHANGED** warning is a reason to stop. Check whether the address now belongs to another device. After you have deliberately reimaged this Pi and confirmed the destination, remove only its old entry, then repeat first-use verification:

**Mac — any directory; use the actual hostname/address:**

```sh
ssh-keygen -R hfs-pi4.local
```

If you also connected by IP, remove that confirmed old IP entry with a separate `ssh-keygen -R` command. Do not delete the entire known-hosts file or disable host-key checking.

## Check the shell, then update

6. After authentication, commands run on the **Pi**, through the Mac's terminal. SSH encrypts a network session to a Linux server process. It is not the Pico USB terminal or a GPIO serial console, and losing SSH does not itself stop Linux. Confirm which machine received your commands before using `sudo`.

**Pi — initial home directory `~`:**

```sh
whoami
hostname
tr -d '\0' < /proc/device-tree/model
printf '\n'
cat /etc/os-release
uname -m
uname -r
findmnt /
df -h /
vcgencmd get_throttled
```

Expect your selected account and hostname, a Raspberry Pi 4 model string, and `aarch64` for this 64-bit baseline. Read `/etc/os-release` for the actual release and retain the full `uname -r` value. The root filesystem should be mounted from the card, commonly `/dev/mmcblk0p2`, with substantial free space after expansion. A 64 GB card will not yield 64 GiB of usable root space; units, boot partition and filesystem overhead account for part of the difference. A tiny root filesystem merits investigation before updates.

An illustrative clean power/status result is `throttled=0x0`. It means none of the reported flags are set, not that supply quality has been measured. Bit `0x1` means current undervoltage; `0x10000` records earlier undervoltage since boot. Other bits describe frequency/thermal limiting; decode a nonzero result using the [utility reference](https://www.raspberrypi.com/documentation/computers/os.html#get_throttled) and resolve supply or cooling problems before continuing.

7. **Pi — same directory:** refresh package metadata, then update installed packages. Read the proposed changes before confirming:

```sh
sudo apt update
sudo apt full-upgrade
sudo reboot
```

Wait for each command to succeed before the next. The reboot intentionally drops SSH. Keep power connected. Reconnect from the **Mac** using the same SSH command after the Pi returns, then repeat `uname -r` and `vcgencmd get_throttled`. Updates can replace the kernel; the running version changes after reboot. This is the [official APT update route](https://www.raspberrypi.com/documentation/computers/os.html#update-your-current-raspberry-pi-software), not a major-release migration. Development packages belong to 5.2.

## Diagnose the observed failure

| Symptom | Next check |
| --- | --- |
| Hostname cannot be resolved | Try the router's current Pi IP. If that works, investigate mDNS or network isolation; credentials are not yet involved. |
| Connection times out | Wait for first boot; confirm power, card seating, network credentials, country and router client entry. Ensure both devices can communicate across the local network; a VPN or guest isolation may interfere. |
| Wi-Fi never joins | Recheck SSID/password and supported band. If a cable is available, try Pi Ethernet to the router and look for its wired address. A captive portal or enterprise login needs a different provisioning route from the simple SSID/password fields. |
| Connection refused at a confirmed Pi address | The machine is reachable but SSH may be disabled or still starting. With a trusted local console, run `sudo systemctl enable --now ssh`; without one, preserve data and reimage with SSH enabled. |
| Permission denied | Check Pi username, selected authentication method and public-key selection. A private-key passphrase prompt belongs to the Mac; an account-password prompt belongs to the Pi. Retry key login with `ssh -v -o IdentitiesOnly=yes -i ~/.ssh/hfs_pi_ed25519 "$PI_USER@$PI_HOST"` and inspect which key is offered. |
| Repeated disconnects or undervoltage flags | Use the official supply directly and leave unnecessary peripherals detached. Check cooling and power before treating it as an SSH problem. |
| No boot after several minutes; repeating LED code | Consult the [official LED-code table](https://www.raspberrypi.com/documentation/computers/configuration.html#led-warning-flash-codes). Recheck the selected OS/device and completed image verification before considering bootloader recovery. |

Keep credentials, private keys and verbose logs containing local network details out of the public book or issue reports.

## Leave a known state

For [5.2 — Verify the Linux development environment](5.2-verify-the-linux-development-environment.md), leave the updated Pi powered, networked and reachable, with its header still empty. Record the selected image date, OS release and running kernel privately. `exit` closes an SSH shell while leaving the Pi running; reconnect whenever needed.

To pack away instead, **Pi — any directory**, run:

```sh
sudo poweroff
```

The SSH session closes before all shutdown work necessarily finishes. Wait for shutdown activity to finish; the documented halt indication is **zero long, ten short ACT flashes**, rather than ordinary card activity. See the [LED-code table](https://www.raspberrypi.com/documentation/computers/configuration.html#led-warning-flash-codes). The red power light may remain on while the supply is attached. Once halted, disconnect the supply before removing the card or changing wiring. Restore power to boot again. Never join Pi and Pico power rails, and power down both before the later inter-board wiring lessons.
