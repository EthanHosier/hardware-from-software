# 1.4 — Make the build–flash–observe loop repeatable

A successful build tells you that the Mac produced firmware. It does not tell you which firmware the Pico is running. Here you will make a visible source change, carry it through the build and flash steps, and use the running program's identity to close that gap. You will also keep a recovery image that works even when an experimental program has no USB serial interface.

Complete [1.3 — Flash with BOOTSEL and read output](1.3-flash-with-bootsel-and-read-output.md) first: you should have observed `hardware-from-software heartbeat v1` from your non-wireless Pico 2. Keep the same data-capable USB cable and the assembled GP16 LED circuit: physical pin 21 → 1 kΩ → LED anode; cathode → GND physical pin 23. Leave the Pi, Debug Probe and button disconnected. No wiring changes are needed. Heartbeat configures neither the external nor onboard LED, so neither should be expected to blink.

## Keep source, build and board separate

The stable example name is `heartbeat`. Its source is `examples/pico/heartbeat.cpp`; its build products are `.build/pico/heartbeat.elf` for debugging and `.build/pico/heartbeat.uf2` for BOOTSEL copying. Changing a string does not change those filenames. Rebuilding replaces the products on the Mac; flashing replaces the installed firmware on the board.

This is the complete **downloaded baseline source**, also used in the preceding lessons:

```cpp
{{#include ../examples/pico/heartbeat.cpp}}
```

The edits below are local experiments for you to make in your copy. The downloadable baseline remains `v1` with `sleep_ms(1000)`. Keep the identity in every repeated line: a startup-only banner can be missed while the Mac discovers the USB device. The SDK's USB stdio implementation provides CDC serial output and uses interrupt/background work; it must be initialised by the application. [SDK 2.3.1 USB stdio](https://github.com/raspberrypi/pico-sdk/blob/2.3.1/src/rp2_common/pico_stdio_usb/include/pico/stdio_usb.h).

## 1. Save a known firmware image

Close the serial monitor before disconnecting the board. For macOS `screen`, press **Control-A**, release both keys, then press **Control-\**, and answer **Y** if asked to confirm. Control-A followed by D only detaches it and can leave the port open.

Check that your local source still matches the baseline above. Then build and preserve its UF2 before making experiments.

**Mac — working directory: `~/hardware-from-software`:**

```sh
cd ~/hardware-from-software
python3 scripts/setup_deps.py
python3 scripts/build_examples.py --pico
cp .build/pico/heartbeat.uf2 .build/heartbeat-v1-recovery.uf2
shasum -a 256 .build/pico/heartbeat.uf2 .build/heartbeat-v1-recovery.uf2
```

The two hashes should match. Keep this recovery file unchanged through the experiment. Call it known-good for your board only after observing its `v1` output there; compilation alone does not establish that. If you have changed source since lesson 1.3, restore the baseline, rebuild and flash it before assigning that meaning to this saved image.

## 2. Make two deliberate edits

Open `examples/pico/heartbeat.cpp` in your editor. Replace these two lines, shown as a **fragment of the baseline**:

```cpp
        std::printf("hardware-from-software heartbeat v1: %u\n", count++);
        sleep_ms(1000);
```

with this **experimental replacement fragment**:

```cpp
        std::printf("hardware-from-software heartbeat v2: %u\n", count++);
        sleep_ms(500);
```

Save the file. The string gives a direct identity check; the shorter delay gives a second observation. `500` requests half a second of sleep between iterations. USB and printing work add time, so do not treat the arrival interval as a clock measurement.

**Mac — working directory: `~/hardware-from-software`:**

```sh
cd ~/hardware-from-software
python3 scripts/build_examples.py --pico
ls -l .build/pico/heartbeat.elf .build/pico/heartbeat.uf2
```

Continue only if the build succeeds. A failed build can leave an older UF2 at the same path. Its presence, or a filename containing “heartbeat”, does not establish that it contains your saved changes.

## 3. Flash and rediscover the USB port

Unplug the Pico's USB cable, hold BOOTSEL, reconnect it to the Mac, then release BOOTSEL. Check for the `RP2350` volume. This name distinguishes Pico 2's loader from the older Pico's `RPI-RP2` volume. Copy the newly built file; the board should leave mass-storage mode and reboot. [Official BOOTSEL procedure](https://www.raspberrypi.com/documentation/microcontrollers/c_sdk.html#your-first-binaries).

**Mac — working directory: `~/hardware-from-software`; after entering BOOTSEL:**

```sh
cd ~/hardware-from-software
ls /Volumes
ls /Volumes/RP2350/INFO_UF2.TXT
cp .build/pico/heartbeat.uf2 /Volumes/RP2350/
```

If the volume has another mount path, identify the actual Pico volume first and substitute that path. Do not create a missing `/Volumes/RP2350` directory. The disappearing volume indicates that the loader has left this mode; it does not establish that your application has started successfully.

After reboot, list serial devices again. A previous port name may no longer apply:

**Mac — working directory: `~/hardware-from-software`:**

```sh
cd ~/hardware-from-software
find /dev -maxdepth 1 -name 'cu.usbmodem*' -print
```

Use the actual newly discovered Pico path. For example, **only if your listing contains this exact path**, run:

```sh
screen /dev/cu.usbmodem1101 115200
```

`115200` is the terminal setting used here; USB CDC is not a physical 115200-baud UART link. If several devices are listed, compare the listing with the Pico unplugged and reconnected. Reopen the port rather than waiting in an old terminal session.

Illustrative output, not a recorded board trace:

```text
hardware-from-software heartbeat v2: 14
hardware-from-software heartbeat v2: 15
hardware-from-software heartbeat v2: 16
```

Expect repeated `v2` lines more frequently than `v1`. The first visible counter need not be zero: the program may already have iterated before the monitor connected. The repeated identity is the stronger check. A report saying `v1` means you have not yet demonstrated the intended new image on the observed device.

## 4. Recover when application USB is absent

An application may fail before `stdio_init_all()`, omit it, or stop servicing USB. The missing serial device does not imply that the BOOTSEL loader is broken. BOOTSEL uses code in the RP2350's read-only boot ROM, independently of the application in external flash. [Raspberry Pi recovery documentation](https://www.raspberrypi.com/documentation/microcontrollers/pico-series.html#reset-flash-memory).

You can exercise this deliberately now. Exit `screen`. In your **local experimental source only**, replace the initialisation line with this **fault fragment**:

```cpp
    // stdio_init_all(); // Deliberate experiment: do not initialise USB stdio.
```

Rebuild with `python3 scripts/build_examples.py --pico`, and repeat step 3's BOOTSEL copy of `.build/pico/heartbeat.uf2`. This variant should not expose the application's USB serial device. Its lack of output is expected; a successful compile cannot detect this missing runtime initialisation.

To recover, unplug the Pico, hold BOOTSEL while reconnecting, release it, and verify the `RP2350` volume again. No running serial connection or software reset command is required.

**Mac — working directory: `~/hardware-from-software`; after re-entering BOOTSEL:**

```sh
cd ~/hardware-from-software
ls /Volumes/RP2350/INFO_UF2.TXT
cp .build/heartbeat-v1-recovery.uf2 /Volumes/RP2350/
```

Rediscover the port and reopen the monitor as above. Repeated `v1` output is the recovery observation. The saved file is important: rebuilding the faulty source again would merely regenerate the faulty firmware.

## Record what you actually used

Keep a small report beside the build. These commands select tools by explicit path, so another shell's `PATH` cannot silently select a different compiler.

**Mac — working directory: `~/hardware-from-software`; after a successful build:**

```sh
cd ~/hardware-from-software
{
    date -u
    sw_vers
    .deps/arm-gnu-toolchain-14.2.rel1-darwin-arm64-arm-none-eabi/bin/arm-none-eabi-gcc --version
    .deps/venv/bin/cmake --version
    .deps/venv/bin/ninja --version
    git -C .deps/pico-sdk rev-parse HEAD
    shasum -a 256 examples/pico/heartbeat.cpp examples/pico/CMakeLists.txt .build/pico/heartbeat.elf .build/pico/heartbeat.uf2 .build/heartbeat-v1-recovery.uf2
} > .build/heartbeat-version-report.txt
cat .build/heartbeat-version-report.txt
```

The book's compiled baseline used SDK **2.3.1**, commit `079c6f39023649b154152db30f1d781e884879bc`, Arm GNU **14.2.Rel1** (compiler `14.2.1`), CMake **3.31.6** and Ninja package **1.11.1.4** (executable banner `1.11.1.git.kitware.jobserver-1`). The script selects `pico2`, `rp2350-arm-s` and `Debug`. [SDK release identity](https://github.com/raspberrypi/pico-sdk/releases/tag/2.3.1). Add your observed firmware identity and whether the source contains the deliberate USB fault to your notes.

A checksum identifies file bytes, not board contents. This report associates the files present when you ran it; it does not prove that they were built together or flashed. Save it immediately after the successful build, and keep the separate serial observation. All twelve baseline Pico targets were compiled during book preparation; physical flashing and runtime were not exercised by the authors.

## Diagnose the observed symptom

**The build fails but a UF2 exists.** Treat it as potentially stale. Correct the error and finish a successful build before flashing. If configuration is inconsistent, preserve the generated directory under an unused backup name and rebuild as described in [1.2](1.2-understand-the-smallest-useful-project.md).

**The monitor still prints `v1` after the `v2` experiment.** Check that the editor saved the correct source, that the build succeeded, and that you copied `.build/pico/heartbeat.uf2` rather than the recovery file or a UF2 from Downloads. Close the monitor, identify the Pico's current port, and flash again.

**The volume disappears but no serial port appears.** That is the deliberate fault's expected symptom. With other firmware, allow time for enumeration, compare device listings, close old monitors and recover using BOOTSEL plus the saved image. Do not infer successful application startup from the copy operation.

**Neither BOOTSEL storage nor serial appears.** Start with the data cable, adapter/hub, connection and hold-BOOTSEL-during-power-up sequence. The application cannot remove the ROM loader, but a charge-only cable, missing power or damaged hardware can prevent the Mac seeing it. Do not alter the LED wiring while powered.

## Restore the next lesson's starting state

Exit the monitor. Restore all three baseline lines in your local source: uncomment `stdio_init_all();`, change `v2` back to `v1`, and change `sleep_ms(500)` back to `sleep_ms(1000)`. Compare with the complete baseline above. Rebuild successfully, regenerate the report, then flash `.build/pico/heartbeat.uf2` and confirm repeated `v1` output. This makes source, current build and installed application agree again.

Leave the external LED assembled and power the Pico down after closing the monitor. Keep the recovery image and report. [The next lesson](2.1-wire-and-verify-an-external-led.md) will make GP16 drive that circuit; heartbeat itself has made no LED test.
