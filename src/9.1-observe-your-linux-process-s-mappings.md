# 9.1 — Observe your Linux process's mappings

A pointer printed by a Linux program identifies a location in that process's **virtual address space**. It does not give you a RAM chip location or a peripheral register address. You will save two runs of a small program, classify its mappings, and create an ordinary anonymous mapping whose address Linux chooses.

Use the Pi development environment and checkout from [5.2](5.2-verify-the-linux-development-environment.md). After [8.6](8.6-make-failure-and-teardown-behaviour-explicit.md), retain its final state: driver bound, permissions rule installed, no clients running, and the Pi-only button and LED circuit unchanged. The Pico remains unplugged, its local circuit retained, with all inter-board bus and debug wires absent. This program neither opens GPIO devices nor changes driver binding; it also works if you chose 8.6's full cleanup. No wiring changes or new hardware are needed.

The shared example has been compiled for Linux, including hosted native Arm64; a hosted Linux run has also exercised its mapping and child-fault paths. That is software evidence, not a physical Pi runtime measurement. All output below is illustrative. Run the commands as your ordinary user in a **Pi SSH shell**, from **`~/hardware-from-software`**.

## Virtual addresses describe a process

Linux maintains mappings that associate virtual address ranges with backing storage and access permissions. The processor's memory-management unit uses page tables to translate accesses. Different processes can use the same virtual number without referring to the same memory; a mapping can also share backing pages with another process. A contiguous virtual range need not have contiguous physical backing. See the kernel's [memory-management concepts](https://docs.kernel.org/admin-guide/mm/concepts.html).

`/proc/self/maps` describes the process that opens it. Here, the C++ program opens the file itself, so the output describes `memory_lab`. Running `cat /proc/self/maps` instead describes `cat`, not your shell or a previously exited program. The kernel documents the mapping format in its [proc filesystem guide](https://www.kernel.org/doc/html/v6.12/filesystems/proc.html#process-specific-subdirectories).

## 1. Read and build the complete program

Use all of `examples/linux/memory_lab.cpp`. It performs both this page's mapping experiment and the next page's paging/protection experiment:

```cpp
{{#include ../examples/linux/memory_lab.cpp}}
```

Read its order carefully: it prints the existing mappings, queries the page size, creates a new mapping, writes one byte per page, then prints its new virtual address. Finally it forks a child that deliberately faults, waits for that child, unmaps the parent's region and exits. **The initial maps listing precedes this new allocation.** It cannot show the mapping created later. The program finishes quickly; there is no background process to inspect afterward.

Build on the **Pi**, working directory **`~/hardware-from-software`**:

```sh
cd ~/hardware-from-software
mkdir -p .build
g++ -std=c++20 -Wall -Wextra -Wpedantic -O2 \
  examples/linux/memory_lab.cpp -o .build/memory_lab
```

This is a native Linux executable, not Pico firmware. It needs neither the Pico SDK nor kernel-module headers.

## 2. Save two separate runs

On the **Pi**, in the same directory:

```sh
(ulimit -c 0; ./.build/memory_lab) > .build/memory-run-1.txt
echo $?
(ulimit -c 0; ./.build/memory_lab) > .build/memory-run-2.txt
echo $?
cat .build/memory-run-1.txt
cat .build/memory-run-2.txt
```

Each `echo` should report `0`. The output ends with a line beginning `virtual mapping=` and then `child protection fault: expected SIGSEGV`. The deliberate invalid write happens only in the child; the parent recognises the signal and returns success. [9.2](9.2-observe-demand-paging-and-protection-faults.md) explains that experiment and `minor_fault_delta` in detail.

The subshell's `ulimit` limits ordinary core files without changing your interactive shell's setting. The child also attempts to set its own core limit to zero. A system crash collector configured through a pipe in `core_pattern` can still receive a dump despite that limit; do not change system-wide crash policy for this lesson. See the [Linux core-dump manual](https://man7.org/linux/man-pages/man5/core.5.html).

## 3. Classify the saved mappings

Each mapping has this column order. These invented rows illustrate the format, **not a measured Pi layout**; paths, addresses, sizes, device numbers and inodes will differ:

```text
address                   perms offset   dev   inode pathname
aaaae1000000-aaaae1002000   r-xp  00002000  b3:02 12345 /home/pi/hardware-from-software/.build/memory_lab
aaaaf0000000-aaaaf0021000   rw-p  00000000  00:00 0     [heap]
ffff80000000-ffff80010000   rw-p  00000000  00:00 0
ffff81000000-ffff81180000   r-xp  00020000  b3:02 23456 /usr/lib/aarch64-linux-gnu/libc.so.6
ffffffe00000-ffffffff0000   rw-p  00000000  00:00 0     [stack]
```

The real file has no heading. Interpret a row using the [Linux maps manual](https://man7.org/linux/man-pages/man5/proc_pid_maps.5.html):

| Field | Meaning |
| --- | --- |
| `address` | Hexadecimal virtual bounds: start included, end excluded. The first example spans `0x2000` bytes. |
| `perms` | `r`, `w`, `x` permit reading, writing and execution; `-` omits a permission. The final `p` means private/copy-on-write; `s` means shared. |
| `offset` | Hexadecimal offset into the backing file, not a physical address. |
| `dev`, `inode` | Backing filesystem device's major/minor identifiers and inode number; inode zero means no associated inode. |
| `pathname` | Usually the backing file, a bracketed special label, or blank for an anonymous mapping. |

Locate rows naming `.build/memory_lab`, shared libraries, `[heap]`, `[stack]`, and rows with blank pathnames in your saved run. One executable or library commonly has several rows because its code and data have different permissions and file offsets. A library can have `p` mappings: its name being “shared library” does not require an `s` flag. Private file mappings can share unchanged physical pages while writes use copy-on-write.

`[heap]` identifies the traditional heap region, but it is not a list of all C++ dynamic allocations. The C library allocator can obtain memory through both the program break (`brk`) and anonymous `mmap`; its choices depend on allocation size and allocator state. See the [Linux allocator notes](https://man7.org/linux/man-pages/man3/malloc.3.html#NOTES). Likewise, a blank pathname does not identify a particular source variable.

The `[stack]` row covers the main thread's currently mapped virtual stack area. Its range is not the amount of RAM currently resident, nor necessarily its eventual growth limit. `maps` reports ranges and permissions; the separate `smaps` interface reports resident memory. These distinctions are documented in the [kernel proc guide](https://www.kernel.org/doc/html/v6.12/filesystems/proc.html). Do not add up mapping lengths and call the result physical RAM consumption.

## 4. Interpret the new mapping and compare runs

The program asks `sysconf(_SC_PAGESIZE)` for the page size in bytes instead of assuming 4096. Its mapping length is **128 times that value**: 512 KiB if the reported page size is 4096. `_SC_PAGESIZE` is a runtime configuration query, as specified by [sysconf](https://man7.org/linux/man-pages/man3/sysconf.3.html).

In `mmap`, `nullptr` asks Linux to choose a page-aligned address. `PROT_READ | PROT_WRITE` requests readable, writable memory; `MAP_ANONYMOUS` supplies zero-initialised memory without a backing file, so the descriptor is `-1` and offset is zero. `MAP_PRIVATE` requests private copy-on-write semantics. Failure returns `MAP_FAILED`, which the program checks before accessing memory. These are the [mmap API's defined behaviours](https://man7.org/linux/man-pages/man2/mmap.2.html).

Compare the two `virtual mapping=` values and the locations of the stack and libraries. With typical address-space layout randomisation (ASLR), many addresses change between executions. The [kernel's `randomize_va_space` documentation](https://www.kernel.org/doc/html/v6.12/admin-guide/sysctl/kernel.html#randomize-va-space) describes which regions the policy randomises, including executable placement for position-independent executables. Different values are common, not guaranteed for every region or every pair of runs. Matching values do not show that memory is physical; differing values do not show that the backing RAM changed. Keep the normal system policy and compare what your machine actually prints.

Neither the mapping pointer nor a maps row reveals physical page addresses. On the Pico, a documented RP2350 MMIO address names a peripheral in that microcontroller's address map. Pasting that number into a Linux process would supply a virtual address to a different processor's translation system. A cast, even to a `volatile` pointer, creates no mapping and grants no hardware ownership. We will trace Linux's existing controller driver in [9.3](9.3-trace-a-real-kernel-mmio-mapping.md), rather than dereferencing an MCU address on the Pi.

## Diagnose and leave a known state

| Symptom | Check |
| --- | --- |
| Missing `sys/mman.h`, `sys/resource.h`, or `/proc` | Confirm this is the Pi's Linux shell, not the Mac terminal. Use 5.2's native development environment. |
| Source or executable not found | Return to the checkout root; check `examples/linux/memory_lab.cpp` and rebuild. |
| Allocation error or nonzero exit | Read standard error and check user/container memory and process limits. Do not retry with `sudo`; ordinary user access is sufficient. |
| Printed pointer absent from the maps listing | Expected: that listing was printed before `mmap`. |
| Addresses match across runs | Compare more regions; ASLR policy and executable/linker choices affect placement. Do not disable protections to force a result. |
| `unexpected result`, or parent crashes | Retain the output, verify the complete source, and rebuild. The expected child signal is different from the parent itself failing. |

Both parent processes have exited and their mappings are gone; there is no manual memory release or hardware reset to perform. Keep `.build/memory_lab` and both output files for [9.2 — Observe demand paging and protection faults](9.2-observe-demand-paging-and-protection-faults.md). GPIO binding, wiring and the unplugged Pico state remain as they were on entry.
